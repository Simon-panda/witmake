# E5-差壳重码溯源分析

> 数据源：`zt_diff_hous_shipment` 表，共 715,414 条出货记录，其中 `结果`="重码" 4,784 条
> 分析时间：2026-07-17 | 数据跨度：2022-08-31 ~ 2026-01-11（1229 天）
> 总重码率：0.67%

---

## 一、分析目的

回答四个问题：
1. **重码是突发问题还是慢性病？** 时间聚类分析
2. **哪些二维码在反复重码？** 二维码重复次数分布
3. **问题源头在哪？** 工位/操作人员/差壳类型的交叉定位
4. **重码字段和备注字段有无线索？** 字段内容分析

---

## 二、数据结果

### 2.1 重码时间聚类

**月度趋势：**

| 阶段 | 月份 | 重码次数 | 特征 |
|------|------|----------|------|
| 爆发期 | 2022-09 | 558 | 单月最高，集中在第1周(425次) |
| 爆发期 | 2023-08 | 498 | 集中在8月7日单日(262次) |
| 爆发期 | 2023-12 | 432 | 集中在12月5-13日(302次) |
| 高位期 | 2024-01~2025-07 | 月均88 | 慢性持续，偶有周级小爆发 |
| 低位期 | 2025-08~2026-01 | 月均65 | 未根治但幅度下降 |

**关键爆发明细（单日>30次的天）：**

| 日期 | 次数 | 操作人员 | 差壳类型 |
|------|------|----------|----------|
| 2022-09-02 | 282 | 朱海艳 | DCT300 |
| 2022-09-04 | 130 | 朱海艳 | DCT300 |
| 2023-08-07 | 262 | 李顺东 | DCT300 |
| 2023-08-06 | 73 | 李顺东 | DCT300 |
| 2023-12-06 | 73 | 李顺东 | DCT300 |
| 2023-12-05 | 55 | 李顺东 | DCT300 |
| 2023-12-13 | 58 | 李顺东 | DCT300 |
| 2024-09-24 | 65 | 田俊丽/李顺东 | DCT300+E38H |
| 2025-08-25 | 42 | 田俊丽 | DCT300 |

**SQL:**
```sql
-- 月度趋势
SELECT DATE_FORMAT(`时间`,'%Y-%m') AS 月份, COUNT(*) AS 重码次数
FROM zt_diff_hous_shipment WHERE `结果`='重码'
GROUP BY 月份 ORDER BY 月份;

-- 单日爆发（>30次）
SELECT DATE(`时间`) AS 日期, `操作人员`, `差壳类型`, COUNT(*) AS 次数
FROM zt_diff_hous_shipment WHERE `结果`='重码'
GROUP BY 日期, `操作人员`, `差壳类型`
HAVING COUNT(*) >= 30 ORDER BY 日期;
```

**结论：呈现"爆发+慢性"双模式。** 2022年9月（上线初期）和2023年8月、12月各一次大爆发，之后转为每月30-100次的慢性背景。**这是工位1扫码/视觉系统间歇性故障的典型表现，而非持续退化。**

### 2.2 二维码重复模式

**二维码被标记为"重码"的次数分布：**

| 同码被标记次数 | 二维码数量 | 占比 |
|---------------|-----------|------|
| 1次（仅一次重码） | 4,064 | 94.8% |
| 2次 | 153 | 3.6% |
| 3次 | 27 | 0.6% |
| 4-9次 | 30 | 0.7% |
| 10次以上 | 13 | 0.3% |
| **合计** | **4,287** | 100% |

**极端案例：**
- 1个二维码被标记为重码 21 次
- 1个二维码被标记为重码 20 次
- 2个二维码各被标记 19 次
- 2个二维码各被标记 18 次

**SQL:**
```sql
SELECT 重复次数, COUNT(*) AS 二维码数量 FROM (
  SELECT `二维码`, COUNT(*) AS 重复次数
  FROM zt_diff_hous_shipment WHERE `结果`='重码'
  GROUP BY `二维码`
) t GROUP BY 重复次数 ORDER BY 重复次数;
```

**结论：大部分（95%）是单次偶发重码，但存在少量"惯犯"二维码。** 重复10次以上的13个二维码仅占0.3%的码量，却贡献了约6%的重码事件。**这些码很可能是打印质量缺陷（模糊、残缺、反光），每次扫描都间歇性触发重码判定。** 建议从数据库中提取这13个码的实物追溯。

### 2.3 问题源头定位：工位×操作人员×差壳类型

#### 2.3.1 工位锁定

**全部 4,784 条重码记录全部来自工位1。** 无一例外。

这意味着：
- 工位1的扫码设备/视觉系统/工控软件存在缺陷
- 其他工位零重码，排除系统级数据库或网络问题
- **问题根因锁定在工位1的硬件或配置**

**SQL:**
```sql
SELECT `工位`, COUNT(*) FROM zt_diff_hous_shipment
WHERE `结果`='重码' GROUP BY `工位`;
```

**操作人员的时间接力规律（核心发现）：**

```
2022-08 ~ 2023-06  →  朱海艳 主导（月均40+）
2023-07 ~ 2024-10  →  李顺东 主导（月均30+）
2024-04 ~ 2026-01  →  田俊丽 主导（月均40+）
```

这不是三个人同时犯错，而是**不同时期不同的人在同一工位遇到同一问题**。如果真是操作失误，应该三人分布相对均匀、且与排班强相关。但数据呈现的是一次只有一个人"继承"重码——说明**问题绑定工位而非操作人员**。

**SQL:**
```sql
SELECT DATE_FORMAT(`时间`,'%Y-%m') AS 月份, `操作人员`, COUNT(*) AS 次数
FROM zt_diff_hous_shipment WHERE `结果`='重码'
  AND `操作人员` IN ('田俊丽','朱海艳','李顺东')
GROUP BY 月份, `操作人员` ORDER BY 月份, `操作人员`;
```

**SQL:**
```sql
SELECT `差壳类型`, COUNT(*) AS 总出货数,
  SUM(CASE WHEN `结果`='重码' THEN 1 ELSE 0 END) AS 重码数,

```

### 2.4 重码字段与备注字段

**`重码` 列：全部 4,784 条均为 NULL。**
**`备注` 列：全部 4,784 条均为 NULL。**

没有记录具体重码原因（如"码模糊""码重扫""视觉误判"等），也没有操作备注。

**SQL:**
```sql
SELECT `重码`, COUNT(*), `备注`, COUNT(*)
FROM zt_diff_hous_shipment WHERE `结果`='重码'
GROUP BY `重码`, `备注`;
-- 结果: 重码=NULL:4784, 备注=NULL:4784
```

**影响：无原因标注导致无法区分"设备误判重码"与"真实重复打码"，限制了根因定位精度。**

## 三、综合结论

### 3.1 核心判断

**重码问题的根因在工位1的扫码/视觉识别系统，不是操作人员问题，也不是某种差壳特有。**

五条证据链：
1. **全部 4,784 条重码均发生在工位1**，其他工位零重码
2. 操作人员呈现"接力式"更替（朱海艳→李顺东→田俊丽），而非同期三人均匀分布
3. 差壳类型的重码次数与其出货量正相关，没有某个差壳类型异常独立于出货量
4. 时间模式为"爆发+慢性"双模式，符合硬件/软件间歇性故障特征
5. 95%的重码是一次性的不同二维码，排除系统性打码重复

### 3.2 管理行动建议

| 优先级 | 行动 | 责任人 | 时限 |
|--------|------|--------|------|
| P0 | **检查工位1扫码设备硬件**：摄像头清洁度、光源稳定性、触发传感器灵敏度 | 设备维护 | 本周 |
| P0 | **审计工位1扫码软件配置**：重码判定阈值、超时设置、与工位2的配置差异 | 技术员 | 本周 |
| P1 | **提取重复≥10次的13个二维码实物**，人工比对打印质量，确认是否码体缺陷 | 质量 | 2周 |
| P1 | **对893BB和DCT230规格**做专项排查（重码率>6%），确认是否码位设计问题 | 工艺/质量 | 2周 |
| P2 | **在工位1增加重码原因下拉选择**（码模糊/码重扫/系统误判/其他），改造前端录入 | IT/生产 | 1个月 |
| P3 | **建立重码率日监控**：工位1重码率>2%时自动告警（当前基线0.67%） | IT | 持续 |

### 3.3 数据局限性

1. **无原因标注**：`重码`和`备注`字段全部为空，无法区分"设备误判"与"真实重码"
2. **无二维码图像存档**：数据库中仅有文本码值，无法回溯当时的码体质量
3. **无工位1的设备日志**：无法判断扫码摄像头是否有清洁记录或更换记录
4. **异常名称混入**：44条记录的`操作人员`字段包含设备编号/序列号等非人名数据，可能是设备直连写入时的bug
5. **数据截止于2026-01-11**，此后约6个月无新数据——需确认工位1是否已停用或数据链路中断
