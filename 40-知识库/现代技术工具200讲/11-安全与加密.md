# 第11组：安全与加密

## 101. openssl

**前世今生：** OpenSSL 的前身是 Eric A. Young 和 Tim J. Hudson 于 1995 年开发的 SSLeay（"SSL, Eric A. Young" 的缩写）。1998 年 SSLeay 停止维护后，社区 fork 为 OpenSSL 项目，由 Ben Laurie、Ralf S. Engelschall 等人维护。OpenSSL 迅速成为互联网 TLS/SSL 的事实标准——几乎所有 HTTPS 网站背后的加密都由 OpenSSL 提供。2014 年 Heartbleed 漏洞（CVE-2014-0160）震动了整个互联网，暴露出 OpenSSL 长期资金和人力不足的问题。此后 Linux 基金会成立了 Core Infrastructure Initiative，OpenSSL 成为首批获得资助的关键项目。2018 年后 OpenSSL 3.0 引入了 Provider 架构（类似插件系统），支持 FIPS 140-3 认证。今天 OpenSSL 仍然是全球部署最广的密码学库。

**使用方法与案例：**

安装：
```bash
apt install openssl      # Linux (通常预装)
brew install openssl     # macOS
# Windows: 下载安装包或 winget install OpenSSL
```

**案例1：生成自签名证书用于内网测试**
```bash
# 一键生成私钥 + 自签名证书（365 天有效）
openssl req -x509 -newkey rsa:4096 -keyout key.pem -out cert.pem \
  -days 365 -nodes -subj "/CN=mes-server.internal"
# -nodes: 不加密私钥（方便自动化）
# 用于内网 HTTPS，避免浏览器"不安全"警告
```

**案例2：查看远程服务器证书信息**
```bash
# 查看证书详情
echo | openssl s_client -connect example.com:443 -servername example.com 2>/dev/null | \
  openssl x509 -noout -text | grep -E "Subject:|Not Before|Not After|DNS:"
```
输出证书主题、有效期、SAN 域名列表。用于排查证书过期、域名不匹配等问题。

**案例3：加密/解密文件**
```bash
# AES-256-CBC 加密
openssl enc -aes-256-cbc -salt -in report.pdf -out report.pdf.enc -pass pass:mysecret
# 解密
openssl enc -aes-256-cbc -d -in report.pdf.enc -out report_decrypted.pdf -pass pass:mysecret
# 计算文件哈希
openssl dgst -sha256 report.pdf
```

**进阶技巧：**
- `openssl s_time -connect example.com:443` 测试 TLS 握手性能
- `openssl rand -base64 32` 生成随机密码/Token
- PKCS#12 格式转换：`openssl pkcs12 -export -in cert.pem -inkey key.pem -out cert.pfx`（Windows/IIS 需要 PFX）

## 102. age

**前世今生：** age（Actually Good Encryption）由 Filippo Valsorda（前 Google Go 安全团队负责人）于 2019 年创建。Valsorda 对 GPG 的复杂性感到绝望——GPG 的 man page 有 1.6 万行，用户界面极其不友好。age 的设计哲学是"简单到不可能误用"：没有配置选项、没有算法选择、密钥文件就是一个随机字符串。age 2021 年被接纳为 IETF 标准草案（draft-irtf-cfrg-age）。虽然功能少于 GPG（不签名、不信任网络），但 age 在一个关键场景做到了极致：对称文件加密。它对标的是 "tar cz file | gpg -c" 这个最常见用法。

**使用方法与案例：**

安装：
```bash
go install filippo.io/age/cmd/...@latest   # Go
brew install age                           # macOS
apt install age                            # Debian/Ubuntu
```

**案例1：生成密钥对 + 加密文件**
```bash
# 生成密钥对
age-keygen -o key.txt
# key.txt 内容: # created: 2026-07-05
# # public key: age1ql3z7hjy54p3...
# AGE-SECRET-KEY-1...

# 查看公钥
age-keygen -y key.txt

# 用公钥加密
age -r age1ql3z7hjy54p3... -o report.pdf.age report.pdf

# 用私钥解密
age -d -i key.txt -o report.pdf report.pdf.age
```

**案例2：用密码加密（对称加密，不需要密钥文件）**
```bash
# 加密（提示输入密码）
age -p -o secret.txt.age secret.txt

# 解密
age -d -o secret.txt secret.txt.age
```

**案例3：批量加密给多个接收者**
```bash
age -r age1aaa... -r age1bbb... -r age1ccc... \
    -o shared_report.age report.pdf
# 三个公钥持有者中任何一人都能解密
```

**进阶技巧：**
- `age` 和 `ssh-keygen` 互操作：age 可以加密给 SSH 公钥（`age -R ~/.ssh/id_ed25519.pub`）
- 管道友好：`tar cz /data | age -r age1... > backup.tar.gz.age`
- 无元数据泄露：密文不含文件名、时间戳等明文信息

## 103. gpg (GnuPG)

**前世今生：** GnuPG（GNU Privacy Guard）由德国开发者 Werner Koch 于 1997 年创建，作为 PGP（Pretty Good Privacy）的 GPL 兼容替代。当时 Phil Zimmermann 的 PGP 受美国加密软件出口管制限制，欧洲急需一个不受 ITAR 约束的实现。Koch 用德国的 DM 资助（约 31.8 万欧元）完成了 GnuPG 1.0。GnuPG 完全兼容 OpenPGP 标准（RFC 4880），并逐步成为 Linux 发行版签名验证、Git commit 签名、APT 包验证的基础设施。2014 年 Koch 几乎因资金短缺放弃维护，直到 Linux 基金会和 Stripe 等公司提供资助。今天，`gpg --verify` 是验证软件完整性的标准方式。

**使用方法与案例：**

安装：
```bash
apt install gnupg       # Linux
brew install gnupg      # macOS
gpg4win                 # Windows（集成资源管理器右键菜单）
```

**案例1：生成 GPG 密钥 + 签名 Git Commit**
```bash
# 生成密钥（RSA 4096）
gpg --full-generate-key
# 选择: RSA and RSA / 4096 / 2y / 你的名字和邮箱

# 列出密钥
gpg --list-secret-keys --keyid-format LONG
# sec   rsa4096/3AA5C34371567BD2  ← 这个 ID 就是 GPG key ID

# 配置 Git 签名
git config --global user.signingkey 3AA5C34371567BD2
git config --global commit.gpgsign true

# 在 GitHub 上添加 GPG 公钥
gpg --armor --export 3AA5C34371567BD2
```

**案例2：加密文件发送**
```bash
# 用对方公钥加密
gpg --encrypt --recipient simon@company.com report.xlsx
# 生成 report.xlsx.gpg

# 对方解密
gpg --decrypt report.xlsx.gpg > report.xlsx
```

**案例3：签名验证（软件包完整性检查）**
```bash
# 下载软件 + 签名文件
wget https://example.com/app.tar.gz
wget https://example.com/app.tar.gz.asc

# 验证签名
gpg --verify app.tar.gz.asc app.tar.gz
# Good signature from "Developer <dev@example.com>" → 安全
# BAD signature → 文件被篡改或损坏
```

**进阶技巧：**
- `gpg --refresh-keys` 从密钥服务器更新公钥（过期/吊销信息）
- `gpg --export-secret-keys --armor > private.asc` 备份私钥（安全存储）
- `--trust-model tofu` 首次使用信任模型（减轻手动签名的负担）
- GPG agent：`gpg-connect-agent /bye` 管理密码缓存

## 104. sops

**前世今生：** sops（Secrets OPerationS）由 Mozilla 的 Julien Vehent 于 2015 年创建。Vehent 当时在 Mozilla 的安全团队，面临一个常见问题：如何把数据库密码、API 密钥存在 Git 里，同时保证安全？传统方案（加密整个文件 + .gitignore）导致看不到配置变更历史，不知道谁改了哪个密码。sops 的巧妙设计是"部分加密"——只加密 YAML/JSON 文件中的值，保留键和结构。文件可以安全地存在 Git 中，`git diff` 能看到结构变化。sops 支持 AWS KMS、GCP KMS、Azure Key Vault、age、GPG 多种后端。2023 年 sops 被 CNCF 接纳为沙箱项目。

**使用方法与案例：**

安装：
```bash
brew install sops              # macOS
apt install sops               # Debian/Ubuntu
go install go.mozilla.org/sops/v3/cmd/sops@latest
```

**案例1：用 age 加密配置文件**
```bash
# 创建 .sops.yaml（项目根目录，声明加密规则）
cat > .sops.yaml << 'EOF'
creation_rules:
  - age: age1ql3z7hjy54p3...   # 你的 age 公钥
EOF

# 创建带加密字段的配置
cat > config.yaml << 'EOF'
database:
  host: db.internal
  username: app_user
  password: ENC[AES256_GCM,data:...]   # ← 将被加密
EOF

# 加密
sops -e -i config.yaml
# 现在 password 字段被加密，其余明文。可以安全 git commit。

# 解密（编辑）
sops config.yaml     # 在 $EDITOR 中明文编辑
# 应用运行时解密
sops -d config.yaml | myapp --config /dev/stdin
```

**案例2：多环境密钥管理**
```yaml
# .sops.yaml
creation_rules:
  - path_regex: config/prod/.*\.yaml$
    age: age1prod...
  - path_regex: config/staging/.*\.yaml$
    age: age1staging...
  - path_regex: config/dev/.*\.yaml$
    age: age1dev...
```
开发人员只有 dev 密钥，无法解密生产配置，最小权限原则。

**案例3：跨云 KMS 加密（生产环境）**
```yaml
creation_rules:
  - aws_profile: production
    kms: arn:aws:kms:us-east-1:123456789:key/xxx
    gcp_kms: projects/myproject/locations/global/keyRings/sops/cryptoKeys/sops-key
```
加密后的文件，有 AWS 或 GCP 任一权限就能解密，实现跨云灾备。

**进阶技巧：**
- `sops updatekeys` 定期轮换加密密钥（不改秘书密文）
- `sops exec-env` 解密后注入环境变量：`sops exec-env config.enc.yaml 'myapp'`
- Helm 集成：`helm secrets` 插件底层用 sops
- `.sops.yaml` 可配置 `shamir_threshold`（门限解密：需要 N 个密钥中的 M 个）

## 105. certbot

**前世今生：** certbot 的前身是 EFF（电子前哨基金会）于 2015 年发布的 "Let's Encrypt 官方客户端"。Let's Encrypt 由 Mozilla、EFF、密歇根大学等联合发起，目标是实现 100% 的互联网 HTTPS 化。此前 HTTPS 证书年费 $50-$500，Let's Encrypt 免费提供且自动化。certbot 使用 ACME 协议自动验证域名所有权、签发证书、配置 Web 服务器。2016 年更名为 certbot。截至 2024 年，Let's Encrypt 已签发超过 4 亿张证书，全球 80%+ 的网页加载通过 HTTPS。certbot 是互联网安全的无名英雄。

**使用方法与案例：**

安装：
```bash
apt install certbot python3-certbot-nginx   # Nginx
apt install certbot python3-certbot-apache  # Apache
snap install certbot --classic              # 最新版
```

**案例1：一键获取 HTTPS 证书（Nginx）**
```bash
certbot --nginx -d mes.example.com -d api.example.com
# certbot 自动：
# 1. 验证域名所有权（HTTP-01 challenge）
# 2. 签发证书
# 3. 修改 Nginx 配置添加 HTTPS
# 4. 设置自动续期
```
全程交互式，不到 2 分钟。

**案例2：仅获取证书（不自动配 Web 服务器）**
```bash
certbot certonly --standalone -d mes.example.com
# 证书路径:
# /etc/letsencrypt/live/mes.example.com/fullchain.pem
# /etc/letsencrypt/live/mes.example.com/privkey.pem
```
适用于自己配 Nginx 或用于非 Web 服务（如 MQTT broker）。

**案例3：通配符证书（覆盖所有子域名）**
```bash
certbot certonly --manual --preferred-challenges dns \
  -d '*.example.com' -d example.com
# 需要在 DNS 添加 TXT 记录 _acme-challenge.example.com
# 一张证书覆盖: mes.example.com, api.example.com, docs.example.com...
```

**进阶技巧：**
- 自动续期：certbot 安装时自动加 cron/systemd timer，每天检查两次
- `certbot renew --dry-run` 测试续期是否正常（不实际签发）
- `--deploy-hook "systemctl reload nginx"` 续期后自动重载 Web 服务器
- 内网无公网端口：用 `--preferred-challenges dns` + DNS API 插件（Cloudflare、阿里云）

## 106. trivy

**前世今生：** trivy 由日本安全公司 Aqua Security 的 Teppei Fukuda 于 2019 年创建。Fukuda 发现现有的容器漏洞扫描工具（Clair、Anchore）太重，需要数据库服务、配置复杂，不适合开发者的日常使用。trivy 的设计哲学是"一命令扫描一切"——`trivy image nginx:latest` 无需任何配置。trivy 用 Go 编写，漏洞数据库以单文件嵌入二进制，离线也能扫描。2021 年后 trivy 从容器扫描扩展到文件系统、Git 仓库、K8s 集群、IaC 配置（Terraform/CloudFormation）。截至 2024 年 GitHub 已超 25k stars，是容器安全扫描的事实标准。

**使用方法与案例：**

安装：
```bash
brew install trivy                # macOS
apt install trivy                 # Debian/Ubuntu
curl -sfL https://raw.githubusercontent.com/aquasecurity/trivy/main/contrib/install.sh | sh
```

**案例1：扫描 Docker 镜像漏洞**
```bash
trivy image python:3.11-slim
```
输出：
```
python:3.11-slim (debian 12.5)
Total: 3 (UNKNOWN: 0, LOW: 1, MEDIUM: 1, HIGH: 1, CRITICAL: 0)

┌──────────────┬──────────────┬──────────┬────────┬───────────────────┐
│   Library    │ Vulnerability│ Severity │ Status │ Installed Version  │
├──────────────┼──────────────┼──────────┼────────┼───────────────────┤
│ libssl3      │ CVE-2024-... │ HIGH     │ fixed  │ 3.1.5-1            │
└──────────────┴──────────────┴──────────┴────────┴───────────────────┘
```

**案例2：扫描代码仓库里的密钥泄露**
```bash
trivy fs --scanners secret /path/to/repo
# 检测 AWS 密钥、GitHub Token、私钥等意外提交
```

**案例3：扫描 Terraform 配置的云安全风险**
```bash
trivy config ./terraform/
# 检查 S3 桶公开、安全组过于宽松、IAM 策略过度授权等
```

**进阶技巧：**
- `trivy image --ignore-unfixed` 只看已有修复的漏洞（更可靠）
- `trivy --severity CRITICAL,HIGH` 只看高危和严重漏洞
- `--format sarif` 输出为 GitHub 安全面板兼容格式
- trivy server 模式：集中化扫描，团队共享漏洞数据库

## 107. falco

**前世今生：** falco 由意大利安全公司 Sysdig 的 Loris Degioanni 于 2016 年创建，2018 年捐献给 CNCF。Degioanni 是系统调用追踪的前辈（Wireshark 创始人之一），他意识到传统安全工具（防火墙、IDS）对容器环境视而不见——容器内的异常行为无法从外部检测。falco 的独特机制是深入内核层：通过内核模块/eBPF probe 监控所有系统调用，用规则引擎匹配异常行为（如"容器内启动 shell"、"打开敏感文件"、"异常网络连接"），实时告警。2024 年 falco 从 CNCF 毕业。它是 Kubernetes 运行时安全的标杆项目。

**使用方法与案例：**

安装（K3s/Minikube 部署）：
```bash
helm repo add falcosecurity https://falcosecurity.github.io/charts
helm install falco falcosecurity/falco \
  --set falco.driver.kind=modern_ebpf   # 无需内核模块
```

**案例1：检测容器内异常 Shell 执行**
```yaml
# falco 内置规则自动检测:
# - 容器内启动 bash/sh
# - 写入 /etc/ 目录
# - 读取敏感文件 (/etc/shadow)
# - 非包管理器修改二进制文件
```
告警输出：
```
Warning: Shell spawned in container (user=root container_id=abc123
  container_name=nginx shell=bash parent=runc cmdline=bash -i)
```

**案例2：自定义规则——检测 MES 数据库未授权访问**
```yaml
# /etc/falco/falco_rules.local.yaml
- rule: Unauthorized MES DB Access
  desc: Detect access to production database from unexpected containers
  condition: >
    evt.type=connect and
    fd.sport=5432 and                                   # PostgreSQL port
    container.name not in (mes-api, mes-worker, db-admin)
  output: >
    Unauthorized PostgreSQL connection (container=%container.name
    proc=%proc.name ip=%fd.rip user=%user.name)
  priority: CRITICAL
```

**案例3：集成飞书告警**
```yaml
# falco.yaml
json_output: true
program_output:
  enabled: true
  program: |
    curl -X POST https://open.feishu.cn/open-apis/bot/v2/hook/xxx \
      -H "Content-Type: application/json" \
      -d '{"msg_type":"text","content":{"text":"Falco Alert: %container.name - %evt.type"}}'
```

**进阶技巧：**
- falcosidekick 项目：将 falco 告警转发到 40+ 个目标（Slack、飞书、Datadog、Webhook）
- `falco --list` 列出所有已加载规则
- `falco-driver-loader` 处理内核兼容性
- play 模式：录制系统调用 + 重放测试规则

## 108. crowdsec

**前世今生：** crowdsec 由法国开发者 Philippe Humeau 和 Thibault Koechlin 于 2019 年创建。他们发现 fail2ban（2004 年诞生）虽然经典，但设计模式过时了——每个服务器独立判断，攻击者换个 IP 继续。crowdsec 的核心创新是"协同式网络安全"：每个运行 crowdsec 的节点将攻击信息匿名上报到中央数据库，其他节点自动获得更新后的黑名单。类似于"网络安全的 Waze"（众包交通信息）。截至 2024 年 crowdsec 拥有超过 10 万个用户节点，共享 IP 信誉数据库覆盖数百万恶意 IP。

**使用方法与案例：**

安装：
```bash
curl -s https://packagecloud.io/install/repositories/crowdsec/crowdsec/script.deb.sh | sudo bash
apt install crowdsec
```

**案例1：自动保护 SSH 和 Web 服务**
```bash
# 安装后默认已保护 SSH
# 添加 Nginx 防护
cscli collections install crowdsecurity/nginx
systemctl reload crowdsec
```
crowdsec 自动解析 Nginx 访问日志，检测 SQL 注入、路径遍历、暴力破解等攻击并封禁 IP。

**案例2：查看攻击统计和控制面板**
```bash
cscli alerts list          # 查看最近告警
cscli decisions list       # 查看当前被封的 IP
cscli metrics              # 统计：攻击类型、来源国家、时间分布
```
Web 控制台（Metabase 集成）自动展示攻击趋势图。

**案例3：自定义场景——检测 MES API 异常调用**
```yaml
# /etc/crowdsec/scenarios/mes_bruteforce.yaml
type: leaky
name: mes-api-bruteforce
description: "Detect brute force on MES login API"
filter: "evt.Meta.service == 'http' && evt.Meta.log_type == 'mes_api'"
groupby: evt.Meta.source_ip
capacity: 5
leakspeed: "10s"
blackhole: 1m
labels:
  remediation: true
  classification: MES_BRUTE
```

**进阶技巧：**
- bouncer 组件：用 `cs-firewall-bouncer` 自动更新 iptables/nftables 规则
- `cscli hub update` 每周更新检测规则（类似杀毒软件更新病毒库）
- `cscli parsers install` 安装针对特定应用的日志解析器（如 PostgreSQL、Docker）
- crowdsec-appsec 模块做应用层 WAF（Web 应用防火墙）

## 109. gitleaks

**前世今生：** gitleaks 由 Zachary Rice 于 2018 年创建，最初是他在安全咨询工作中为自动化检测 Git 仓库里的密钥泄露而编写的 Go 工具。随着 GitHub 上每天数千个密钥意外泄露（AWS access key、GitHub token、私钥），gitleaks 迅速成为 CI/CD 流水线的标配检查项。gitleaks 的原理是用 150+ 条正则和熵检测规则扫描代码历史和增量变更。2022 年获得了 CNCF 和 Google 开源安全团队的支持。不同于 git-secrets（只支持 AWS），gitleaks 覆盖 GitHub/GitLab/Bitbucket/私钥/JWT/Slack Webhook 等多种密钥格式。

**使用方法与案例：**

安装：
```bash
brew install gitleaks             # macOS
go install github.com/gitleaks/gitleaks/v8@latest
# 或下载 GitHub Releases 二进制
```

**案例1：扫描当前仓库全部历史**
```bash
gitleaks detect --source . --verbose
```
输出：
```
Finding:     "AKIAIOSFODNN7EXAMPLE"
Secret:      AWS Access Key
RuleID:      aws-access-key
Commit:      a1b2c3d4
Author:      simon
File:        config/deploy.sh
Date:        2026-06-15
```
精准定位到具体的 commit、文件和作者。

**案例2：作为 pre-commit hook 阻止密钥提交**
```bash
# .pre-commit-config.yaml
repos:
  - repo: https://github.com/gitleaks/gitleaks
    rev: v8.18.0
    hooks:
      - id: gitleaks
```
现在每次 `git commit` 前自动扫描，发现密钥拒绝提交。

**案例3：仅扫描增量变更（CI/CD 快速扫描）**
```bash
# 只扫描最新提交到当前工作区的变更
gitleaks detect --source . --log-opts="HEAD~1..HEAD"
```

**进阶技巧：**
- `.gitleaks.toml` 自定义规则：增加自定义密钥模式、排除测试文件、排除已知假阳性
- `--no-git` 扫描非 Git 目录（纯文件扫描）
- `--format json --report-path report.json` 输出 SARIF/JSON 集成到安全平台
- Redact 模式：`gitleaks protect` 实时监控并阻止密钥提交

## 110. cosign

**前世今生：** cosign 由 Google 的 Dan Lorenc（也是 Tekton、Chainguard 联合创始人）和 Matt Moore 于 2021 年创建。软件供应链安全在 SolarWinds 攻击后成为焦点——"我下载的容器镜像真的是官方发布的，还是被篡改过的？" cosign 基于 Sigstore 项目，用 OIDC + 透明日志（Rekor）实现容器镜像的无密钥签名。你的 GitHub Actions/OIDC 身份就是你的签名密钥——不需要管理 GPG 密钥。2022 年 Sigstore 被 OpenSSF 采纳为供应链安全标准。2024 年 K8s 1.29 支持原生镜像签名验证。

**使用方法与案例：**

安装：
```bash
brew install cosign              # macOS
go install github.com/sigstore/cosign/v2/cmd/cosign@latest
```

**案例1：签名容器镜像（无密钥模式）**
```bash
# 在 CI/CD 中（如 GitHub Actions），只需：
cosign sign --yes ghcr.io/myorg/mes-api:v1.2.3
# cosign 自动用 OIDC token 签名 + 上传到 Rekor 透明日志
```

**案例2：验证镜像签名**
```bash
cosign verify \
  --certificate-identity https://github.com/myorg/mes//.github/workflows/release.yml@refs/heads/main \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com \
  ghcr.io/myorg/mes-api:v1.2.3
```
输出验证通过或失败。可集成到 K8s 准入控制器中，只允许签名过的镜像。

**案例3：签名任意文件（非容器）**
```bash
# 签名
cosign sign-blob --yes report.pdf --bundle report.pdf.sig

# 验证
cosign verify-blob --bundle report.pdf.sig report.pdf
```

**进阶技巧：**
- `cosign attest` 附加 SBOM 或漏洞扫描结果到镜像
- `cosign copy` 跨仓库复制镜像+签名
- 策略引擎：用 CUE/Rego 写策略（"只允许来自 GitHub Actions main 分支的镜像"）
- 私钥模式（不依赖 OIDC）：`cosign generate-key-pair` → `cosign sign --key cosign.key`
