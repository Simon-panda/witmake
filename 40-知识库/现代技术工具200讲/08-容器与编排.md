# 第8组: 容器与编排

从单体应用到微服务，从物理机到云原生——容器技术彻底改变了软件的构建、交付和运行方式。本组涵盖10个核心容器与编排工具，构成现代基础设施的基石。

---

### 71. Docker

**前世今生**

Docker 由 Solomon Hykes 于 2010 年在法国的 dotCloud 公司内部创建，2013 年 3 月作为开源项目发布——这个时间点被视为容器时代的元年。Docker 并非发明了容器技术（Linux 容器早在 2008 年就已存在于内核中），而是通过优雅的分层镜像模型、简单的 Dockerfile 语法和统一的 CLI/Daemon 架构，让容器变得平易近人。2014 年 Docker 1.0 发布，随之而来的 Docker Hub 镜像仓库、Docker Compose 编排工具和 Docker Swarm 集群方案形成了完整生态。2015 年 Docker 贡献 runc 和 containerd 给 OCI（开放容器倡议），推动了容器标准的行业统一。虽然 Docker 在容器编排大战中输给了 Kubernetes（2017 年将 Docker Enterprise 出售给 Mirantis），但作为开发和 CI/CD 的核心工具，Docker 至今仍是开发者学习容器的第一站，Docker Hub 拥有超过 1000 万个镜像仓库。

**使用方法与案例**

**安装：**
```bash
# macOS
brew install --cask docker
# 启动 Docker Desktop 应用

# Linux (Ubuntu)
sudo apt update && sudo apt install docker.io
sudo usermod -aG docker $USER  # 免 sudo 使用

# Windows
# 下载 Docker Desktop: https://docker.com/products/docker-desktop
# 或通过 winget: winget install Docker.DockerDesktop
```

**核心命令：**
```bash
docker run -d -p 80:80 nginx        # 启动容器
docker build -t myapp:v1 .          # 构建镜像
docker ps                           # 列出运行中的容器
docker exec -it <id> /bin/bash      # 进入容器
docker-compose up -d                # 启动多容器应用
```

**案例一：Dockerfile 多阶段构建——Go 应用**
```dockerfile
# 阶段1: 编译
FROM golang:1.22-alpine AS builder
WORKDIR /app
COPY go.mod go.sum ./
RUN go mod download
COPY . .
RUN CGO_ENABLED=0 go build -o server .

# 阶段2: 最小运行镜像
FROM alpine:3.19
RUN apk add --no-cache ca-certificates
COPY --from=builder /app/server /server
EXPOSE 8080
ENTRYPOINT ["/server"]
```
```bash
docker build -t go-server .
docker run -d -p 8080:8080 --name myapp go-server
```

**案例二：Docker Compose 编排 LAMP 栈**
```yaml
# docker-compose.yml
services:
  web:
    image: nginx:alpine
    ports: ["80:80"]
    volumes: ["./html:/usr/share/nginx/html"]
    depends_on: [app]
  app:
    build: ./php
    volumes: ["./php:/var/www/html"]
    depends_on: [db]
  db:
    image: mysql:8
    environment:
      MYSQL_ROOT_PASSWORD: secret
    volumes: ["db_data:/var/lib/mysql"]

volumes:
  db_data:
```
```bash
docker-compose up -d
docker-compose logs -f app
docker-compose down -v
```

**案例三：Docker 资源限制与监控**
```bash
# 限制 CPU 和内存
docker run -d --cpus="1.5" --memory="512m" --name limited-app nginx

# 查看资源使用
docker stats limited-app

# 查看容器日志（含时间戳）
docker logs -f --tail 100 --timestamps limited-app

# 清理未使用的资源
docker system prune -a --volumes --force
```

**进阶技巧：** 使用 `.dockerignore` 排除不需要的文件，加速构建并减小镜像。多阶段构建可将最终镜像缩小 90% 以上。`docker buildx` 支持多平台构建（`--platform linux/amd64,linux/arm64`）。避免在 Dockerfile 中使用 `latest` 标签——固定版本号确保可复现性。`docker scan` 可扫描镜像安全漏洞。使用 `HEALTHCHECK` 指令定义容器健康检查。

### 72. Podman

**前世今生**

Podman（Pod Manager）由 Red Hat 的 Daniel Walsh 团队于 2017 年创建，2018 年发布 1.0 版本。它的诞生源于对 Docker Daemon 架构安全性的担忧——Docker 需要一个以 root 权限运行的守护进程，这构成了潜在的攻击面。Podman 的设计核心理念是"无守护进程"（daemonless）——直接通过 runc 或 crun 启动容器，无需后台常驻进程，每个容器作为用户进程运行。Podman 还首创了"rootless 容器"概念，允许普通用户安全地运行容器而无需 root 权限。它的 CLI 有意与 Docker 兼容（甚至可以 `alias docker=podman`），降低了迁移成本。2022 年 Red Hat Enterprise Linux 8 后完全移除了 Docker 支持，Podman 成为默认容器引擎。Podman 还引入了 Pod 概念（受 Kubernetes Pod 启发），可以在本地模拟 K8s Pod 运行模式。

**使用方法与案例**

**安装：**
```bash
# macOS
brew install podman
podman machine init && podman machine start

# Linux (RHEL/CentOS/Fedora)
sudo dnf install podman -y

# Linux (Ubuntu/Debian)
sudo apt install podman -y

# Windows
winget install RedHat.Podman
# 或通过: https://github.com/containers/podman/releases
```

**核心命令：**
```bash
podman run -d -p 8080:80 nginx       # 与 docker 命令兼容
podman pod create --name mypod       # 创建 Pod
podman machine ssh                   # 进入虚拟机（macOS）
systemctl --user enable podman.socket # 启用 socket
```

**案例一：Rootless 容器——作为普通用户运行**
```bash
# 无需 sudo，直接以普通用户身份运行
podman run -d --name web -p 8080:80 docker.io/nginx

# 验证容器以当前用户权限运行
ps aux | grep nginx
# 输出显示进程属于当前用户，而非 root

# 查看容器文件系统（无需 root）
podman unshare ls -la ~/.local/share/containers/storage/
```

**案例二：Pod 模式——模拟 Kubernetes Pod**
```bash
# 创建一个包含两个容器的 Pod（共享网络命名空间）
podman pod create --name myapp-pod -p 8080:80

# 在 Pod 中添加容器
podman run -d --pod myapp-pod --name web nginx:alpine
podman run -d --pod myapp-pod --name sidecar alpine \
  sh -c "while true; do echo 'heartbeat at' $(date); sleep 5; done"

# 查看 Pod 状态（类似 kubectl get pods）
podman pod ps
podman pod inspect myapp-pod

# 一键生成 Kubernetes YAML
podman generate kube myapp-pod > pod.yaml
```

**案例三：Podman Compose 替代 Docker Compose**
```yaml
# podman-compose.yml（或 docker-compose.yml）
services:
  redis:
    image: docker.io/redis:alpine
    ports: ["6379:6379"]
  app:
    image: docker.io/python:3.12-alpine
    command: python -m http.server 8000
    ports: ["8000:8000"]
    depends_on: [redis]
```
```bash
# 安装 podman-compose
pip install podman-compose

# 启动
podman-compose up -d
podman-compose logs
podman-compose down
```

**进阶技巧：** Podman 的 `--replace` 标志可原子替换容器。`podman auto-update` 结合 systemd 定时器实现自动更新。`podman image scp` 可在主机间复制镜像。使用 `podman machine` 在 macOS/Windows 上管理 Linux VM。Podman 的 API 兼容 Docker API（通过 `podman.socket`），可作为 Docker Desktop 的直接替代。注意 rootless 模式下某些端口范围受限（<1024 不可用）。

### 73. Kubernetes (k8s)

**前世今生**

Kubernetes（希腊语意为"舵手"或"领航员"，简称 k8s）诞生于 Google 内部，由 Joe Beda、Brendan Burns 和 Craig McLuckie 于 2014 年创建。它源于 Google 运行了十多年的内部容器编排系统 Borg 和 Omega 的经验。2015 年 7 月，Kubernetes 1.0 发布并捐赠给新成立的 CNCF（云原生计算基金会），成为其第一个毕业项目。短短几年内，K8s 在与 Docker Swarm 和 Apache Mesos 的编排器大战中胜出，成为事实标准——AWS EKS、Azure AKS、Google GKE 几乎所有云厂商都提供托管 K8s 服务。Kubernetes 的核心抽象——Pod、Service、Deployment、Ingress——彻底改变了应用部署范式，从"在服务器上运行程序"转变为"声明期望状态并让系统自动调谐"。2024 年，Kubernetes 已发布 30 个版本，被全球超过 60% 的企业采用。

**使用方法与案例**

**安装（本地开发）：**
```bash
# minikube - 单节点本地集群
curl -LO https://storage.googleapis.com/minikube/releases/latest/minikube-linux-amd64
sudo install minikube-linux-amd64 /usr/local/bin/minikube
minikube start

# kind (Kubernetes IN Docker) - 推荐用于 CI/测试
brew install kind              # macOS
kind create cluster --name dev

# k3s - 轻量级，适合边缘/ARM
curl -sfL https://get.k3s.io | sh
```

**核心命令：**
```bash
kubectl get pods                     # 查看 Pod
kubectl apply -f deployment.yaml     # 部署应用
kubectl logs -f <pod>               # 查看日志
kubectl exec -it <pod> -- /bin/sh   # 进入容器
kubectl port-forward <pod> 8080:80  # 端口转发
```

**案例一：完整应用部署（Deployment + Service + Ingress）**
```yaml
# app.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: nginx-deploy
spec:
  replicas: 3
  selector:
    matchLabels:
      app: nginx
  template:
    metadata:
      labels:
        app: nginx
    spec:
      containers:
      - name: nginx
        image: nginx:1.25
        ports:
        - containerPort: 80
        resources:
          requests: {memory: "64Mi", cpu: "100m"}
          limits:   {memory: "128Mi", cpu: "200m"}
        livenessProbe:
          httpGet: {path: /, port: 80}
---
apiVersion: v1
kind: Service
metadata:
  name: nginx-svc
spec:
  selector:
    app: nginx
  ports:
  - port: 80
    targetPort: 80
  type: LoadBalancer
```
```bash
kubectl apply -f app.yaml
kubectl rollout status deployment/nginx-deploy
kubectl scale deployment nginx-deploy --replicas=5
```

**案例二：ConfigMap + Secret 管理配置**
```yaml
# config.yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: app-config
data:
  app.properties: |
    db.host=postgres-svc
    cache.ttl=300
---
apiVersion: v1
kind: Secret
metadata:
  name: db-secret
type: Opaque
stringData:
  password: "MyS3cret!"
```
```bash
kubectl create secret generic api-key --from-literal=key=abc123

# 在 Pod 中使用
kubectl set env deployment/myapp --from=configmap/app-config
kubectl get secret db-secret -o jsonpath="{.data.password}" | base64 -d
```

**案例三：Helm Chart 部署 + 回滚**
```bash
# 添加 Helm 仓库
helm repo add bitnami https://charts.bitnami.com/bitnami
helm repo update

# 安装 Redis 集群
helm install my-redis bitnami/redis \
  --set architecture=replication \
  --set auth.password=secret123

# 查看部署状态
helm list
kubectl get all -l app.kubernetes.io/instance=my-redis

# 升级与回滚
helm upgrade my-redis bitnami/redis --set replica.replicaCount=5
helm rollback my-redis 1
```

**进阶技巧：** `kubectl explain` 随时查阅资源定义。`kubectx` + `kubens` 快速切换集群和命名空间。`k9s` 是 TUI 交互式管理面板。Pod 的 `restartPolicy: Always` 是生产默认配置。使用 `ResourceQuota` 和 `LimitRange` 控制多租户资源。`kubectl debug` 可以创建临时调试容器。善用 `kubectl diff -f manifest.yaml` 预览变更。

### 74. k9s

**前世今生**

k9s 由 Fernando "Fred" Chiocca 于 2019 年创建，是一个基于终端的 Kubernetes 集群管理 TUI（终端用户界面）。Chiocca 作为一位频繁在多个集群间切换的 SRE 工程师，发现 `kubectl` 命令行虽然功能强大，但在实时监控和快速导航方面效率低下——每次必须完整输入命令、频繁复制粘贴资源名。k9s 的灵感来自 Unix 哲学和 vim 风格键盘操作，它将 Kubernetes 资源以可滚动、可搜索、可交互的表格形式展示，支持一键进入 Pod 日志、Shell、描述 YAML、编辑资源等操作。它使用 Go 语言编写，单个二进制文件部署，无需服务端组件。k9s 迅速成为云原生工程师的标准工具箱之一，在 GitHub 上获得超过 2.5 万星标，被纳入 CNCF 沙箱项目。

**使用方法与案例**

**安装：**
```bash
# macOS
brew install k9s

# Linux
curl -sS https://webinstall.dev/k9s | bash
# 或直接下载: https://github.com/derailed/k9s/releases

# Windows
winget install derailed.k9s
```

**核心操作（键盘快捷键，需先运行 `k9s`）：**
```bash
:namespace         # 切换命名空间（按冒号输入）
:pods              # 查看 Pods（同样 :deploy, :svc, :node 等）
/ 搜索词           # 搜索过滤
d                  # 描述资源
e                  # 编辑资源 YAML
l                  # 查看日志
s                  # 进入 Shell
Ctrl+D             # 删除资源
?                  # 显示所有快捷键
ESC                # 返回上一级
```

**案例一：快速诊断故障 Pod**
```bash
# 启动 k9s（自动连接当前 kubeconfig 上下文）
k9s

# 界面操作流程:
# 1. 按 0 查看所有命名空间的 Pod
# 2. 按 / 然后输入 "Error|CrashLoop" 过滤问题 Pod
# 3. 光标移到问题 Pod，按 l 查看日志
# 4. 按 0 切换显示所有容器日志
# 5. 按 w 开启自动换行便于阅读
# 6. 按 s 进入容器 Shell 执行诊断命令
```

**案例二：实时监控资源使用**
```bash
k9s

# 在 k9s 内操作:
# 1. 按 :pods 进入 Pod 视图
# 2. 按 :pulses 查看集群实时健康仪表盘
#    显示 CPU、MEM、Pod 状态等趋势图
# 3. 按 :xray 查看资源关系图（Xray 视图）
#    可视化展示 Deployment → ReplicaSet → Pod 层级
```

**案例三：批量操作与集群切换**
```bash
k9s

# 批量删除:
# 1. :pods 进入 Pod 视图
# 2. 空格键标记多个 Pod（标记后显示 + 符号）
# 3. Ctrl+D 批量删除标记的 Pod

# 集群切换:
# 1. 按 :ctx 查看所有 context
# 2. 直接按回车切换到选中的集群

# 自定义配置 (~/.config/k9s/config.yaml):
k9s:
  liveViewAutoRefresh: false
  screenDumpDir: /tmp/k9s-screens
  refreshRate: 2
  maxConnRetry: 5
```

**进阶技巧：** 配置 `$K9S_EDITOR` 环境变量指定编辑资源的编辑器（如 `nvim`）。k9s 支持插件系统，可自定义快捷键映射到自定义命令。`k9s --readonly` 只读模式防止误操作。使用 `k9s info` 查看当前连接信息。`:pulses` 命令可快速一览集群健康度。`Ctrl+A` 查看所有别名资源。日志视图中按 `w` 切换自动换行。

### 75. Helm

**前世今生**

Helm（意为"舵柄"）由 Deis 公司（后被微软收购）的 Matt Butcher 和 Matt Farina 等人于 2015 年创建，2016 年加入 Kubernetes 组织，2018 年 6 月发布 Helm 3（完全重构）。它被称为"Kubernetes 的包管理器"，类似于 apt/yum/brew——但管理的是 K8s 应用而非系统包。Helm 的核心概念是 Chart（应用包）和 Release（部署实例），通过 Go template 模板引擎将可复用的 Kubernetes YAML 模板化。Helm 3 移除了 Helm 2 中需要服务端组件 Tiller 的安全隐患，所有操作直接在客户端完成。如今 Helm 是部署 Kubernetes 应用最主流的方式，Artifact Hub 拥有超过 1 万个 Chart，几乎所有云原生项目（Prometheus、Grafana、Istio、ArgoCD）都提供官方 Helm Chart。

**使用方法与案例**

**安装：**
```bash
# macOS
brew install helm

# Linux
curl https://raw.githubusercontent.com/helm/helm/main/scripts/get-helm-3 | bash

# Windows
winget install Helm.Helm
```

**核心命令：**
```bash
helm repo add bitnami https://charts.bitnami.com/bitnami
helm search repo nginx            # 搜索 Chart
helm install myapp ./chart        # 安装本地 Chart
helm upgrade myapp ./chart        # 升级
helm rollback myapp 1             # 回滚
helm uninstall myapp              # 卸载
```

**案例一：创建并部署自定义 Chart**
```bash
# 创建 Chart 脚手架
helm create my-webapp

# 目录结构:
# my-webapp/
# ├── Chart.yaml          # Chart 元数据
# ├── values.yaml         # 默认配置值
# ├── templates/
# │   ├── deployment.yaml
# │   ├── service.yaml
# │   └── _helpers.tpl    # 模板辅助函数
# └── charts/             # 依赖子 Chart
```

```yaml
# values.yaml - 自定义配置
replicaCount: 3
image:
  repository: nginx
  tag: "1.25"
service:
  type: ClusterIP
  port: 80
ingress:
  enabled: true
  host: myapp.local
resources:
  limits: {memory: "128Mi", cpu: "200m"}
```

```bash
# 试运行（验证但不部署）
helm install myapp ./my-webapp --dry-run --debug

# 部署到指定命名空间
helm install myapp ./my-webapp -n production --create-namespace

# 使用自定义 values 文件
helm upgrade myapp ./my-webapp -f prod-values.yaml
```

**案例二：使用 Library Chart 管理公共模板**
```yaml
# library-chart/templates/_service.yaml
{{- define "mylib.service" -}}
apiVersion: v1
kind: Service
metadata:
  name: {{ .Release.Name }}
spec:
  ports:
  - port: {{ .Values.service.port }}
  selector:
    app: {{ .Release.Name }}
{{- end -}}
```

```yaml
# 在应用 Chart 中调用 library
dependencies:
  - name: mylib
    version: 1.0.0
    repository: "file://../library-chart"
```

**案例三：Helm Hooks 实现部署流程控制**
```yaml
# templates/db-migration.yaml
apiVersion: batch/v1
kind: Job
metadata:
  name: {{ .Release.Name }}-db-migrate
  annotations:
    "helm.sh/hook": pre-upgrade     # 升级前执行
    "helm.sh/hook-weight": "5"      # 执行顺序
    "helm.sh/hook-delete-policy": hook-succeeded
spec:
  template:
    spec:
      restartPolicy: Never
      containers:
      - name: migrate
        image: myapp-migrate:{{ .Values.image.tag }}
        command: ["./migrate", "up"]
```
```bash
helm upgrade myapp ./chart --wait  # 等待 hook 执行完毕
```

**进阶技巧：** `helm lint` 检查 Chart 语法。`helm template` 渲染模板查看最终 YAML。`helm dependency update` 下载子 Chart 依赖。使用 `tpl` 函数在 values.yaml 中嵌入模板表达式。`--set` 覆盖 values 适合 CI/CD 流水线。Chart 版本遵循语义化版本（SemVer 2）。善用 `NOTES.txt` 为 Chart 用户提供部署后的使用说明。

### 76. Lima

**前世今生**

Lima（Linux MAchines）由 Akihiro Suda（也是 containerd 和 nerdctl 的核心维护者）于 2021 年创建。它的灵感来自 Windows 的 WSL2，但面向 macOS 和 Linux 主机——在本地运行轻量级 Linux 虚拟机。在 Docker Desktop 更改许可协议（2022 年对大企业收费）后，Lima 迅速成为免费替代方案的核心组件。Lima 默认使用 QEMU 虚拟化（也支持 VZ，macOS 13+），内置 containerd 和 nerdctl，支持自动端口转发、文件共享（virtio-9p/virtfs）和跨平台网络。Lima 的设计哲学是"可编写脚本的虚拟机"——通过 YAML 配置文件声明式定义 VM 环境，支持在 VM 启动时执行 provisioning 脚本。它也是 Rancher Desktop、Finch（AWS）和 Colima 等流行工具的基础引擎。

**使用方法与案例**

**安装：**
```bash
# macOS
brew install lima

# Linux
curl -fsSL https://github.com/lima-vm/lima/releases/latest/download/lima-$(uname -s)-$(uname -m).tar.gz | tar xz -C /usr/local

# Windows（需要 WSL2）
winget install lima-vm.lima
```

**核心命令：**
```bash
limactl start default                  # 启动默认 VM
limactl list                           # 列出所有 VM
limactl shell default                  # 进入 VM Shell
lima nerdctl run -d -p 8080:80 nginx   # 在 VM 中运行容器
limactl stop default                   # 停止 VM
```

**案例一：创建自定义 Lima VM**
```yaml
# custom.yaml
images:
```

### 77. containerd

**前世今生**

containerd 最初由 Docker 公司于 2015 年开发，作为 Docker 引擎内部的容器运行时层，2016 年 12 月被拆分为独立项目，2017 年 3 月捐赠给 CNCF，2019 年 2 月成为 CNCF 毕业项目。containerd 的名字源于"容器守护进程"（container daemon），它负责容器生命周期的核心操作——镜像拉取、存储、容器创建、启动、停止和进程监控。从 2017 年底开始，Kubernetes 通过 CRI（容器运行时接口）直接对接 containerd，不再需要 Docker shim 作为中间层。2020 年底，Kubernetes 正式宣布弃用 Dockershim，containerd 成为 K8s 集群最主流的容器运行时。它如今是几乎所有云原生容器平台的底层默认选择——从 AKS 到 EKS 到 GKE，支撑着全球数百万个生产集群。

**使用方法与案例**

**安装：**
```bash
# Linux (Ubuntu)
sudo apt install containerd

# 或从 GitHub Release 手动安装
wget https://github.com/containerd/containerd/releases/download/v1.7.0/containerd-1.7.0-linux-amd64.tar.gz
sudo tar Cxzvf /usr/local containerd-1.7.0-linux-amd64.tar.gz

# 启动服务
sudo systemctl enable containerd --now
```

**核心命令（通过 ctr 客户端）：**
```bash
ctr image pull docker.io/library/nginx:alpine    # 拉取镜像
ctr run -d docker.io/library/nginx:alpine myapp  # 运行容器
ctr containers ls                                  # 列出容器
ctr tasks ls                                       # 列出运行中的任务
```

**案例一：containerd + nerdctl 完整容器工作流**
```bash
# 安装 nerdctl（Docker 兼容的 containerd 客户端）
wget https://github.com/containerd/nerdctl/releases/download/v1.7.0/nerdctl-1.7.0-linux-amd64.tar.gz
sudo tar Cxzvf /usr/local/bin nerdctl-1.7.0-linux-amd64.tar.gz

# 镜像管理
nerdctl pull nginx:alpine
nerdctl images

# 容器运行
nerdctl run -d --name web -p 8080:80 nginx:alpine
nerdctl ps
nerdctl logs -f web

# Docker Compose 兼容
nerdctl compose up -d

# 构建镜像（支持 Dockerfile）
nerdctl build -t myapp:v1 .
```

**案例二：配置 containerd 使用镜像代理**
```toml
# /etc/containerd/config.toml
version = 2

[plugins."io.containerd.grpc.v1.cri".registry.mirrors."docker.io"]
  endpoint = ["https://mirror.gcr.io", "https://registry-1.docker.io"]

[plugins."io.containerd.grpc.v1.cri".registry.configs."my-registry.com"]
  [plugins."io.containerd.grpc.v1.cri".registry.configs."my-registry.com".tls]
    insecure_skip_verify = false
  [plugins."io.containerd.grpc.v1.cri".registry.configs."my-registry.com".auth]
    username = "user"
    password = "pass"
```

**案例三：Namespace 隔离多租户环境**
```bash
# containerd 支持命名空间隔离镜像和容器
ctr namespace create dev
ctr namespace create prod

# 在不同命名空间中拉取镜像
ctr -n dev image pull docker.io/library/nginx:alpine
ctr -n prod image pull docker.io/library/nginx:1.25

# 命名空间完全隔离
ctr -n dev images ls     # 只显示 dev 命名空间的镜像
ctr -n prod images ls    # 只显示 prod 命名空间的镜像

# 查看并清理
ctr namespaces ls
ctr -n dev containers ls
ctr -n dev containers rm web-app
```

**进阶技巧：** `nerdctl` 是 containerd 的最佳日常客户端（Docker 兼容）。containerd 的 snapshotter 插件可切换存储驱动（overlayfs、btrfs、devmapper 等）。使用 `ctr image export` 和 `import` 导出/导入镜像归档。containerd 的 CRI 插件是 Kubernetes 集成的关键组件——确保 `disabled_plugins` 中不包含 `cri`。

### 78. Buildah

**前世今生**

Buildah（发音"build-ah"）由 Red Hat 的 Daniel Walsh 团队于 2017 年创建，是容器生态"去守护进程化"运动的重要组成。它的名字来源于创始人 Walsh 的波士顿口音——"Builder"的戏谑发音。Buildah 专注于 OCI 镜像的构建，与 Podman 共享底层库但职责不同：Podman 运行容器，Buildah 构建镜像。它的核心创新在于打破传统 `docker build` 的限制——Buildah 无需 Dockerfile 也能构建镜像（通过交互式命令直接修改容器文件系统），支持脚本化构建流程，且完全无需守护进程。Buildah 可直接输出 OCI 格式镜像和 Docker 兼容镜像，甚至可以在 Kubernetes 无特权 Pod 中安全运行构建任务。它和 Podman、Skopeo 一起构成了 Red Hat 的"容器三剑客"。

**使用方法与案例**

**安装：**
```bash
# macOS（通过 Podman 附带）
brew install podman
# Buildah 作为 podman-machine 的一部分

# Linux (RHEL/CentOS/Fedora)
sudo dnf install buildah -y

# Linux (Ubuntu/Debian)
sudo apt install buildah -y
```

**核心命令：**
```bash
buildah from alpine            # 从基础镜像创建工作容器
buildah run container -- cmd   # 在容器内运行命令
buildah commit container img   # 提交为镜像
buildah build -t myapp .       # 使用 Dockerfile 构建
buildah push img registry.com  # 推送镜像
```

**案例一：无 Dockerfile 的脚本化镜像构建**
```bash
#!/bin/bash
# 纯命令行构建自定义 Go 应用镜像

# 1. 创建工作容器
container=$(buildah from golang:1.22-alpine)
mountpoint=$(buildah mount $container)

# 2. 编译 Go 应用
buildah run $container -- apk add --no-cache git
buildah run $container -- sh -c 'cat > /app/main.go <<EOF
package main
import "fmt"
func main() { fmt.Println("Built with Buildah!") }
EOF'
buildah run $container -- go build -o /app/server /app/main.go

# 3. 构建最小最终镜像
final=$(buildah from scratch)
buildah copy $final /app/server /server
buildah config --entrypoint '["/server"]' $final
buildah config --port 8080 $final

# 4. 提交并清理
buildah commit $final myapp:buildah-built
buildah rm $container $final
buildah images | grep myapp
```

**案例二：Buildah + Podman 的 CI/CD 流水线**
```bash
# 使用 Dockerfile 构建
buildah bud -t myapi:v1 \
  --build-arg VERSION=1.0 \
  --label "built-by=buildah" \
  -f Dockerfile .

# 推送到本地 Podman 仓库（无需 Docker daemon）
buildah push myapi:v1 docker-daemon:myapi:v1

# 或直接推送到远程仓库
buildah push myapi:v1 docker://registry.example.com/myapi:v1

# 多架构构建（通过 manifest）
buildah manifest create myapp-multi
buildah bud --arch amd64 -t myapi:amd64 .
buildah bud --arch arm64 -t myapi:arm64 .
buildah manifest add myapp-multi myapi:amd64
buildah manifest add myapp-multi myapi:arm64
buildah manifest push --all myapp-multi docker://registry.example.com/myapi:latest
```

**案例三：在 Kubernetes 中安全构建（无特权模式）**
```yaml
# kaniko-build.yaml — 使用 Buildah 的 K8s 安全替代方案
apiVersion: v1
kind: Pod
metadata:
  name: buildah-build
spec:
  containers:
  - name: buildah
    image: quay.io/buildah/stable:latest
    command: ["/bin/bash", "-c"]
    args:
    - |
      buildah bud -t myapp:$BUILD_ID \
        --storage-driver=vfs \
        -f /workspace/Dockerfile \
        /workspace/
      buildah push myapp:$BUILD_ID docker://registry.example.com/myapp:$BUILD_ID
    volumeMounts:
    - name: workspace
      mountPath: /workspace
```

**进阶技巧：** `buildah from scratch` 创建空镜像，适合构建极小的静态二进制镜像。`buildah run` 不修改镜像层，`buildah config` 不创建新层。`buildah copy` 和 `buildah add` 是 Dockerfile 指令的等效命令。`buildah mount` 可将容器文件系统挂载到主机直接操作。使用 `--squash` 将多层压缩为一层减小镜像体积。

### 79. Skopeo

**前世今生**

Skopeo（希腊语意为"观察/查看"）由 Red Hat 的 Antonio Murdaca 于 2016 年创建，最初是 Project Atomic 的一部分。它专注于容器镜像的"非运行式"操作——检查、复制、签名和删除镜像，全程无需拉取完整镜像或启动容器守护进程。Skopeo 的名字暗示了它的核心功能：在不运行容器的情况下"审视"镜像信息。传统上，要查看远程镜像的元数据必须先 `docker pull` 下载整个镜像，而 Skopeo 可以直接查询远程仓库获取镜像的 manifests、layers、config 等信息。2020 年随着 OCI 标准的普及，Skopeo 成为容器镜像管理的重要瑞士军刀——特别是在镜像跨仓库同步、镜像签名验证和安全审计等场景中。它至今仍是容器生态中"小而美"类工具的代表作。

**使用方法与案例**

**安装：**
```bash
# macOS
brew install skopeo

# Linux (RHEL/CentOS/Fedora)
sudo dnf install skopeo -y

# Linux (Ubuntu/Debian)
sudo apt install skopeo -y
```

**核心命令：**
```bash
skopeo inspect docker://nginx:alpine       # 查看远程镜像信息
skopeo copy docker://src docker://dest     # 跨仓库复制镜像
skopeo list-tags docker://nginx            # 列出所有标签
skopeo delete docker://registry/myimg:old  # 删除镜像
```

**案例一：远程镜像检查（无需下载）**
```bash
# 查看远程镜像的详细信息
skopeo inspect docker://nginx:alpine

# 输出示例:
# {
#   "Name": "docker.io/library/nginx",
#   "Digest": "sha256:abc123...",
#   "Architecture": "amd64",
#   "Os": "linux",
#   "Layers": ["sha256:def456...", ...],
#   "Env": ["PATH=/usr/local/sbin/...", ...]
# }

# 只看特定字段
skopeo inspect docker://nginx:alpine | jq '{name: .Name, arch: .Architecture, layers: .Layers | length}'
# {"name": "docker.io/library/nginx", "arch": "amd64", "layers": 8}
```

**案例二：跨仓库镜像同步（一次命令完成迁移）**
```bash
# Docker Hub → 私有 Harbor 仓库
skopeo copy \
  --src-creds="dockeruser:dockerpass" \
  --dest-creds="harboruser:harborpass" \
  docker://docker.io/nginx:1.25 \
  docker://harbor.example.com/library/nginx:1.25

# 批量同步多个镜像到不同架构
for img in nginx redis postgres; do
  skopeo copy \
    --multi-arch all \
    docker://docker.io/library/$img:alpine \
    docker://mirror.local/base/$img:alpine
done

# 同步到本地目录（OCI 格式）
skopeo copy docker://nginx:alpine oci:/tmp/nginx-oci
ls /tmp/nginx-oci/
# blobs/  oci-layout  index.json
```

**案例三：镜像差异分析与安全审计**
```bash
# 查看两个镜像版本之间的层差异
skopeo inspect docker://nginx:1.24 > /tmp/v1.json
skopeo inspect docker://nginx:1.25 > /tmp/v2.json

diff <(jq '.Layers[]' /tmp/v1.json | sort) \
     <(jq '.Layers[]' /tmp/v2.json | sort)

# 删除远程仓库中的旧镜像
skopeo delete \
  --creds="admin:pass" \
  docker://harbor.example.com/myapp:old-build-20230101

# 同步时排除特定层（节省带宽）
skopeo copy \
  --dest-compress-format=gzip \
  docker://source:latest \
  docker://dest:latest
```

**进阶技巧：** `skopeo sync` 命令可基于 YAML 配置文件批量同步镜像。`skopeo login` 统一管理多仓库认证。`--src-tls-verify=false` 跳过源仓库 TLS 验证（仅测试用）。`docker-archive:` 格式可将镜像保存为 `docker save` 兼容的 tar 文件。结合 `cron` 可实现定期镜像备份。企业用户常用 Skopeo 搭建 Docker Hub 镜像缓存代理。

### 80. Earthly

**前世今生**

Earthly 由 Vlad A. Ionescu 于 2020 年创建，2022 年发布 1.0 版本。Ionescu 此前在 CircleCI 和 Docker 公司工作，深刻理解 CI/CD 流水线中"Dockerfile 只能构建镜像"和"CI 配置文件不可本地运行"的两大痛点。Earthly 的核心理念是"一次编写，随处运行"——使用类似 Dockerfile + Makefile 混合语法的 Earthfile，在开发环境和 CI 环境中产生完全相同的构建结果。它通过容器化每个构建步骤，确保构建过程在任何机器上可复现，同时支持智能缓存（基于依赖图而非文件时间戳）和并行执行。Earthly 被认为代表了"下一代构建系统"的方向——将 Docker、Makefile 和 CI 配置文件的能力统一到一个声明式构建系统中。它已获得包括 Google 在内的多家企业采用。

**使用方法与案例**

**安装：**
```bash
# macOS
brew install earthly/earthly/earthly

# Linux
sudo /bin/sh -c 'wget https://github.com/earthly/earthly/releases/latest/download/earthly-linux-amd64 -O /usr/local/bin/earthly && chmod +x /usr/local/bin/earthly'

# Windows (需要 WSL2)
# 在 WSL 中按 Linux 方式安装

# 启动 Earthly 守护进程（后台）
earthly bootstrap
```

**核心命令：**
```bash
earthly +build                 # 运行 build target
earthly +test                  # 运行 test target
earthly +docker                # 构建 Docker 镜像
earthly --push +docker         # 构建并推送
earthly +all                   # 运行所有 target
```

**案例一：全栈应用的单文件构建**
```earthly
# Earthfile
VERSION 0.8
FROM golang:1.22-alpine
WORKDIR /app

# 依赖层（缓存友好）
deps:
    COPY go.mod go.sum ./
    RUN go mod download

# 编译后端
build:
    FROM +deps
    COPY . .
    RUN go build -o server ./cmd/api
    SAVE ARTIFACT server AS LOCAL build/server

# 前端构建
frontend:
    FROM node:20-alpine
    WORKDIR /ui
    COPY ui/package.json ui/yarn.lock ./
    RUN yarn install
    COPY ui/ ./
    RUN yarn build
    SAVE ARTIFACT dist AS LOCAL build/static

# Docker 镜像
docker:
    FROM alpine:3.19
    COPY +build/server /server
    COPY +frontend/dist /static
    EXPOSE 8080
    ENTRYPOINT ["/server"]
    SAVE IMAGE myapp:latest

# 测试
test:
    FROM +deps
    COPY . .
    RUN go test ./... -v -race

# 一键执行所有
all:
    BUILD +test
    BUILD +docker
```
```bash
earthly +all                     # 本地运行完整流水线
earthly --push +docker           # 构建并推送镜像
earthly -P +test                 # 仅运行测试（PR 模式）
```

**案例二：Monorepo 多服务构建**
```earthly
# Earthfile
VERSION 0.8

# 全局基础设置
base:
    FROM alpine:3.19
    RUN apk add --no-cache ca-certificates

# 服务A
service-a:
    FROM golang:1.22-alpine
    COPY services/a/ ./
    RUN go build -o /out/svc-a .
    SAVE ARTIFACT /out/svc-a

# 服务B
service-b:
    FROM node:20-alpine
    COPY services/b/ ./
    RUN npm ci && npm run build
    SAVE ARTIFACT dist AS LOCAL /out/svc-b

# 各自的 Docker 镜像
image-a:
    FROM +base
    COPY +service-a/svc-a /app
    ENTRYPOINT ["/app/svc-a"]
    SAVE IMAGE registry.example.com/svc-a:latest

image-b:
    FROM +base
    COPY +service-b/dist /app
    CMD ["node", "/app/index.js"]
    SAVE IMAGE registry.example.com/svc-b:latest
```
```bash
# 仅构建变更的服务（自动缓存未变更部分）
earthly --push +image-a
earthly --push +image-b

# 并行构建所有镜像
earthly -P --push +image-a +image-b
```

**案例三：Earthly 作为 CI 配置文件**
```yaml
# .github/workflows/ci.yml
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
    - uses: actions/checkout@v4
    - name: Earthly Build
      uses: earthly/actions-setup@v1
      with:
        version: "latest"
    - run: earthly --ci --push +all
      env:
        EARTHLY_TOKEN: ${{ secrets.EARTHLY_TOKEN }}
```
```bash
# 同一命令在本地开发环境也能完美运行
earthly --push +all
```

**进阶技巧：** `SAVE ARTIFACT` 将构建产物导出到本地或传递给下游 target。`LOCALLY` 关键词在主机上执行命令（而非容器内）。`ARG` 支持构建参数传递（类似 Docker Build Args）。`GIT CLONE` 可在构建中引用外部仓库。Earthly 的缓存基于内容哈希，修改 README 不会触发代码重新编译。使用 `earthly account register` 注册云端账户获取共享缓存。
