# 第16组：可观测性与监控

## 151. Prometheus

**前世今生：** Prometheus 由 SoundCloud 的 Matt T. Proud 和 Julius Volz 于 2012 年创建，灵感来自 Google 内部监控系统 Borgmon。当时 SoundCloud 用的监控方案（Graphite + Nagios）无法适应微服务架构，他们需要一种 pull 式、多维标签、时序数据原生的监控系统。Prometheus 的核心创新是"拉取模型"——Prometheus server 主动去每个服务拉取 metrics 端点（`/metrics`），而不是服务 push 过来。2016 年捐献给 CNCF，成为仅次于 K8s 的第二个毕业项目。PromQL（Prometheus 查询语言）和 Alertmanager（告警系统）共同构成了云原生监控的事实标准。

**使用方法与案例：**

安装：
```bash
# Docker 方式
docker run -d -p 9090:9090 -v prometheus.yml:/etc/prometheus/prometheus.yml prom/prometheus
```

**案例1：监控 Python 应用**
```python
from prometheus_client import start_http_server, Gauge, Counter, Histogram

# 定义指标
oee_gauge = Gauge('mes_oee_current', 'Current OEE value', ['line'])
production_counter = Counter('mes_production_total', 'Total production units', ['line'])
request_duration = Histogram('mes_api_duration_seconds', 'API request duration', ['endpoint'])

start_http_server(8000)  # 暴露 /metrics 端点

# 业务代码中更新指标
oee_gauge.labels(line='A').set(88.5)
production_counter.labels(line='A').inc(450)
```
```yaml
# prometheus.yml
scrape_configs:
  - job_name: 'mes-api'
    static_configs:
      - targets: ['mes-api:8000']
```

**案例2：PromQL 查询 OEE 趋势**
```promql
# 过去 1 小时 OEE 平均值
avg by (line) (mes_oee_current)

# OEE 低于 85% 超过 5 分钟
mes_oee_current < 85

# QPS（每秒请求数）
rate(mes_api_requests_total[5m])

# P99 延迟
histogram_quantile(0.99, rate(mes_api_duration_seconds_bucket[5m]))
```

**案例3：告警规则**
```yaml
# alert_rules.yml
groups:
  - name: production
    rules:
      - alert: LowOEE
        expr: avg by (line) (mes_oee_current) < 85
        for: 5m
        labels:
          severity: warning
        annotations:
          summary: "OEE 低于 85%"
          description: "产线 {{ $labels.line }} OEE: {{ $value }}%"
```
Alertmanager 收到告警后：分组去重、静默抑制（如维护窗口）、路由到飞书/钉钉/邮件。

**进阶技巧：**
- `rate()` 计算变化率（Counter 类型）
- `increase()` 计算区间增量
- Recording Rules 预计算常用查询，加速仪表盘
- Thanos/Mimir 实现长期存储和全局视图（多集群聚合）

## 152. Grafana

**前世今生：** Grafana 由瑞典开发者 Torkel Ödegaard 于 2014 年创建，最初是 Kibana（Elasticsearch 可视化工具）的一个 fork。Ödegaard 发现 Kibana 与 Elasticsearch 绑定太紧，他想做一个"数据源无关"的可视化平台。Grafana 用 Go + TypeScript 编写，通过插件架构支持任何数据源（Prometheus、InfluxDB、PostgreSQL、MySQL、Elasticsearch 等 100+ 个）。它的仪表盘生态系统极强——社区贡献了数万个预制 Dashboard。2021 年 Grafana Labs 估值 30 亿美元。Grafana 已成为可观测性 UI 的标准。

**使用方法与案例：**

安装：
```bash
brew install grafana          # macOS
docker run -d -p 3000:3000 grafana/grafana
# 访问 http://localhost:3000 (admin/admin)
```

**案例1：MES 产线监控大屏**
1. Data Sources → 添加 Prometheus URL
2. Dashboards → Import → 输入开源 Dashboard ID 或从头创建
3. Panel 配置：
```promql
# 实时 OEE（数字面板）
avg(mes_oee_current)

# 产量趋势（时间序列面板）
sum by (line) (rate(mes_production_total[5m]))

# 产线对比（柱状图）
avg by (line) (mes_oee_current)

# 告警状态（表格面板）
ALERTS{alertstate="firing"}
```

**案例2：多数据源混合面板**
一个 Dashboard 可以同时显示：
- Prometheus → 实时机器状态
- PostgreSQL → 历史产量排行
- Loki → 错误日志流（关联时间轴）
在 Grafana 内点击图表上的异常点，自动跳转到对应时间的日志（Loki logQL），这就是"可观测性三位一体"（Metrics + Logs + Traces）。

**案例3：飞书告警通知**
Grafana Alerting → Contact points → Webhook → 飞书机器人 URL：
```json
{
  "msg_type": "interactive",
  "card": {
    "header": {"title": {"content": "{{ .CommonLabels.alertname }}"}},
    "elements": [{"content": "{{ .CommonAnnotations.description }}"}]
  }
}
```

**进阶技巧：**
- Variables 模板变量：切换产线/时间段自动刷新面板
- Grafana Playlist 轮播模式用于车间大屏
- `$__interval` 动态时间间隔适配不同时间范围

## 153. OpenTelemetry

**前世今生：** OpenTelemetry（简称 OTel）由 OpenTracing 和 OpenCensus 两个项目于 2019 年合并而成，2021 年发布 1.0。背后的推动者包括 Google、微软、Lightstep、Splunk 等。OTel 的核心使命是"一套 API、SDK 和采集器，统一所有遥测数据"——Traces（追踪）、Metrics（指标）、Logs（日志），避免厂商锁定。OTel Collector 是一个独立进程，接收/处理/导出遥测数据到任何后端（Jaeger、Prometheus、Datadog）。CNCF 仅次于 K8s 的第二活跃项目。OTel 的目标是让可观测性像 TCP/IP 一样成为基础设施。

**使用方法与案例：**

**案例：Python 应用集成**
```python
from opentelemetry import trace
from opentelemetry.sdk.trace import TracerProvider
from opentelemetry.exporter.otlp.proto.grpc.trace_exporter import OTLPSpanExporter
from opentelemetry.instrumentation.flask import FlaskInstrumentor

# 设置 tracer
trace.set_tracer_provider(TracerProvider())
trace.get_tracer_provider().add_span_processor(
    BatchSpanProcessor(OTLPSpanExporter(endpoint="http://otel-collector:4317"))
)

# 自动检测 Flask
FlaskInstrumentor().instrument_app(app)

# 手动追踪
tracer = trace.get_tracer(__name__)
with tracer.start_as_current_span("calculate_oee") as span:
    span.set_attribute("line", "A")
    span.set_attribute("oee", 88.5)
    result = compute_oee()
    span.set_attribute("result", result)
```
所有追踪数据自动发送到 OTel Collector → Jaeger/Prometheus/Datadog。

**进阶技巧：**
- Auto-instrumentation：无需改代码，启动时注入 agent 自动追踪（Java/Python/Node.js）
- OTel Collector Receiver/Processor/Exporter 管道模式，灵活路由
- 支持 Baggage：在分布式系统中传递业务上下文

## 154. Jaeger

**前世今生：** Jaeger 由 Uber 于 2015 年创建，名字来自德语"猎人"（追踪分布式请求的猎手）。Uber 的微服务架构有数千个服务，一次 API 请求经过数十个服务，需要分布式追踪还原完整链路。Jaeger 基于 OpenTracing（后来融入 OpenTelemetry）API，用 Go 编写，存储后端支持 Cassandra/Elasticsearch。2017 年捐献给 CNCF，2019 年毕业。Jaeger 的 UI 提供 Gantt 图展示每个 Span 的耗时瀑布——一眼看出是哪个服务拖慢了整体响应。

**案例：追踪 API 请求链路**
```
HTTP GET /api/oee → [mes-gateway: 2ms] → [auth-service: 5ms] → [oee-calculator: 120ms] → [db-query]
                                     ↓
                                   120ms ← 这里最慢！
```

```bash
docker run -d --name jaeger \
  -p 16686:16686 -p 4317:4317 \
  jaegertracing/all-in-one:latest
```

## 155. Loki ### 156. Sentry

**Loki** 由 Grafana Labs 于 2019 年创建，是"Prometheus 风格的日志系统"。与 Elasticsearch 不同，Loki 不索引全文而索引标签（labels），搜索时才扫描内容（grep-like）。这使得 Loki 的成本比 ELK 低 10× 以上。在 Grafana 中 Loki 和 Prometheus 无缝关联——点击指标异常点打开对应日志。

**Sentry** 由 David Cramer 于 2008 年创建（最初是 Django 的错误跟踪插件）。Sentry 捕获异常时不仅记录堆栈，还记录请求上下文、本地变量、用户信息、面包屑（breadcrumb）——让开发者不依赖用户报告就能复现 bug。2016 年开源化（之前是 SaaS），提供自托管版。

```python
import sentry_sdk
sentry_sdk.init(dsn="https://xxx@sentry.io/xxx",
    traces_sample_rate=1.0)
# 未捕获的异常自动上报，或手动
sentry_sdk.capture_message("OEE calculation anomaly: value=150%")
```

## 157. Vector ### 158. Fluentd

**Vector** 由 Timber.io 于 2019 年创建，用 Rust 重写了日志管道。相比 Fluentd（Ruby），Vector 快 10×、内存省 90%。它不仅能处理日志，还支持 Metrics 和 Traces 转换。单核 CPU 一天可处理 10TB 数据。

**Fluentd** 由 Sadayuki Furuhashi（Treasure Data）于 2011 年创建，是 CNCF 最早毕业的项目之一。它的核心理念是"统一日志层"——500+ 插件覆盖所有输入/输出源。但 Ruby 实现的性能是瓶颈，新项目推荐 Vector。

```yaml
# Vector 配置: Nginx 日志 → ClickHouse
sources:
  nginx:
    type: file
    include: [/var/log/nginx/access.log]
transforms:
  parse:
    inputs: [nginx]
    type: remap
    source: |
      . = parse_json!(.message)
      .timestamp = now()
sinks:
  clickhouse:
    inputs: [parse]
    type: clickhouse
    database: logs
    table: nginx_access
```

## 159. SigNoz ### 160. VictoriaMetrics

**SigNoz** 由 Prashant Shahi 等人于 2021 年创建，定位是"开源 Datadog 替代"。一体化平台：Metrics + Traces + Logs + 告警。前端用 React，后端 ClickHouse 存数据，OpenTelemetry 原生集成。

**VictoriaMetrics** 由 Aliaksandr Valialkin 于 2018 年创建，是 Prometheus 兼容的高性能时序数据库。比 Prometheus 省 7× 内存，写入快 20×。支持集群模式横向扩展和长期存储。

```bash
# 替换 Prometheus 只需改 remote_write 地址
./victoria-metrics-prod -storageDataPath=/data -retentionPeriod=12
```
Prometheus 的 remote_write → VictoriaMetrics，长期历史查询用 VictoriaMetrics 的 PromQL 接口。
