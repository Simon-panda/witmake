# 第6组: 构建与包管理

> 从语言级构建系统到系统级包管理器，覆盖现代开发的依赖管理和构建工作流。

### 51. Cargo

**前世今生**

Cargo 由 Rust 核心团队于 2014 年随 Rust 1.0 发布周期一同开发，核心贡献者包括 Yehuda Katz（Bundler 和 Ruby on Rails 核心成员）、Carl Lerche 和 Alex Crichton。Cargo 的灵感主要来自 Ruby 的 Bundler 和 Node.js 的 npm，但设计目标更为宏大：它不仅是一个包管理器，更是一个完整的构建系统和项目管理工具。Cargo 在 Rust 1.0（2015 年 5 月）之前就已集成到 Rust 发行版中，与 Rust 编译器一起分发。这种"自带构建工具"的策略后来被 Go Modules、Deno 等生态系统效仿。Cargo 的独特之处在于：声明式配置（`Cargo.toml`）、锁定文件（`Cargo.lock`）确保可重现构建、内置文档生成和测试运行器、与 crates.io（Rust 包注册中心）无缝集成。它已成为现代语言自带构建工具的黄金标准。

**使用方法与案例**

**安装方式：**

Cargo 随 Rust 一起安装，无需单独安装：

```bash
# macOS / Linux
curl --proto '=https' --tlsv1.2 -sSf https://sh.rustup.rs | sh

# Windows
# 下载 rustup-init.exe: https://rustup.rs/

# 验证安装
cargo --version
rustc --version
```

**基础用法：**

```bash
# 创建新项目
cargo new my-project        # 创建库项目（--lib）
cargo new my-app --bin      # 创建二进制项目

# 构建项目
cargo build                 # 开发构建（未优化，带调试信息）
cargo build --release       # 发布构建（优化，去除调试信息）

# 运行项目
cargo run                   # 构建并运行
cargo run -- --flag value   # 传递参数给程序

# 测试
cargo test                  # 运行所有测试
cargo test test_name        # 运行特定测试
cargo test -- --nocapture   # 显示测试中的 println 输出

# 检查代码（不生成二进制，比 build 快）
cargo check

# 自动格式化
cargo fmt

# Lint 检查
cargo clippy
```

**实战案例一：管理依赖和 Cargo.toml**

```toml
# Cargo.toml 示例
[package]
name = "web-server"
version = "0.1.0"
edition = "2021"
description = "A simple async web server"

[dependencies]
# 从 crates.io 安装
tokio = { version = "1", features = ["full"] }
serde = { version = "1.0", features = ["derive"] }
serde_json = "1.0"

# Git 依赖
# mylib = { git = "https://github.com/user/mylib", branch = "main" }

# 本地路径依赖
# mylib = { path = "../mylib" }

# 条件依赖
[target.'cfg(unix)'.dependencies]
openssl = "0.10"

[dev-dependencies]
# 仅在测试/基准测试中使用的依赖
criterion = "0.5"
pretty_assertions = "1"

[build-dependencies]
# 构建脚本使用的依赖
cc = "1.0"

[profile.release]
opt-level = 3       # 最高优化级别
lto = true          # 链接时优化
strip = true        # 去除符号表
```

**实战案例二：自定义构建脚本和特性标记**

```toml
# Cargo.toml 中的特性定义
[features]
default = ["json-support"]
json-support = ["serde", "serde_json"]
yaml-support = ["serde_yaml"]
full = ["json-support", "yaml-support"]

[dependencies]
serde = { version = "1.0", optional = true }
serde_json = { version = "1.0", optional = true }
serde_yaml = { version = "0.9", optional = true }
```

**进阶技巧：**

- `cargo add <crate>` 添加依赖（无需手动编辑 Cargo.toml）
- `cargo update` 更新 Cargo.lock 中的依赖版本
- `cargo tree` 查看依赖树
- `cargo bench` 运行基准测试（需要 nightly）
- `cargo doc --open` 生成并打开文档
- `cargo vendor` 将所有依赖下载到本地目录（离线构建）

**避坑指南：**

- `Cargo.lock` 对库项目会被忽略（库应该让用户决定依赖版本），但二进制项目应提交
- `cargo update` 会更新所有依赖，用 `cargo update -p <crate>` 只更新特定包
- 编译慢是 Cargo 常见抱怨，用 `sccache` 或 `mold` 链接器可显著加速
- 在中国大陆使用 crates.io 很慢，可配置镜像：在 `~/.cargo/config.toml` 中设置 `[source.crates-io] replace-with = 'ustc'`

### 52. npm (Node Package Manager)

**前世今生**

npm 由 Isaac Z. Schlueter 于 2010 年 1 月创建，最初是作为 Node.js 的包管理器。Isaac 当时在 Joyent（Node.js 的商业支持公司）工作，他看到了服务端 JavaScript 生态需要一个类似 RubyGems/CPAN 的包管理系统。npm 的创新包括：声明式依赖描述（`package.json`）、语义化版本（SemVer）、嵌套式依赖树（node_modules 中每个包可拥有自己的依赖副本）。npm 于 2014 年成立了 npm, Inc. 公司，2015 年推出了私有包托管服务。2020 年，npm, Inc. 被 GitHub（微软）收购。尽管 Yarn、pnpm 等竞争工具后来实现了更优的性能和磁盘效率，npm 仍是 Node.js 官方包管理器，随 Node.js 一起分发。截至 2025 年，npm registry 上有超过 250 万个包，是世界上最大的包注册中心。

**使用方法与案例**

**安装方式：**

npm 随 Node.js 一起安装：

```bash
# macOS
brew install node

# Linux
curl -fsSL https://deb.nodesource.com/setup_20.x | sudo -E bash -
sudo apt-get install nodejs

# 使用 nvm（推荐，方便版本管理）
curl -o- https://raw.githubusercontent.com/nvm-sh/nvm/v0.39.7/install.sh | bash
nvm install 20
nvm use 20

# Windows
# 从 https://nodejs.org 下载安装程序
# 或
scoop install nodejs
```

**基础用法：**

```bash
# 初始化项目
npm init                 # 交互式创建 package.json
npm init -y              # 使用默认值快速创建

# 安装依赖
npm install              # 安装 package.json 中的所有依赖
npm install <package>    # 安装并添加到 dependencies
npm install -D <package> # 安装为 devDependencies
npm install -g <package> # 全局安装

# 卸载
npm uninstall <package>

# 更新
npm update               # 更新所有依赖
npm update <package>     # 更新特定包

# 运行脚本
npm run <script>         # 运行 package.json 中定义的脚本
npm start                # npm run start 的简写
npm test                 # npm run test 的简写

# 查看信息
npm list                 # 列出已安装的包
npm outdated             # 查看过时的依赖
npm audit                # 安全审计
```

**实战案例一：package.json 脚本配置**

```json
{
  "name": "my-app",
  "version": "1.0.0",
  "scripts": {
    "dev": "next dev",
    "build": "next build",
    "start": "next start",
    "lint": "eslint . --ext .ts,.tsx",
    "lint:fix": "eslint . --ext .ts,.tsx --fix",
    "format": "prettier --write '**/*.{ts,tsx,json,md}'",
    "test": "jest --coverage",
    "test:watch": "jest --watch",
    "prepare": "husky install",
    "prebuild": "npm run lint && npm run test",
    "postbuild": "echo 'Build complete!'"
  },
  "dependencies": {
    "react": "^18.2.0",
    "next": "14.0.0"
  },
  "devDependencies": {
    "typescript": "^5.3.0",
    "@types/react": "^18.2.0",
    "eslint": "^8.0.0",
    "prettier": "^3.0.0"
  }
}
```

```bash
# 串行执行多个脚本
npm run lint && npm run test && npm run build

# 并行执行（需要 npm-run-all 或 concurrently）
npx npm-run-all --parallel dev:* 

# 传递参数
npm run test -- --watch --testPathPattern=user
# "--" 后面的参数会传递给实际执行的命令
```

**实战案例二：npm workspaces 管理 monorepo**

```json
// 根目录 package.json
{
  "name": "my-monorepo",
  "private": true,
  "workspaces": [
    "packages/*",
    "apps/*"
  ],
  "scripts": {
    "build": "npm run build --workspaces",
    "test": "npm run test --workspaces",
    "lint": "npm run lint --workspaces"
  }
}
```

```bash
# 在特定 workspace 中安装依赖
npm install express -w packages/api

# 在特定 workspace 中运行脚本
npm run build -w apps/web

# 在所有 workspace 中运行
npm test --workspaces
```

**进阶技巧：**

- `npx <package>` 无需安装即可执行包中的命令
- `npm ci` 严格按 lock 文件安装（CI/CD 环境必须使用）
- `npm link` 本地开发时链接本地包
- `npm version patch|minor|major` 更新版本号并创建 Git tag
- `.npmrc` 文件配置 registry、认证 token、安装行为
- `overrides` 字段强制指定传递依赖的版本

**避坑指南：**

- `^`（插入符）允许小版本和补丁更新，`~`（波浪号）只允许补丁更新；新项目建议严格锁版本
- `node_modules` 黑洞——用 `npm prune` 清理未在 package.json 中声明的包
- `npm audit fix` 可能引入破坏性变更，先在 CI 中测试
- npm 的扁平化安装可能导致幽灵依赖（可以 import 未在 package.json 声明的包）

### 53. pnpm

**前世今生**

pnpm（performant npm）由 Zoltan Kochan 于 2017 年创建，TypeScript/JavaScript 编写。Zoltan 是一位波兰开发者，他对 npm 和 Yarn 的磁盘空间浪费和安装速度不满，提出了一个创新的方案：全局内容寻址存储（Content-Addressable Store）+ 硬链接。pnpm 的核心思想是"全局只保存一份包的物理文件，项目中的 node_modules 通过硬链接指向全局存储"。这个设计带来了三个巨大优势：磁盘空间节省 50% 以上、安装速度显著提升（尤其是多项目场景）、杜绝了幽灵依赖问题（严格模式下未声明的依赖不可访问）。pnpm 还原生支持 workspace 协议（monorepo 管理）。尽管初期面临兼容性挑战（部分包依赖幽灵依赖行为），pnpm 现在已被 Prisma、Vue、Next.js 等主流项目采用，成为大型 monorepo 的首选包管理器。

**使用方法与案例**

**安装方式：**

```bash
# macOS / Linux
curl -fsSL https://get.pnpm.io/install.sh | sh -

# 或通过 npm（但不推荐用 npm 全局安装 pnpm）
npm install -g pnpm

# 通过 corepack（Node.js 16+ 内置）
corepack enable
corepack prepare pnpm@latest --activate

# Windows (Scoop/PowerShell)
scoop install pnpm
# 或
iwr https://get.pnpm.io/install.ps1 -useb | iex
```

**基础用法：**

```bash
# 初始化项目
pnpm init

# 安装依赖
pnpm install               # 安装所有依赖
pnpm add <package>         # 添加到 dependencies
pnpm add -D <package>      # 添加到 devDependencies
pnpm add -g <package>      # 全局安装

# 删除
pnpm remove <package>

# 更新
pnpm update
pnpm update <package>      # 更新特定包
pnpm update --latest       # 更新到最新版本

# 运行脚本
pnpm <script>              # 直接运行（不需要 run）
pnpm run <script>          # 标准方式

# 查看信息
pnpm list                  # 列出依赖
pnpm outdated              # 查看过时的包
pnpm audit                 # 安全审计
```

**实战案例一：pnpm workspace（monorepo）**

```yaml
# pnpm-workspace.yaml
packages:
  - 'apps/*'
  - 'packages/*'
  - '!**/test/**'
```

```json
// packages/shared/package.json
{
  "name": "@myorg/shared",
  "version": "1.0.0",
  "main": "./dist/index.js",
  "types": "./dist/index.d.ts",
  "scripts": {
    "build": "tsc",
    "dev": "tsc --watch"
  }
}

// apps/web/package.json
{
  "name": "@myorg/web",
  "version": "1.0.0",
  "dependencies": {
    "@myorg/shared": "workspace:*",
    "react": "^18.2.0"
  },
  "scripts": {
    "dev": "next dev",
    "build": "next build"
  }
}
```

```bash
# 在所有 workspace 中运行命令
pnpm -r run build

# 在特定 workspace 中运行
pnpm --filter @myorg/web run dev

# 安装依赖到特定 workspace
pnpm --filter @myorg/api add express

# 并行运行多个 workspace 的脚本
pnpm -r --parallel run dev
```

**实战案例二：利用 pnpm 的严格模式避免幽灵依赖**

```bash
# pnpm 的 node_modules 是非扁平的（严格模式）
# 这意味着你只能访问 package.json 中声明的包

# 示例：项目声明了 express，但未声明 body-parser
# 在 npm/Yarn 的扁平化 node_modules 中，body-parser 可能可被直接引入
# pnpm 中则不行：

# pnpm add express
# import bodyParser from 'body-parser'  ← 报错！未在 dependencies 中声明

# 如果需要使用，必须显式安装：
pnpm add body-parser

# 检查幽灵依赖（验证项目是否依赖了未声明的包）：
# 使用 dependency-cruiser 或 eslint-plugin-import 的规则
```

**进阶技巧：**

- `pnpm store path` 查看全局存储位置
- `pnpm store prune` 清理全局存储中未被任何项目引用的包
- `.npmrc` 中设置 `shamefully-hoist=true` 在遇到兼容性问题时退回到扁平模式
- `pnpm dlx` 等同于 `npx`，临时执行包
- `pnpm patch <package>` 创建包的本地补丁（适合快速修复上游 bug）
- `pnpm import` 从其他包管理器的 lock 文件生成 `pnpm-lock.yaml`

**避坑指南：**

- 部分旧包或构建工具依赖了幽灵依赖行为，在 pnpm 严格模式下会失败
- pnpm 的 node_modules 结构较特殊，某些工具的路径解析可能出错
- `public-hoist-pattern` 配置可以解决特定包的提升需求
- CI 中应使用 `pnpm install --frozen-lockfile`（类似 `npm ci`）

### 54. uv

**前世今生**

uv 由 Charlie Marsh（Astral 公司创始人，也是 Ruff 的创建者）于 2024 年 2 月发布，Rust 语言编写。uv 诞生于 Python 包管理领域长期"军阀割据"的背景下：pip 是标准但功能简陋、pip-tools 增加了锁文件、Poetry 引入了现代依赖解析但性能堪忧、PDM 和 Hatch 各有侧重。uv 的设计哲学是"用 Rust 重写 pip 和 pip-tools，追求极致速度"——它在许多场景下比 pip 快 10-100 倍，比 Poetry 快一个数量级。uv 基于 Rust 的生态系统（`pubgrub` 依赖解析器、`reqwest` HTTP 客户端）构建，支持 pip 兼容的接口、虚拟环境管理、锁文件、Python 版本管理等。Astral 公司由 Charlie Marsh 创立，获得了 Accel 等风投的投资。uv 的发布在 Python 社区引起了巨大震动，被广泛视为"Python 包管理的未来"。

**使用方法与案例**

**安装方式：**

```bash
# macOS / Linux
curl -LsSf https://astral.sh/uv/install.sh | sh

# 或通过 Homebrew
brew install uv

# 或通过 pip
pip install uv

# Windows (PowerShell)
powershell -c "irm https://astral.sh/uv/install.ps1 | iex"

# 或通过 Scoop
scoop install uv

# 验证安装
uv --version
```

**基础用法：**

```bash
# 创建虚拟环境
uv venv                    # 在当前目录创建 .venv
uv venv my-env             # 指定名称
uv venv --python 3.12      # 指定 Python 版本

# 激活虚拟环境
source .venv/bin/activate   # Linux/macOS
.venv\Scripts\activate      # Windows

# 安装包（pip 兼容接口）
uv pip install flask
uv pip install -r requirements.txt
uv pip install "django>=4.2,<5.0"

# 同步环境
uv pip sync requirements.txt  # 精确同步（移除不在 requirements 中的包）

# 编译锁文件（pip-tools 兼容接口）
uv pip compile requirements.in -o requirements.txt
uv pip compile pyproject.toml -o requirements.txt

# 查看已安装的包
uv pip list
uv pip tree                  # 依赖树
```

**实战案例一：从 Poetry 迁移到 uv**

```bash
# 原有 Poetry 项目结构：
# pyproject.toml + poetry.lock

# 1. 导出 Poetry 依赖到 requirements 格式
poetry export -f requirements.txt -o requirements.txt --without-hashes
poetry export -f requirements.txt -o requirements-dev.txt --with dev --without-hashes

# 2. 用 uv 创建环境并安装
uv venv
source .venv/bin/activate
uv pip install -r requirements.txt
uv pip install -r requirements-dev.txt

# 3. 编译锁文件
uv pip compile pyproject.toml -o requirements.txt

# 4. 检查性能差异
# 在大型项目上，uv install 通常比 poetry install 快 5-10 倍
```

**实战案例二：uv 管理多 Python 版本**

```bash
# uv 内置 Python 版本管理（实验性功能）

# 安装特定 Python 版本
uv python install 3.12
uv python install 3.11
uv python install pypy@3.10

# 列出已安装的 Python
uv python list

# 查找系统中可用的 Python
uv python find

# 为项目指定 Python 版本
uv venv --python 3.12

# 创建 .python-version 文件（类似 pyenv）
echo "3.12" > .python-version
uv venv  # 自动使用 .python-version 中指定的版本
```

**进阶技巧：**

- `uv pip install --reinstall <package>` 强制重装（即使版本相同）
- `uv pip install --no-deps <package>` 不安装依赖
- `uvx` 命令：类似 `pipx`，在临时环境中运行 Python 工具
- `uv cache dir` 查看缓存目录，`uv cache clean` 清理缓存
- 设置 `UV_LINK_MODE=copy` 在 Docker 构建中避免硬链接问题

**避坑指南：**

- uv 仍在快速发展中，某些边缘功能可能不稳定
- `uv pip compile` 默认使用 `--generate-hashes` 以外的模式，生产环境建议开启
- Python 版本管理功能（`uv python`）仍处于实验阶段
- 部分依赖 pyproject.toml 的构建后端可能不完全兼容

### 55. Poetry

**前世今生**

Poetry 由 Sébastien Eustace 于 2018 年创建，Python 语言编写。Sébastien 是法国开发者，他对 Python 生态中缺乏一个类似 npm/Cargo 的统一工具感到沮丧——开发者通常需要组合 pip + virtualenv + setuptools + twine + pip-tools 等多个工具才能完成依赖管理、打包和发布。Poetry 的核心理念是"Python 打包和依赖管理的应许之地"：它使用 `pyproject.toml`（PEP 518）作为唯一配置文件，内置依赖解析器（基于 SAT 求解算法）、虚拟环境管理和发布工具。Poetry 率先推广了 `pyproject.toml` 作为 Python 项目元数据的标准格式，这一做法后来被 PEP 621 正式化。尽管 uv 在性能上后来居上，Poetry 至今仍是 Python 生态中最成熟的现代包管理工具之一。

**使用方法与案例**

**安装方式：**

```bash
# macOS / Linux / WSL
curl -sSL https://install.python-poetry.org | python3 -

# 或通过 pipx（推荐，隔离安装）
pipx install poetry

# 或通过 Homebrew
brew install poetry

# 验证安装
poetry --version
```

**基础用法：**

```bash
# 创建新项目
poetry new my-project
cd my-project

# 在已有项目中初始化
poetry init

# 添加依赖
poetry add flask
poetry add --group dev pytest pytest-cov black

# 移除依赖
poetry remove flask

# 安装所有依赖
poetry install

# 更新依赖
poetry update
poetry update flask          # 更新特定包

# 运行命令（在虚拟环境中）
poetry run python script.py
poetry run pytest

# 进入虚拟环境 shell
poetry shell

# 构建和发布
poetry build                 # 构建 wheel 和 sdist
poetry publish               # 发布到 PyPI
```

**实战案例一：完整的 pyproject.toml 配置**

```toml
[tool.poetry]
name = "my-web-app"
version = "1.0.0"
description = "A modern web application"
authors = ["Your Name <email@example.com>"]
readme = "README.md"
license = "MIT"

[tool.poetry.dependencies]
python = "^3.11"
fastapi = "^0.109.0"
```

### 56. Nix

**前世今生**

Nix 由 Eelco Dolstra 于 2003 年在乌得勒支大学博士研究期间创建。Eelco 的博士论文《The Purely Functional Software Deployment Model》奠定了 Nix 的理论基础。Nix 的核心理念是"函数式包管理"——每个包是其输入（源代码、依赖、构建脚本）的纯函数，输出存放在一个不可变的、基于哈希的路径中（如 `/nix/store/abc123...-package-version/`）。这种设计带来了两个革命性特性：可重现构建（同一输入必然产生同一输出）和原子升级（新旧版本可以并存，回滚只需切换符号链接）。Nix 后来衍生出 NixOS（一个基于 Nix 的 Linux 发行版）和 Nixpkgs（最大的开源软件仓库之一，超过 80,000 个包）。尽管学习曲线陡峭，Nix 在 DevOps 和可重现研究领域拥有忠实追随者。

**使用方法与案例**

**安装方式：**

```bash
# macOS
sh <(curl -L https://nixos.org/nix/install)

# Linux (多用户安装，推荐)
sh <(curl -L https://nixos.org/nix/install) --daemon

# 或使用 Determinate Systems 的安装器（更好的默认配置）
curl --proto '=https' --tlsv1.2 -sSf -L https://install.determinate.systems/nix | sh -s -- install

# Windows (WSL2 中安装)
# 在 WSL2 中运行上述 Linux 安装命令
```

**基础用法：**

```bash
# 临时使用一个包（不安装到系统）
nix run nixpkgs#cowsay -- "Hello Nix"
nix run nixpkgs#python3 -- -c "print('Hello')"

# 搜索包
nix search nixpkgs nodejs

# 安装包到用户环境
nix profile install nixpkgs#ripgrep
nix profile install nixpkgs#fd

# 列出已安装的包
nix profile list

# 移除包
nix profile remove ripgrep

# 进入包含特定包的临时 shell
nix shell nixpkgs#nodejs nixpkgs#yarn
# 在 shell 中可以使用 node 和 yarn，退出后不再可用
```

**实战案例一：创建开发环境 shell.nix**

```nix
    ]))

  # 进入环境时执行的命令
  shellHook = ''
    echo "Dev environment ready!"
    export PATH="$PWD/node_modules/.bin:$PATH"
  '';
}
```

```bash

# 或使用 direnv 自动激活

# use nix
# 然后运行 direnv allow
```

**实战案例二：Nix Flakes（下一代 Nix）**

- `nix-store --gc` 垃圾回收未使用的包
- `nix-collect-garbage -d` 删除所有旧版本
- `nix-channel --update` 更新 nixpkgs 频道
- `nixpkgs-fmt` 格式化 .nix 文件
- `home-manager`：用 Nix 声明式管理用户配置（dotfiles）

**避坑指南：**

- Nix 语言有自己的语法（函数式、惰性求值），学习曲线陡峭
- macOS 上 `/nix` 目录会占用大量空间，定期运行垃圾回收

### 57. Homebrew

**前世今生**

Homebrew 由 Max Howell 于 2009 年创建，Ruby 语言编写。Max 是英国开发者，曾在 Last.fm 和 Twitter 工作。在 Homebrew 之前，macOS 用户安装开源软件主要依赖 MacPorts（基于 FreeBSD ports 系统）或 Fink（基于 Debian 的 dpkg/apt），这些工具要么编译速度慢、要么与 macOS 集成不友好。Homebrew 的口号"macOS 缺失的包管理器"精准击中了痛点：它使用 Ruby DSL 定义包安装"公式"（Formula），优先提供预编译二进制（Bottle），安装过程简洁到只需 `brew install <package>`。Homebrew 的巨大成功也带来了争议——Max Howell 在 2015 年应聘 Google 时因"不会在白板上翻转二叉树"而被拒（他的经典推文："Google: 90% of our engineers use the software you wrote, but you can't invert a binary tree so fuck off."）。如今 Homebrew 已扩展到 Linux（Linuxbrew），拥有超过 7,000 个官方维护的 formula。

**使用方法与案例**

**安装方式：**

```bash
# macOS / Linux
/bin/bash -c "$(curl -fsSL https://raw.githubusercontent.com/Homebrew/install/HEAD/install.sh)"

# 安装后按提示将 Homebrew 添加到 PATH
# Linux 上安装后通常需要：
echo 'eval "$(/home/linuxbrew/.linuxbrew/bin/brew shellenv)"' >> ~/.bashrc
eval "$(/home/linuxbrew/.linuxbrew/bin/brew shellenv)"
```

**基础用法：**

```bash
# 安装软件
brew install git
brew install --cask visual-studio-code     # GUI 应用（macOS）
brew install node@20                        # 特定版本

# 搜索软件
brew search python

# 查看软件信息
brew info python

# 更新
brew update                    # 更新 Homebrew 自身和 formula 索引
brew upgrade                   # 升级所有已安装的包
brew upgrade python            # 升级特定包

# 卸载
brew uninstall python
brew autoremove                # 移除不再需要的依赖

# 系统诊断
brew doctor                    # 检查潜在问题
brew cleanup                   # 清理旧版本和缓存
```

- `brew deps --tree <formula>` 查看依赖树
- `HOMEBREW_NO_AUTO_UPDATE=1 brew install ...` 跳过自动更新

**避坑指南：**

- `brew cleanup` 需要定期执行，否则旧版本会占用大量磁盘空间
- 安装某些 formula 时可能需要 Xcode Command Line Tools：`xcode-select --install`
- Cask（GUI 应用）只适用于 macOS；Linux 上 Homebrew 只能安装 CLI 工具

### 58. Scoop

**前世今生**

Scoop 由 Luke Sampson 于 2014 年创建，PowerShell 编写。Luke 是澳大利亚开发者，他注意到 Windows 开发者社区长期缺乏一个类似 Homebrew/apt 的命令行包管理器。Chocolatey 虽然存在更早（2011 年），但它需要管理员权限，且软件安装在系统目录。Scoop 的核心创新是"用户态安装"——所有软件安装到 `~/scoop/` 目录，不需要管理员权限，不会污染系统 PATH 和环境变量。每个应用安装在自己的版本化目录中（如 `~/scoop/apps/python/3.11.5/`），通过 shim（垫片）暴露到 PATH，多版本可以并存。Scoop 的设计理念明确针对开发者工具和命令行软件（不追求覆盖所有 Windows 软件），这使它在 Windows 开发者社区中获得了稳定的用户基础。

**使用方法与案例**

**安装方式：**

```powershell
# PowerShell 中运行（非管理员）
Set-ExecutionPolicy RemoteSigned -Scope CurrentUser
irm get.scoop.sh | iex

# 或自定义安装目录
irm get.scoop.sh -outfile 'install.ps1'
.\install.ps1 -ScoopDir 'D:\Scoop'
```

**基础用法：**

```powershell
# 添加常用 bucket（软件仓库）
scoop bucket add extras      # GUI 应用和工具
scoop bucket add versions    # 旧版本软件
scoop bucket add nerd-fonts  # Nerd Font 字体

# 搜索和安装
scoop search python
scoop install python
scoop install git nodejs neovim

# 更新
scoop update                # 更新 Scoop 自身
scoop update *              # 更新所有已安装应用
scoop update python         # 更新特定应用

# 查看
scoop list                  # 已安装的应用
scoop info python           # 应用详情
scoop status                # 检查哪些应用可更新

# 卸载
scoop uninstall python

# 清理旧版本
scoop cleanup *
```

**实战案例一：Windows 开发环境一键搭建**

```powershell
# setup-windows-dev.ps1
# 以普通用户身份在 PowerShell 中运行

scoop install nodejs-lts python rust go
scoop install neovim vscode

# 安装命令行工具

# 安装终端和字体
scoop install windows-terminal
scoop bucket add nerd-fonts
scoop install FiraCode-NF-Mono

# 安装容器工具
scoop install docker

# 查看安装了哪些软件
scoop list

Write-Host "Don't forget to restart your terminal!"
```

**实战案例二：管理多个软件版本**

```powershell

scoop bucket add versions
scoop install python311
scoop install python312

# 切换默认版本

# 查看当前使用的版本

# 切换到另一个版本

python --version  # 3.12.x

# 安装特定版本的 Node.js
scoop install nodejs18
scoop install nodejs-lts
```

**进阶技巧：**

- `scoop hold <app>` 锁定应用版本，防止更新
- `scoop reset <app>` 切换活动版本（已安装多版本时）
- `scoop export > scoopfile.json` 导出已安装列表
- `scoop import scoopfile.json` 从文件批量安装
- `scoop config aria2-enabled true` 启用 aria2 多线程下载加速
- `scoop checkup` 检查潜在问题

**避坑指南：**

- Scoop 的 `main` bucket 包很少，必须添加 `extras` 和 `versions` bucket
- 某些软件（尤其是 GUI 应用）的 manifest 可能过时，需要手动更新
- `scoop reset` 切换版本时，全局 shim 会指向新版本，但已打开的终端不受影响
- 安装 scoop 后如果命令不可用，检查 `$env:SCOOP` 是否已添加到 PATH

### 59. just

**前世今生**

just 由 Casey Rodarmor 于 2016 年创建，Rust 语言编写。Casey 是美国开发者，他还创建了 Bitcoin Ordinals 协议和 `ago`（时间格式化库）。`just` 的定位是"命令运行器"（Command Runner）——它类似于 `make`，但专门为运行项目命令（而非构建 C/C++ 项目）而设计。传统 `make` 在非 C/C++ 项目中被广泛滥用来定义 `make lint`、`make test`、`make deploy` 等任务，但 Makefile 的语法（Tab 缩进、`.PHONY` 声明、`$@`/`$^` 等自动变量）对于非构建场景过于复杂。`just` 提供了一个简洁、直观的语法，类似于 Makefile 但去掉了所有构建时概念，并增加了参数传递、环境变量管理、多平台支持等现代化特性。它在 Rust 社区迅速流行，随后扩展到全栈开发领域。

**使用方法与案例**

**安装方式：**

```bash
# macOS
brew install just

# Linux (Debian/Ubuntu)
sudo apt install just

# 或从 GitHub Releases 下载预编译二进制
# https://github.com/casey/just/releases

# Windows (Scoop)
scoop install just

# 通过 cargo
cargo install just
```

**基础用法：**

```makefile
# justfile — 项目命令定义

# 默认任务（直接运行 just 时执行）
default:
    just --list

# 基本命令
build:
    cargo build --release

test:
    cargo test

lint:
    cargo clippy -- -D warnings

format:
    cargo fmt -- --check

# 依赖：deploy 依赖 build 和 test
deploy: build test
    echo "Deploying..."
    ./scripts/deploy.sh

# 带参数的命令
release VERSION:
    git tag -a v{{VERSION}} -m "Release v{{VERSION}}"
    git push origin v{{VERSION}}

# 带默认值的参数
serve port='3000':
    python -m http.server {{port}}

# 环境变量
export RUST_BACKTRACE := "1"

# 可选的默认值
watch pattern='src/':
    cargo watch -x run -w {{pattern}}
```

**实战案例一：多语言项目的统一命令入口**

```makefile

set positional-arguments := true
set shell := ["bash", "-c"]

# 列出所有可用命令
default:
    @just --list

# === 后端 (Python) ===
backend-install:
    cd backend && poetry install

backend-dev:
    cd backend && poetry run uvicorn main:app --reload

backend-test:
    cd backend && poetry run pytest -v

backend-lint:
    cd backend && poetry run ruff check .
    cd backend && poetry run mypy .

# === 前端 (React) ===
frontend-install:
    cd frontend && pnpm install

frontend-dev:
    cd frontend && pnpm dev

frontend-build:
    cd frontend && pnpm build

frontend-test:
    cd frontend && pnpm test

# === Docker ===
docker-build:
    docker compose build

docker-up:
    docker compose up -d

docker-down:
    docker compose down

# === 组合命令 ===
setup: backend-install frontend-install
    @echo "Setup complete!"

dev:
    just backend-dev & just frontend-dev

# === 数据库 ===
db-migrate msg:
    cd backend && poetry run alembic upgrade head

db-reset:
    cd backend && poetry run alembic downgrade base
    cd backend && poetry run alembic upgrade head
```

**实战案例二：CI/CD 集成**

```makefile
# justfile — CI 管道命令

ci-test:
    #!/usr/bin/env bash
    set -euxo pipefail
    cargo test --all-features
    cargo clippy --all-features -- -D warnings
    cargo fmt --all -- --check

ci-build image_tag:
    #!/usr/bin/env bash
    set -euxo pipefail
    docker build -t myapp:{{image_tag}} .
    docker push myapp:{{image_tag}}

# 使用条件判断
ci-deploy env='staging':
    #!/usr/bin/env bash
    set -euxo pipefail
    if [ "{{env}}" = "production" ]; then
        echo "Deploying to production..."
        kubectl apply -f k8s/prod/
    else
        echo "Deploying to staging..."
        kubectl apply -f k8s/staging/
    fi
```

**进阶技巧：**

- `just --list` 列出所有可用命令（带描述）
- `just --summary` 查看 justfile 的简洁摘要
- 使用 `#!/usr/bin/env bash` 作为 shebang 编写多行脚本
- `set dotenv-load := true` 自动加载 `.env` 文件
- `@` 前缀静默执行（不打印命令本身）
- 支持从其他 justfile 导入：`import 'other.justfile'`

**避坑指南：**

- `just` 默认在当前目录找 `justfile`，子目录中运行 `just` 会向上递归查找
- 变量使用双花括号 `{{variable}}`（为与 Makefile 的 `$(var)` 区分）
- 命令中的 `cd` 不会影响后续命令，每个命令行是独立进程
- Windows 上默认使用 PowerShell 执行命令，需要通过 `set shell` 修改

### 60. mise

**前世今生**

mise（原名 rtx，2024 年改为 mise）由 Jeff Dickey 于 2022 年创建，Rust 语言编写。Jeff 是美国开发者，他感到现有的工具版本管理器（asdf、nvm、pyenv、rbenv 等）架构过时且分散——asdf 虽支持多语言但依赖 shim 机制导致性能问题，且每个工具需要单独安装插件。mise 的设计理念是"统一的开发环境管理器"：它用一个 Rust 二进制文件替代了 asdf+direnv+make 的组合，支持管理多种编程语言的运行时版本（Node.js、Python、Ruby、Go、Rust 等）、项目级环境变量、任务运行（类似 just）和目录特定的自动激活。mise 使用符号链接而非 shim 来切换版本，避免了 asdf 的性能问题。项目在 2024 年改名 mise（法语"放置/设置"），迅速在 Rust 和 DevOps 社区获得关注。

**使用方法与案例**

**安装方式：**

```bash
# macOS / Linux
curl https://mise.run | sh

# 或通过 Homebrew
brew install mise

# 或通过 cargo
cargo install mise

# Windows (Scoop)
scoop install mise

# 激活 mise（添加到 ~/.bashrc 或 ~/.zshrc）
eval "$(mise activate bash)"  # bash
eval "$(mise activate zsh)"   # zsh
# 或通用方式
echo 'eval "$(mise activate)"' >> ~/.bashrc
```

**基础用法：**

```bash
# 安装语言运行时
mise use node@20             # 在当前目录设置 Node.js 20
mise use python@3.12         # 在当前目录设置 Python 3.12
mise use go@1.21             # 在当前目录设置 Go 1.21

# 全局设置
mise use -g node@20
mise use -g python@3.12

# 查看已安装的工具
mise ls

# 查看当前使用的版本
mise current

# 安装并设置多个工具
mise use node@20 python@3.12 rust@latest

# 卸载工具
mise uninstall node@18
```

**实战案例一：项目环境配置 (.mise.toml)**

```toml
# .mise.toml — 项目级开发环境配置

[tools]
# 语言运行时版本
node = "20"
python = "3.12"
go = "1.21"

# 从特定源安装
# "node" = { version = "20", source = "github:asdf-community/asdf-nodejs" }

[env]
# 项目级环境变量（进入目录时自动设置）
DATABASE_URL = "postgresql://localhost:5432/myapp"
API_PORT = "3000"
NODE_ENV = "development"

[tasks.build]
description = "Build the project"
run = '''
  cd frontend && pnpm build
  cd ../backend && go build -o dist/server ./cmd/server
'''

[tasks.dev]
description = "Start development servers"
run = '''
  mise tasks run dev:frontend &
  mise tasks run dev:backend &
  wait
'''

[tasks."dev:frontend"]
run = "cd frontend && pnpm dev"

[tasks."dev:backend"]
run = "cd backend && go run ./cmd/server"

[tasks.test]
description = "Run all tests"
run = '''
  cd frontend && pnpm test
  cd backend && go test ./...
'''

[tasks.lint]
description = "Run all linters"
run = '''
  cd frontend && pnpm lint
  cd backend && golangci-lint run
'''
```

**实战案例二：从 asdf 迁移到 mise**

```bash
# 1. 导出 asdf 的配置
# 查看 .tool-versions 文件：
# nodejs 20.10.0
# python 3.12.1
# golang 1.21.5

# 2. 安装 mise 后导入
mise install        # mise 会自动识别 .tool-versions 文件

# 3. 从 .tool-versions 迁移到 .mise.toml
# 可以直接使用 .tool-versions，也可以手动迁移到 .mise.toml

# 4. 移除 asdf 的 shell 集成（从 .bashrc/.zshrc 中删除）
# 注释掉：. "$HOME/.asdf/asdf.sh"

# 5. 验证迁移
mise current
# 应显示：
# node    20.10.0
# python  3.12.1
# go      1.21.5
```

**进阶技巧：**

- `mise trust` 信任目录下的 `.mise.toml`（防止自动执行不明配置）
- `mise doctor` 诊断环境问题
- `mise plugins ls-remote` 查看可安装的插件
- `mise x <tool> -- <command>` 用临时环境运行命令
- `mise tasks ls` 列出所有定义的任务
- Hook 机制：`[hooks.enter]` 和 `[hooks.leave]` 在进入/离开目录时执行脚本

**避坑指南：**

- mise 与 asdf 共享 `.tool-versions` 格式，但优先读取 `.mise.toml`
- 如果系统中已有 nvm/pyenv 等版本管理器，注意 PATH 优先级不要冲突
- `mise activate` 的初始化在不同 shell 中语法略有不同
- 部分插件（如 Java、.NET）可能需要系统上安装额外的依赖
