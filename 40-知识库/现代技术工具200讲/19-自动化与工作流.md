## 181. n8n

**前世今生：** n8n 由 Jan Oberhauser 于 2019 年创立，总部位于德国柏林。其名称源于 "nodemation"（节点自动化），后来简化为 "n8n"（首尾 n 中间 8 个字母）。n8n 的设计哲学是"公平代码"（Fair-code）——源代码开放、可自托管，但商业使用需授权。这一模式在开源社区引发广泛讨论，但它确实在 Zapier/Make 等闭源平台之外提供了可审计、可定制的替代方案。2021 年获得 Sequoia 领投的 1200 万美元 A 轮，2023 年 B 轮再融 5500 万欧元，成为欧洲增长最快的开源自动化公司之一。截至目前 GitHub 已超 50k stars，其独特优势在于 400+ 原生集成节点 + 可视化拖拽 + 自托管能力，让技术团队可以拥有完整的自动化主权。

**使用方法与案例：**

安装（推荐 Docker 自托管）：
```bash
docker run -d --name n8n -p 5678:5678 \
  -v n8n_data:/home/node/.n8n \
  -e N8N_SECURE_COOKIE=false \
  n8nio/n8n
```
或 npm 全局安装：`npm install -g n8n` 然后 `n8n start`。访问 `http://localhost:5678` 进入画布。

**案例1：飞书消息 → 自动汇总到 Obsidian 日报**
- Trigger 节点：Webhook（接收飞书 outcoming webhook）
- Function 节点：提取消息文本，解析日期/内容
- Write File 节点：追加写入 Obsidian vault 的日报 .md 文件
```javascript
// Function 节点代码示例
const msg = $input.first().json;
const today = new Date().toISOString().slice(0, 10);
const line = `- [${msg.time}] ${msg.user}: ${msg.content}`;
return { filePath: `/vault/日报/${today}.md`, line };
```

**案例2：定时抓取 API 数据 → 飞书通知**
- Schedule 触发器（每天 8:00）
- HTTP Request 节点：调生产系统 API 取 OEE 数据
- IF 节点：当 OEE < 85% 时触发告警
- 飞书消息节点：发送卡片消息到管理群

**进阶技巧：**
- 用 `n8n export:workflow --id=<id>` 备份工作流为 JSON
- 子工作流调用：`Execute Workflow` 节点实现复用
- 错误处理：每个节点可设置 "On Error" 分支，避免单点故障阻断整条流
- 环境变量：`N8N_ENCRYPTION_KEY` 必须设置以加密凭证存储

## 182. Temporal

**前世今生：** Temporal 由 Uber 的前工程师 Maxim Fateev 和 Samar Abbas 于 2019 年创建。两人在 Uber 时开发了 Cadence（Uber 内部的工作流引擎，支撑了数百个微服务的业务逻辑），随后离开 Uber 创立 Temporal Technologies，将 Cadence 的核心思想重写为开源项目。Temporal 解决的核心问题是"持久化执行"——如果一个步骤失败，不是整个流程崩溃，而是自动重试、记录状态、可人为干预。2021 年获得 1.03 亿美元 B 轮融资，估值 15 亿美元。Netflix、Snap、Stripe、Coinbase 都在用 Temporal 管理关键业务流程。它本质上是一个"永远不会丢失工作状态的编排引擎"，将工作流状态外部化到数据库，工作进程可随时重启而不丢失进度。

**使用方法与案例：**

SDK 安装（以 TypeScript 为例）：
```bash
npm install @temporalio/client @temporalio/worker @temporalio/workflow
# 启动开发服务器
temporal server start-dev
```

**案例1：订单处理 Saga 模式**
```typescript
// workflow.ts — 定义工作流
export async function orderWorkflow(order: Order): Promise<void> {
  await reserveInventory(order);   // 步骤1：锁库存
  try {
    await processPayment(order);   // 步骤2：扣款
    await createShipment(order);   // 步骤3：发货
  } catch (err) {
    await releaseInventory(order); // 补偿：释放库存
    throw err;
  }
}
```
关键：如果步骤 3 失败，Temporal 自动重试（可配置指数退避），不会丢状态。如果发货服务宕机 2 小时，恢复后 Temporal 继续从发货步骤执行。

**案例2：数据管道编排**
```typescript
// 每日 ETL：提取 → 清洗 → 写入 → 通知
export async function etlWorkflow(date: string): Promise<void> {
  const raw = await extractData(date);         // Activity 1
  const cleaned = await transformData(raw);    // Activity 2
  await loadToWarehouse(cleaned);              // Activity 3
  await sendFeishuNotification(date);          // Activity 4
}
```
Activities 可以配置超时（`startToCloseTimeout: '5m'`）、重试策略（`maximumAttempts: 3`）、心跳（长任务定期上报进度）。

**进阶技巧：**
- `Workflow.condition()` 等待外部信号，实现人工审批节点
- `Child Workflow` 实现工作流复用和隔离
- `tctl workflow reset` 从历史任意点重新执行
- 生产部署需要自建 Temporal Server（Cassandra/MySQL/PostgreSQL 持久化）

## 183. Apache Airflow

**前世今生：** Airflow 由 Airbnb 的数据工程师 Maxime Beauchemin 于 2014 年创建。当时 Airbnb 的数据管道日益复杂，"cron + bash 脚本"模式已无法满足依赖管理和可视化需求。Beauchemin 设计了一个 DAG（有向无环图）模型，用 Python 代码定义任务依赖，Web UI 监控执行状态。2016 年捐献给 Apache 基金会，2019 年成为顶级项目。Airflow 定义了"工作流即代码"（Workflow as Code）范式，催生了整个数据编排品类。虽然被 Dagster/Prefect 等后来者挑战，但凭借先发优势和庞大生态（1000+ provider 包），至今仍是数据工程领域的事实标准，超过 10 万组织在使用。

**使用方法与案例：**

安装：
```bash
pip install apache-airflow
airflow db init
airflow users create --username admin --password admin \
  --firstname Admin --lastname User --role Admin --email admin@example.com
airflow webserver -p 8080 & airflow scheduler &
```

**案例1：生产日报数据管道**
```python
from airflow import DAG
from airflow.operators.python import PythonOperator
from datetime import datetime, timedelta

default_args = {
    'owner': 'woker',
    'retries': 2,
    'retry_delay': timedelta(minutes=5),
}

with DAG('daily_production_report',
         default_args=default_args,
         schedule_interval='0 6 * * *',  # 每天早 6 点
         start_date=datetime(2026, 1, 1),
         catchup=False) as dag:

    def extract_production_data(**context):
        # 从 MES 系统拉取昨日数据
        ds = context['ds']  # 逻辑日期
        return fetch_from_api(f"/api/production?date={ds}")

    def calculate_oee(**context):
        data = context['task_instance'].xcom_pull(task_ids='extract')
        oee = (data['availability'] * data['performance'] * data['quality']) / 10000
        return round(oee, 2)

    def send_report(**context):
        oee = context['task_instance'].xcom_pull(task_ids='calc_oee')
        send_feishu_card(f"昨日 OEE: {oee}%")

    t1 = PythonOperator(task_id='extract', python_callable=extract_production_data)
    t2 = PythonOperator(task_id='calc_oee', python_callable=calculate_oee)
    t3 = PythonOperator(task_id='send', python_callable=send_report)

    t1 >> t2 >> t3  # 依赖关系
```

**案例2：条件分支 + 并行处理**
```python
from airflow.operators.bash import BashOperator

# 并行处理 3 条产线
for line in ['A', 'B', 'C']:
    process = BashOperator(
        task_id=f'process_line_{line}',
        bash_command=f'python process.py --line {line}'
    )
    t1 >> process >> t3  # 每条线独立并行
```

**进阶技巧：**
- `xcom_pull` 在不同 Task 间传递数据（小数据用 XCom，大数据存 S3/OBS）
- `ShortCircuitOperator` 实现条件跳过
- `ExternalTaskSensor` 等待另一个 DAG 完成
- 生产用 CeleryExecutor 或 KubernetesExecutor 实现分布式执行

## 184. Dagster

**前世今生：** Dagster 由 Nick Schrock（前 Facebook/GraphQL 联合创始人）于 2018 年创立。Schrock 在 Facebook 时深刻体会到"Pipeline 不等于 Data Asset"——传统的管道思维关注执行步骤，却忽略了数据的生命周期。Dagster 的核心创新是"软件定义资产"（Software-Defined Asset），将关注点从"跑什么任务"扭转为"产出什么数据资产"。2022 年 B 轮融资 1.15 亿美元。与 Airflow 的最大区别：Airflow 是"任务中心"，Dagster 是"资产中心"。在 Dagster 中，你会看到"这张表由哪些上游表产生"而非"这些任务按什么顺序跑"。这对数据治理、血缘追踪、增量回填有天然优势。

**使用方法与案例：**

安装：
```bash
pip install dagster dagit
dagster dev  # 一键启动 Web UI + 守护进程
```

**案例1：生产数据资产定义**
```python
from dagster import asset, AssetIn, Definitions, ScheduleDefinition

@asset(key="raw_production")  # 定义资产而非任务
def extract_production_data():
    return fetch_from_mes()  # 返回 DataFrame

@asset(
    ins={"raw": AssetIn("raw_production")},  # 声明输入资产
    key="daily_oee"
)
def compute_oee(raw):
    oee = (raw['availability'] * raw['performance'] * raw['quality']) / 10000
    return {"date": raw['date'].max(), "oee": round(oee, 2)}

@asset(key="oee_report", ins={"oee": AssetIn("daily_oee")})
def generate_report(oee):
    create_excel_report(oee)
    return f"Report generated for OEE: {oee['oee']}%"

# 调度
daily_schedule = ScheduleDefinition(
    job_name="production_pipeline",
    cron_schedule="0 6 * * *"
)

defs = Definitions(
    assets=[extract_production_data, compute_oee, generate_report],
    schedules=[daily_schedule]
)
```

**案例2：增量回填**
```bash
# Airflow 回填很痛苦；Dagster 天然支持
dagster asset backfill --asset daily_oee --partition 2026-01-01..2026-06-30
```
自动分析依赖链，从缺失的最上游资产开始回填，不会重复计算已有数据。

**进阶技巧：**
- `@multi_asset` 一个函数产出多个资产
- `IOManager` 抽象存储后端（本地/S3/BigQuery），代码不变
- `AssetObservation` 记录数据质量元数据（行数、null 率等），在 UI 上直接看到
- `branch_deployment` 让每个 Git 分支有独立的 Dagster 环境

## 185. Prefect

**前世今生：** Prefect 由 Jeremiah Lowin 于 2018 年创建，其设计灵感来自他在金融行业管理复杂数据管道的痛苦经验。Lowin 认为 Airflow 太"静态"——DAG 必须在调度执行前完全定义，无法在运行时动态生成任务。Prefect 的核心差异化是"动态 DAG"和"正向传播"（任务天然知道自己的上游/下游）。2021 年推出 Prefect 2.0，彻底重构为推模式（push model），Python 原生函数即 Task，无需继承特定基类。2023 年 C 轮融资 8500 万美元。Prefect 的定位明确：比 Airflow 更 Pythonic、比 Dagster 更轻量，适合既需要工作流编排又不想被框架绑架的团队。

**使用方法与案例：**

安装：
```bash
pip install prefect
prefect server start  # 启动本地 UI
```

**案例1：Python 原生函数秒变工作流**
```python
from prefect import task, flow

@task(retries=3, retry_delay_seconds=60)  # 装饰器即配置
def fetch_oee_data(line: str) -> dict:
    resp = requests.get(f"http://mes/api/oee/{line}")
    return resp.json()

@task
def analyze(data: list[dict]) -> dict:
    df = pd.DataFrame(data)
    return {"avg_oee": df['oee'].mean(), "worst_line": df.loc[df['oee'].idxmin(), 'line']}

@flow(name="Production-OEE-Analysis")  # 工作流定义
def daily_oee_flow():
    lines = ["A", "B", "C", "D"]
    # 动态并行：4 条线同时抓
    results = fetch_oee_data.map(lines)  # Prefect 的 .map() 并行
    report = analyze(results)
    return report

if __name__ == "__main__":
    daily_oee_flow()  # 直接运行 or `python script.py`
```

**案例2：条件分支 + 通知**
```python
@flow
def production_monitor():
    oee = compute_oee()
    if oee < 0.85:
        alert_feishu(f"⚠️ OEE 低于 85%: {oee}%")
    elif oee >= 0.95:
        post_achievement(f"🎉 OEE 达标: {oee}%")
    # else: 正常，不做动作
```

**进阶技巧：**
- Prefect Cloud 提供托管调度，本地开发→云端运行无缝切换
- `Task concurrency` 限制并行数，保护上游 API
- 结果持久化（`result_storage`）到 S3/MinIO
- 部署到 K8s 用 `prefect deploy` 一行命令生成 Helm chart

## 186. Make (原 Integromat)

**前世今生：** Make 最初名为 Integromat，由 Ondřej Gazda 于 2012 年在捷克布拉格创立。与 Zapier 几乎同期诞生，但早期知名度远不及。Integromat 的差异化在于"可视化数据流"——不是简单的 A→B 触发器，而是带条件分支、迭代器、数据转换器的真正流程图。2021 年更名为 Make 并获得 5500 万美元融资。Make 在"复杂自动化场景"中比 Zapier 更强大——支持数组迭代、错误分支、数据聚合，几乎像是一个无代码编程语言。截至 2024 年拥有 1800+ 集成模板、月活跃数十万用户，是 Zapier 之外最大的可视化自动化平台。

**使用方法与案例：**

无需安装，访问 make.com 注册即用。

**案例1：微信文件 → OCR → Obsidian 日记**
```
Module 1: 邮件触发器（监控 wechat 文件转发邮箱）
    ↓
Module 2: HTTP → 下载附件到服务器
    ↓
Module 3: 调用 OCR API 转文本
    ↓
Module 4: Text Parser → 提取日期/内容
    ↓
Module 5: Webhook → 写入 Obsidian（通过 Local REST API 插件）
```

每个 Module 之间的数据流用可视化连线，鼠标拖拽即可修改。

**案例2：多源数据聚合 → 管理驾驶舱**
```
Module 1: HTTP → MES API 取产量
Module 2: HTTP → ERP API 取成本     (并行)
Module 3: HTTP → 财务 API 取回款
    ↓
Module 4: Data Store → 聚合三个来源
    ↓
Module 5: JSON → 转换为仪表盘格式
    ↓
Module 6: 飞书 → 发送富文本卡片
```

**进阶技巧：**
- Iterator 处理数组（如遍历所有产线）
- Router 实现 if/else 分支（OEE>90% 一条路，<80% 另一条路）
- Error Handler 自定义错误处理，避免"全或无"
- Make 的 Data Store 可做临时缓存，跨 Scenario 共享数据

## 187. Kestra

**前世今生：** Kestra 由 Ludovic Dehon 和 Emmanuel Darras 于 2021 年在法国创立。两人在数据工程领域深耕多年，发现市场上缺少一个"声明式 + 事件驱动"的编排器——Airflow 太重，n8n 太"点对点"，Temporal 太"代码化"。Kestra 的核心理念是：用 YAML 声明流程、支持丰富触发器（定时、事件、API）、插件生态。Kestra 的声明式语法像 K8s 的 YAML 一样，让非开发者也能理解流程定义。2023 年开源，GitHub 迅速突破 10k stars，获得多家欧洲企业采用。

**使用方法与案例：**

安装：
```bash
docker run -d -p 8080:8080 kestra/kestra server local
# 或下载 JAR: java -jar kestra.jar server local
```

**案例1：YAML 声明式 ETL 管道**
```yaml
id: daily_production_report
namespace: production
tasks:
  - id: extract
    type: io.kestra.plugin.fs.http.Request
    uri: "https://mes.company.com/api/production/{{ trigger.date }}"
    method: GET

  - id: transform
    type: io.kestra.plugin.scripts.python.Script
    inputFiles:
      data.py: |
        import json, sys
        data = json.loads(sys.stdin.read())
        oee = sum(d['oee'] for d in data) / len(data)
        print(json.dumps({"oee": round(oee, 2)}))

  - id: load
    type: io.kestra.plugin.jdbc.postgresql.Query
    sql: |
      INSERT INTO oee_daily (date, oee) VALUES ('{{ trigger.date }}', {{ outputs.transform.vars.oee }})
    url: jdbc:postgresql://db:5432/production

triggers:
  - id: schedule
    type: io.kestra.core.models.triggers.types.Schedule
    cron: "0 6 * * *"
```

**案例2：事件驱动 + 条件分支**
```yaml
triggers:
  - id: webhook
    type: io.kestra.core.models.triggers.types.Webhook
    key: production_alert

tasks:
  - id: check_severity
    type: io.kestra.core.tasks.flows.Switch
    value: "{{ trigger.body.severity }}"
    cases:
      critical:
        - id: notify_director
          type: io.kestra.plugin.notifications.feishu.FeishuSend
          ...
      warning:
        - id: log_only
          type: io.kestra.core.tasks.log.Log
          message: "Warning event logged"
```

**进阶技巧：**
- `Flow Trigger` 一个流触发另一个流
- `ForEach` 并行处理数组元素
- 内置重试 (`retry.maxAttempt: 3`)、超时、错误处理
- KV Store 跨流共享状态

## 188. Apache NiFi

**前世今生：** NiFi 最初由美国国家安全局（NSA）于 2006 年开发，代号 "NiagaraFiles"，用于情报数据的自动流转。2014 年 NSA 将其捐献给 Apache 基金会，更名为 NiFi。这个"出身"本身就说明其定位：处理高安全要求、复杂路由、海量数据流的自动化。NiFi 核心理念是"流式编程"——画布上拖拽处理器（Processor），数据以 FlowFile 的形式在处理器间流动，每个 FlowFile 携带内容 + 属性字典。NiFi 的独特优势在于数据溯源（自动追踪每条数据的完整旅程）、背压控制、优先级队列。虽然 UI 看起来有点"老派 Java"，但它在物联网、日志采集、数据合规领域不可替代。

**使用方法与案例：**

安装：
```bash
wget https://dlcdn.apache.org/nifi/1.25.0/nifi-1.25.0-bin.zip
unzip nifi-1.25.0-bin.zip && cd nifi-1.25.0
./bin/nifi.sh start  # 访问 http://localhost:8443/nifi
```

**案例1：MES 数据采集 → 清洗 → Kafka**
```
GetHTTP → EvaluateJsonPath → ReplaceText → PublishKafka
   ↓            ↓                ↓
 拉取 MES     提取字段       格式化为 JSON   发送到 Kafka
```
- GetHTTP: 定期拉 `http://mes/api/data`
- EvaluateJsonPath: 提取 `$.production[*].oee`
- ReplaceText: 转换为 `{"timestamp":"...","oee":85.2}`
- PublishKafka: 写入主题 `mes.raw`

**案例2：多源文件合并 + 去重**
```
GetFile(A) ─┐
GetFile(B) ─┼→ MergeContent → DetectDuplicate → PutFile(merged)
GetFile(C) ─┘
```
- MergeContent 按时间窗口合并文件
- DetectDuplicate 用哈希去重
- 属性传递实现原始来源追溯

**进阶技巧：**
- `Provenance Repository` 自动记录每个 FlowFile 历经的所有处理器，审计必备
- 背压（Back Pressure）：当队列超阈值自动暂停上游，防止 OOM
- `NiFi Registry` 实现流定义的版本管理（类似 Git）
- 集群模式：Zero-Master Clustering，节点对等无单点

## 189. Node-RED

**前世今生：** Node-RED 由 IBM 新兴技术服务部的 Nick O'Leary 和 Dave Conway-Jones 于 2013 年创建，最初是 IBM 内部物联网原型工具的副产品。其设计灵感来自"让非程序员也能连接硬件和在线服务"。Node-RED 基于 Node.js，核心是流编辑器——在浏览器里拖拽节点、连线，点击部署即生效。2016 年成为 JS 基金会项目，2019 年并入 OpenJS 基金会。Node-RED 在物联网（IoT）领域几乎是最流行的低代码平台，Raspberry Pi 预装，Home Assistant 深度集成。2000+ 社区节点覆盖 MQTT、Modbus、OPC-UA、数据库、云服务等。

**使用方法与案例：**

安装：
```bash
npm install -g node-red
node-red  # 访问 http://localhost:1880
```

**案例1：车间 PLC 数据 → 飞书告警**
```
[Modbus Read] → [Function] → [Feishu Push]
     ↓              ↓              ↓
  读 PLC 寄存器  计算 OEE      发卡片消息
```
Function 节点代码：
```javascript
// 从 Modbus 读取的数据计算 OEE
const parts = msg.payload.total_parts;       // 总产量
const ideal = msg.payload.cycle_time * parts; // 理想时间
const actual = msg.payload.run_time;          // 实际运行时间
msg.payload = {
    oee: ((ideal / actual) * 100).toFixed(1),
    line: msg.topic
};
return msg;
```

```
[Inject(每5分钟)] → [HTTP Request] → [MySQL]
      定时触发        调 MES API      写数据库
```

## 190. Home Assistant

**前世今生：** Home Assistant 由荷兰开发者 Paulus Schoutsen 于 2013 年创建，初衷是控制自己家的 Philips Hue 灯泡。Schoutsen 最初写了 200 行 Python 脚本，后来逐步扩展成完整的智能家居平台。2017 年获 Mozilla 资助成立独立公司 Nabu Casa，通过云服务订阅（$6.5/月）实现可持续开源模式。Home Assistant 的核心理念是"本地优先、隐私至上"——所有自动化逻辑在本地执行，数据不离开你的家。超过 2500 个集成（integrations）覆盖几乎所有智能家居协议和品牌。2024 年被 Linux 基金会接纳为官方项目。它不仅是智能家居系统，更是全球最大的开源自动化社区。

**使用方法与案例：**

安装（推荐 HAOS 或 Docker）：
```bash
docker run -d --name homeassistant \
  --privileged \
  -v /path/to/config:/config \
  -p 8123:8123 \
  ghcr.io/home-assistant/home-assistant:stable
```

**案例1：车间环境监控自动化**
```yaml
# configuration.yaml
sensor:
  - platform: modbus
    registers:
      - name: "车间温度"
        address: 100
        unit_of_measurement: "°C"

automation:
  - alias: "高温告警"
    trigger:
      - platform: numeric_state
        entity_id: sensor.车间温度
        above: 35
    action:
      - service: notify.feishu
        data:
          message: "⚠️ 车间温度过高: {{ states('sensor.车间温度') }}°C"
      - service: switch.turn_on
        target:
          entity_id: switch.排风扇
```

**案例2：办公室节能自动化**
```yaml
automation:
  - alias: "下班关灯关空调"
    trigger:
      - platform: time
        at: "18:00"
    condition:
```
