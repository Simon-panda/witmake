# 第9组：基础设施即代码

## 81. Terraform

**前世今生：** Terraform 由 HashiCorp 的 Mitchell Hashimoto 和 Armon Dadgar 于 2014 年创建。当时 AWS CloudFormation 已经存在但严重绑定 AWS，其他云也有各自的模板。Terraform 的创新是"HCL（HashiCorp Configuration Language）+ Provider 插件架构"——用一种语言管理所有云平台。`terraform plan` 让你在执行前预览变更，这是革命性的——终于不用在控制台点"OK"后祈祷了。Terraform 定义了 IaC（Infrastructure as Code）的范式。2023 年 HashiCorp 将 Terraform 从 MPL 改为 BSL（商业源代码许可），引发了 OpenTofu 分支。尽管如此，Terraform 仍然是使用最广的 IaC 工具，管理着全球数以百万计的云资源。

**使用方法与案例：**

安装：
```bash
brew install terraform             # macOS
winget install HashiCorp.Terraform # Windows
apt install terraform              # Linux
```

**案例1：部署一台云服务器**
```hcl
# main.tf
terraform {
  required_providers {
    aws = { source = "hashicorp/aws", version = "~> 5.0" }
  }
}

provider "aws" {
  region = "ap-northeast-1"
}

resource "aws_instance" "mes_server" {
  ami           = "ami-0d527b8c289b4"  # Ubuntu 22.04
  instance_type = "t3.medium"

  tags = {
    Name = "MES-Production"
    Env  = "prod"
  }
}

output "server_ip" {
  value = aws_instance.mes_server.public_ip
}
```
```bash
terraform init      # 下载 provider
terraform plan      # 预览变更
terraform apply     # 执行创建
# 输出: server_ip = "13.xxx.xxx.xxx"
```

**案例2：完整的 MES 基础设施**
```hcl
# VPC + 子网
resource "aws_vpc" "mes" {
  cidr_block = "10.0.0.0/16"
}

resource "aws_subnet" "mes_public" {
  vpc_id     = aws_vpc.mes.id
  cidr_block = "10.0.1.0/24"
}

# RDS PostgreSQL
resource "aws_db_instance" "mes_db" {
  engine         = "postgres"
  engine_version = "16"
  instance_class = "db.t3.medium"
  allocated_storage = 50
  username       = var.db_username
  password       = var.db_password  # 从变量传入（不写死）
  vpc_security_group_ids = [aws_security_group.mes_db.id]
}

# 安全组只允许 MES 服务器访问 DB
resource "aws_security_group" "mes_db" {
  vpc_id = aws_vpc.mes.id
  ingress {
    from_port       = 5432
    to_port         = 5432
    protocol        = "tcp"
    security_groups = [aws_security_group.mes_app.id]
  }
}
```

**案例3：管理状态与团队协作**
```bash
# 生产环境推荐远程状态（S3 + DynamoDB 锁）
terraform {
  backend "s3" {
    bucket         = "mes-terraform-state"
    key            = "prod/terraform.tfstate"
    region         = "ap-northeast-1"
    dynamodb_table = "terraform-locks"
  }
}
```
多人协作时，`terraform apply` 自动获取 DynamoDB 锁，防止并发修改冲突。

**进阶技巧：**
- `terraform import` 导入已有资源到 Terraform 管理
- `terraform state mv` 重构代码时移动资源（不解绑重新绑定）
- `terraform workspace` 多环境隔离（dev/staging/prod）
- `count` 和 `for_each` 批量创建相似资源

## 82. Pulumi

**前世今生：** Pulumi 由 Joe Duffy（前微软 Azure CTO 团队成员）和 Eric Rudder（前微软战略主管）于 2017 年创立。Duffy 在微软时深度参与了 C# 和 Azure，他观察到开发者不想学另一门 DSL（如 HCL），而是希望用自己熟悉的语言（Python、TypeScript、Go）写基础设施。Pulumi 的核心理念是"真正的编程语言写 IaC"——你可以用 for 循环、if 条件、import 库，而不是 HCL 受限的语法。Pulumi 像 Terraform 一样管理状态和依赖图，但用通用语言定义资源。2023 年 Pulumi 开源了其状态管理后端（Pulumi ESC）。

**使用方法与案例：**

安装：
```bash
brew install pulumi                # macOS
winget install Pulumi.Pulumi       # Windows
curl -fsSL https://get.pulumi.com | sh  # Linux
```

**案例1：用 Python 写云基础设施**
```python
import pulumi
import pulumi_aws as aws

# 创建安全组（用 Python 循环！）
ports = [22, 80, 443, 5432, 3000]
sg = aws.ec2.SecurityGroup("mes-sg",
    ingress=[
        aws.ec2.SecurityGroupIngressArgs(
            from_port=p, to_port=p,
            protocol="tcp",
            cidr_blocks=["10.0.0.0/8"]
        ) for p in ports  # ← Python 列表推导式
    ]
)

server = aws.ec2.Instance("mes-server",
    ami="ami-0d527b8c289b4",
    instance_type="t3.medium",
    vpc_security_group_ids=[sg.id],
    tags={"Name": "MES-Server", "Env": pulumi.get_stack()}
)

pulumi.export("server_ip", server.public_ip)
```
用 Python 写 IaC 的优势：IDE 自动补全、类型检查、可复用函数和类。

**案例2：多环境共享代码**
```python
# config.py
def get_instance_type(stack: str) -> str:
    return {"dev": "t3.small", "staging": "t3.medium", "prod": "t3.large"}[stack]
```
```bash
pulumi stack init dev
pulumi config set aws:region ap-northeast-1
pulumi up
```
同一个 Python 代码，不同 stack 不同配置。

**案例3：创建 Kubernetes 资源**
```python
import pulumi_kubernetes as k8s

app = k8s.apps.v1.Deployment("mes-api",
    spec=k8s.apps.v1.DeploymentSpecArgs(
        replicas=3,
        selector=k8s.meta.v1.LabelSelectorArgs(match_labels={"app": "mes"}),
        template=k8s.core.v1.PodTemplateSpecArgs(
            metadata=k8s.meta.v1.ObjectMetaArgs(labels={"app": "mes"}),
            spec=k8s.core.v1.PodSpecArgs(
                containers=[k8s.core.v1.ContainerArgs(
                    name="api",
                    image="ghcr.io/myorg/mes-api:v1.2.3",
                    ports=[k8s.core.v1.ContainerPortArgs(container_port=3000)],
                )]
            )
        )
    )
)
```

**进阶技巧：**
- `pulumi preview` 预览变更（对标 `terraform plan`）
- Automation API: 用 Pulumi SDK 在程序中编程管理基础设施（如 CI/CD 中动态创建环境）
- CrossGuard 策略引擎：定义合规规则（"不允许开放 0.0.0.0/0 的安全组"）
- 与 Terraform 互通：`tf2pulumi` 转换 HCL → Python/TS

## 83. Ansible

**前世今生：** Ansible 由 Michael DeHaan 于 2012 年创建。DeHaan 之前是 Red Hat 的 Cobbler（自动化安装）和 Func（多节点管理）的开发者。他观察到 Puppet 和 Chef 的问题：需要 agent、需要 Ruby 环境、学习曲线陡峭。Ansible 的激进创新是"无 agent"——仅需 SSH 和 Python，YAML 描述配置（"Playbook"），推送式执行。2015 年 Red Hat 收购 Ansible（约 1.5 亿美元），将其打造为企业级自动化平台（Ansible Tower/AWX）。Ansible 的核心哲学是"幂等性"——同一个 Playbook 可以多次运行，结果一致。

**使用方法与案例：**

安装：
```bash
pip install ansible                   # 跨平台
brew install ansible                  # macOS
apt install ansible                   # Linux
```

**案例1：批量初始化服务器**
```yaml
# playbooks/setup.yml
- hosts: mes_servers
  become: yes
  tasks:
    - name: Update packages
      apt:
        update_cache: yes
        upgrade: dist
      when: ansible_os_family == "Debian"

    - name: Install required packages
      apt:
        name:
          - docker.io
          - python3-pip
          - postgresql-client
          - htop
        state: present

    - name: Create app user
      user:
        name: mesapp
        shell: /bin/bash
        groups: docker

    - name: Deploy SSH key
      authorized_key:
        user: mesapp
        key: "{{ lookup('file', '~/.ssh/mes_deploy.pub') }}"
```
```bash
ansible-playbook -i inventory.ini playbooks/setup.yml
# 一键配置 10 台服务器
```

**案例2：部署应用**
```yaml
- hosts: mes_app
  tasks:
    - name: Pull latest Docker image
      docker_image:
        name: ghcr.io/myorg/mes-api
        tag: "{{ version }}"
        source: pull

    - name: Run container
      docker_container:
        name: mes-api
        image: ghcr.io/myorg/mes-api:{{ version }}
        ports:
          - "3000:3000"
        env:
          DB_HOST: "{{ db_host }}"
          DB_PASSWORD: "{{ db_password }}"
        restart_policy: always
```
```bash
ansible-playbook -i inventory.ini -e "version=v1.3.0 db_password=secret" deploy.yml
```

**案例3：Ansible Vault——加密敏感变量**
```bash
ansible-vault create secrets.yml
# 编辑并加密数据库密码、API 密钥等
ansible-playbook --ask-vault-pass deploy.yml
```
支持 AES256 加密，可以安全地存储在 Git 仓库中。

**进阶技巧：**
- `ansible.builtin.template` Jinja2 模板渲染配置文件
- `--check --diff` 演习模式 = 预览变更不执行
- `delegate_to` 把某个任务代理到特定节点（如数据库迁移只在 master 执行）
- Roles 目录结构组织大型 Playbook

## 84. Packer

**前世今生：** Packer 由 HashiCorp 的 Mitchell Hashimoto 于 2013 年创建。传统上构建虚拟机镜像（AMI、Docker image）是手工过程——启动实例、SSH 进去、装软件、关机、做镜像。Packer 用 JSON/HCL 描述这个过程，完全自动化。它的独特设计是"多构建器"——同一个配置文件可以生成 AWS AMI、Docker image、VMware VMDK、VirtualBox OVF 等多种格式。Packer 将"不可变基础设施"理念从代码推到镜像层——部署的不是一个空 VM 然后配环境，而是一个已经包含应用的镜像。

**使用方法与案例：**

安装：
```bash
brew install packer             # macOS
winget install HashiCorp.Packer # Windows
apt install packer              # Linux
```

**案例1：构建 MES API 的 AWS AMI**
```hcl
# mes-ami.pkr.hcl
source "amazon-ebs" "mes" {
  ami_name      = "mes-api-${formatdate("YYYY-MM-DD-hhmm", timestamp())}"
  instance_type = "t3.small"
  region        = "ap-northeast-1"
  source_ami_filter {
    filters = {
      name                = "ubuntu/images/*ubuntu-jammy-22.04-amd64-server-*"
      root-device-type    = "ebs"
      virtualization-type = "hvm"
    }
    most_recent = true
    owners      = ["099720109477"]
  }
  ssh_username = "ubuntu"
}

build {
  sources = ["source.amazon-ebs.mes"]
  
  provisioner "shell" {
    inline = [
      "sudo apt-get update",
      "sudo apt-get install -y docker.io python3-pip",
      "sudo systemctl enable docker",
    ]
  }
  
  provisioner "file" {
    source      = "./app/"
    destination = "/opt/mes/"
  }
  
  provisioner "shell" {
    inline = [
      "cd /opt/mes && docker build -t mes-api .",
    ]
  }
}
```
```bash
packer init . && packer build mes-ami.pkr.hcl
# 10 分钟后 → AWS 上有一个完整的已配好 Docker 和应用的 AMI
```

**案例2：同时构建 Docker 和 AMI**
```hcl
build {
  sources = [
    "source.amazon-ebs.mes",
    "source.docker.mes-docker"
  ]
  # 相同的 provisioner 适用于两个构建器
}
```

**进阶技巧：**
- `packer build -only=docker.mes-docker .` 只构建 Docker
- HCP Packer Registry 追踪镜像版本和依赖
- `post-processor "manifest"` 生成构建产物清单
- `--var-file=prod.pkrvars.hcl` 环境区分

## 85. Vagrant

**前世今生：** Vagrant 由 Mitchell Hashimoto 于 2010 年创建（也是他 2010 年的首个开源项目）。Hashimoto 当时是学生，发现每个项目设置开发环境极其痛苦——安装依赖、配置数据库、解决操作系统差异。Vagrant 用"Vagrantfile"（Ruby DSL）描述开发环境，底层调用 VirtualBox/VMware/Docker。`vagrant up` 一行启动一个与生产一致的 VM。Vagrant 定义了"开发环境即代码"的概念。虽然 Docker 后来在开发环境领域大幅蚕食了 Vagrant 的地盘，但 Vagrant 在需要完整 VM 场景（测试内核模块、多机集群模拟）中仍不可替代。

**使用方法与案例：**

安装：
```bash
brew install vagrant                # macOS
winget install HashiCorp.Vagrant    # Windows
apt install vagrant                 # Linux
# 还需要 VirtualBox 或 VMware
```

**案例1：一键启动开发环境**
```ruby
# Vagrantfile
Vagrant.configure("2") do |config|
  config.vm.box = "ubuntu/jammy64"
  config.vm.network "forwarded_port", guest: 3000, host: 3000
  config.vm.synced_folder "./app", "/opt/mes"
  
  config.vm.provision "shell", inline: <<-SHELL
    apt-get update
    apt-get install -y docker.io postgresql-client
    curl -fsSL https://deb.nodesource.com/setup_20.x | bash -
    apt-get install -y nodejs
  SHELL
  
  config.vm.provider "virtualbox" do |vb|
    vb.memory = "4096"
    vb.cpus = 2
  end
end
```
```bash
vagrant up        # 启动 VM
vagrant ssh       # 进入
vagrant halt      # 关机
vagrant destroy   # 删除
```

**案例2：模拟多机集群**
```ruby
Vagrant.configure("2") do |config|
  config.vm.box = "ubuntu/jammy64"
  
  (1..3).each do |i|
    config.vm.define "node-#{i}" do |node|
      node.vm.network "private_network", ip: "192.168.56.#{10+i}"
      node.vm.hostname = "node-#{i}"
    end
  end
end
```
在本地模拟三节点集群，用于测试 K8s 或分布式部署。

**案例3：快照与回滚**
```bash
vagrant snapshot save fresh_install
# 做危险操作...
vagrant snapshot restore fresh_install  # 秒级回滚
```

**进阶技巧：**
- Vagrant Cloud 托管 box 版本
- `vagrant up --provider=docker` 用容器替代 VM
- 使用 `.vagrantignore` 排除不需要同步到 VM 的文件
- Ansible/Chef/Puppet provisioner 替代 shell 脚本

## 86. Crossplane

**前世今生：** Crossplane 由 Upbound（创始人 Bassam Tabbara，前微软 Azure 架构师）于 2018 年创建，2020 年捐献给 CNCF。Crossplane 的理念是"用 K8s 控制平面管理所有基础设施"——定义一个 K8s CRD，Crossplane 负责在云上创建对应的资源。这与 Terraform 的根本不同：Terraform 是 push 模式（CLI 触发），Crossplane 是 reconcile 模式（控制器持续同步期望状态和实际状态）。Crossplane 让基础设施管理变成了 K8s 原生体验——用 `kubectl apply` 管理一切。

**使用方法与案例：**

安装：
```bash
helm repo add crossplane-stable https://charts.crossplane.io/stable
helm install crossplane crossplane-stable/crossplane --namespace crossplane-system --create-namespace
```

**案例1：声明式创建 RDS 数据库**
```yaml
apiVersion: rds.aws.upbound.io/v1beta1
kind: Instance
metadata:
  name: mes-production-db
spec:
  forProvider:
    allocatedStorage: 50
    engine: postgres
    engineVersion: "16"
    instanceClass: db.t3.medium
    region: ap-northeast-1
    masterUsername: admin
    passwordSecretRef:
      name: db-password
      key: password
```
```bash
kubectl apply -f db.yaml
# Crossplane 自动：创建 RDS → 创建子网组 → 创建安全组
```

**案例2：组合多个资源（Composite Resource）**
```yaml
apiVersion: apiextensions.crossplane.io/v1
kind: Composition
metadata:
  name: xmesenvironment.aws.mes.io
spec:
  compositeTypeRef:
    apiVersion: aws.mes.io/v1alpha1
    kind: XMESEnvironment
  resources:
    - name: vpc
      base:
        apiVersion: ec2.aws.upbound.io/v1beta1
        kind: VPC
        spec:
          forProvider:
            cidrBlock: "10.0.0.0/16"
    - name: database
      base:
        apiVersion: rds.aws.upbound.io/v1beta1
        kind: Instance
        spec:
          forProvider:
            engine: postgres
            instanceClass: db.t3.medium
```
定义一个 "MES 环境" 抽象，包含 VPC + RDS + EKS 等，用户只需申请一个 MES 环境而不需要知道底层细节。

**进阶技巧：**
- `kubectl get managed` 查看所有被 Crossplane 管理的云资源
- Provider 概念：AWS、GCP、Azure、阿里云都有对应 Provider
- `crossplane beta render` CLI 在本地预览（不实际创建）
- 搭配 Argo CD 实现 GitOps：Git 中改 YAML → Argo 同步 → Crossplane 调云 API

## 87. OpenTofu

**前世今生：** OpenTofu 是 Terraform 的社区分支，诞生于 2023 年 HashiCorp 将 Terraform 从 MPL 改为 BSL 许可之后。这一许可变更引发了 IaC 社区的剧烈反应，包括 Google、Microsoft、GitLab 等公司在内的 100+ 组织联合发布了 OpenTofu 宣言。OpenTofu 由 Linux 基金会托管，完全兼容 Terraform 1.5.x 的语法和 Provider，承诺永远使用 MPL 2.0 许可。2024 年 1 月发布 1.6.0 正式版。对于关心许可证风险的企业（尤其是云厂商和 SaaS 公司），OpenTofu 是最直接的 Terraform 替代。

**使用方法与案例：**

安装：
```bash
brew install opentofu             # macOS
# Linux/Windows: 下载 GitHub Releases 二进制
```

**案例：迁移 Terraform → OpenTofu**
```bash
# 1. 安装 OpenTofu CLI (tofu 命令)
# 2. 直接在现有 Terraform 目录中执行
cd my-terraform-project/
tofu init      # 与 terraform init 完全一样的效果
tofu plan      # 与 terraform plan 完全一样
tofu apply     # 与 terraform apply 完全一样
```
迁移成本几乎为零——所有 `.tf` 文件、state 文件、provider 都兼容。

**进阶技巧：**
- OpenTofu 在 Terraform 基础上增加了加密 state 文件和 Provider 函数
- 社区承诺保持与 Terraform 的向后兼容性
- `tofu test` 集成测试框架（Terraform 1.6+ 才有类似功能）
- 如果你的组织对 BSL 许可敏感，选择 OpenTofu

## 88. Chef

**前世今生：** Chef 由 Jesse Robbins（前 Amazon 工程师，被称为"混沌工程之父"）和 Adam Jacob 于 2009 年创立。Chef 受 Amazon 内部基础设施管理方式的启发，用 Ruby DSL 描述服务器配置（"Recipe"），遵循"收敛"模型——agent 定期从 Chef Server 拉取配置并强制执行。Chef 在 2010-2015 年是配置管理的王者，客户包括 Facebook、Etsy。但随着 Ansible（无 agent）和容器化（Docker/K8s）的兴起，Chef 这种重量级 agent 模式逐渐失宠。2021 年 Chef 被 Progress Software 收购，后续创新放缓。今天 Chef 主要用于合规自动化（InSpec 扫描工具），配置管理领域已被 Ansible 超越。

**使用方法与案例（简要，非推荐新项目使用）：**

```ruby
# recipes/default.rb
package 'docker.io'
service 'docker' do
  action [:enable, :start]
end

docker_image 'mes-api' do
  repo 'ghcr.io/myorg/mes-api'
  tag 'v1.3.0'
end
```
```bash
knife bootstrap 192.168.1.10 -x ubuntu -r 'recipe[mes]'
```

## 89. SaltStack

**前世今生：** SaltStack（简称 Salt）由 Thomas S. Hatch 于 2011 年创建。Hatch 想要一个比 Puppet/Chef 更快的配置管理系统，于是用 Python 和 ZeroMQ 编写了 Salt。Salt 的架构是 master-minion 模式，minion 运行在每台机器上，master 通过加密的 ZeroMQ 通道下发命令。Salt 的杀手级功能是"远程执行"——`salt '*' cmd.run 'uptime'` 像在一台机器上执行命令一样方便。2018 年 SaltStack 被 VMware 收购。虽然 Ansible 更流行，但 Salt 在大规模场景（数千台机器）仍然有性能优势。

**使用方法与案例（简要）：**

```yaml
# /srv/salt/mes/init.sls
docker:
  pkg.installed

mes-api:
  docker_container.running:
    - image: ghcr.io/myorg/mes-api:v1.3.0
    - port_bindings:
      - 3000:3000
```
```bash
salt 'mes-*' state.apply mes
```

## 90. NixOS

**前世今生：** NixOS 由 Eelco Dolstra 于 2003 年在乌得勒支大学的博士研究中提出，其核心论文《The Purely Functional Software Deployment Model》至今仍在影响整个行业。Dolstra 发现传统包管理的"依赖地狱"源于可变的状态——升级一个库可能破坏依赖它的软件。NixOS 的解决方案是"函数式"：每个包安装到唯一的哈希路径（如 `/nix/store/abc123-firefox-121.0/`），永远不会冲突。整个系统配置在一个 `configuration.nix` 文件中声明，升级是原子操作，可随时回滚。NixOS 的"可复现性"理念后来启发了 Docker、Flatpak、Guix 等众多项目。2023 年 Nix 生态爆发，devenv/devbox/flox 等工具让开发者无需全面接受 NixOS 也能享受 Nix 的好处。

**使用方法与案例：**

安装：下载 NixOS ISO 安装，或先装 Nix 包管理器（可运行在 macOS/任何 Linux 上）：
```bash
sh <(curl -L https://nixos.org/nix/install)
```

**案例1：声明式系统配置**
```nix
# /etc/nixos/configuration.nix
{ config, pkgs, ... }:
{
  # 系统包
  environment.systemPackages = with pkgs; [
    docker
    postgresql
    python3
    ripgrep
    lazygit
  ];

  # 服务
  services.postgresql = {
    enable = true;
    package = pkgs.postgresql_16;
  };
  services.nginx = {
    enable = true;
    virtualHosts."mes.internal" = {
      root = "/var/www/mes";
    };
  };

  virtualisation.docker.enable = true;
}
```
```bash
nixos-rebuild switch   # 原子升级
# 如果出问题:
nixos-rebuild switch --rollback  # 秒级回滚到上一个配置
```

**案例2：开发环境（nix-shell）**
```bash
# shell.nix
{ pkgs ? import <nixpkgs> {} }:
pkgs.mkShell {
  buildInputs = with pkgs; [
    python311
    python311Packages.pandas
    postgresql
    nodejs_20
  ];
}
```
```bash
nix-shell  # 进入隔离环境，退出后完全不污染系统
```

**案例3：项目依赖锁（flake.nix）**
```nix
{
  inputs.nixpkgs.url = "github:NixOS/nixpkgs/nixos-24.05";
  outputs = { self, nixpkgs }: {
    devShells.x86_64-linux.default = nixpkgs.legacyPackages.x86_64-linux.mkShell {
      packages = with nixpkgs.legacyPackages.x86_64-linux; [
        python311 nodejs_20
      ];
    };
  };
}
```
`flake.lock` 锁定所有依赖版本，团队成员 `nix develop` 获得完全一致的环境。

**进阶技巧：**
- `nix-store --gc` 垃圾回收（删除无引用的旧版本）
- 用 Nix 构建 Docker 镜像：体积更小、更安全（无 bash、无多余包）
- `nixpkgs` 仓库有 8 万+ 包，是最大的 Linux 包仓库
- `home-manager` 用同样的声明式方法管理用户级配置（.bashrc、neovim 配置等）
