# 《深入理解AI Agent》术语词典

> 72 个术语，按主题分组。每个术语含作者定义、关键区分、为什么重要。
> 来源：cangjie 蒸馏流水线阶段 1 术语提取，2026-07-31。


## 一、核心概念（第 1 章）

### Agent 核心公式（Agent = LLM + 上下文 + 工具）

- **来源**：第1章 1.1 / 引言
- **作者定义**："LLM 是Agent 的大脑（决策内核），上下文是Agent 的眼睛（每个决策点能看到的全部信息），工具是Agent 的手脚（能做的所有事情的集合）。"
- **关键区分**：每个词都要广义理解:LLM不只参数,是整个决策内核;上下文不只输入文本,是决策点全部可见信息;工具不只API,含Skills/代码生成/子Agent/事件触发。
对应RL三概念:策略(Policy)/观察空间/动作空间。
生产形态扩展:Agent = Model + Harness = LLM + [上下文+工具+约束+验证+纠正]。
- **为什么重要**：全书总纲;判断"Agent缺什么"的第一张检查表(大脑/眼睛/手脚哪个短板)。

### Harness / Harness 工程

- **来源**：第1章 1.2
- **作者定义**："Harness 原指马具——不是为了限制马的奔跑能力，而是把这种力量引导到正确的方向上。……模型是那匹强大但不可预测的马，Harness 则是把它的能力引导成可靠任务执行的工程外壳。"
- **关键区分**：核心=上下文+工具,再加三层保障:约束(能做什么不能做什么)/验证(做得对不对)/纠正(做错了怎么补救);
生产级Agent系统Harness绝大部分代码在做约束/验证/纠正而非上下文与工具本身(Claude Code为例);
"模型还做不稳的,Harness先补上;模型每内化一层,Harness就卸下一层,转而兜底新的能力前沿"。
- **为什么重要**：企业自建Agent的竞争力所在——模型可以买,Harness必须自己建;
我们的skill体系/memory/cron审批门控就是Harness的一部分。

### ReAct 循环与轨迹（Trajectory）

- **来源**：第1章 1.1.5
- **作者定义**："模型先思考当前应该做什么，然后调用工具行动，再观察工具返回的结果并继续思考下一步。这个'想→做→看→想→做→看'的循环不断重复，直到任务完成。……Agent 的上下文 = 静态前缀 + 轨迹。"
- **关键区分**：轨迹=用户消息+模型回复(思考+工具调用)+工具执行结果的完整序列,append-only;
轨迹即Agent的全部状态(第10章:崩溃后加载轨迹即可恢复会话);
轨迹可分析/可沉淀知识/可训练模型——从经验学习的闭环原料。
- **为什么重要**：理解一切Agent运行/调试/审计/进化的基础单位;
我们的会话记录+session_search正是轨迹管理的实例。

### 编排光谱（工作流 ↔ 自主 Agent）

- **来源**：第1章 1.2.5
- **作者定义**："首先考虑单个LLM 调用……当需要多步骤处理时，对于可以清晰分解为固定子任务的场景，考虑使用工作流；只有当需要动态决策和灵活的执行路径时，才使用自主Agent。"
- **关键区分**：工作流:执行路径代码写死,严格流程控制+安全(攻击面限单节点),但缺变通;
自主Agent:路径由Agent按环境反馈实时决定,适用开放式问题,但成本更高+复合错误风险;
实践多混合:关键合规流程用工作流,灵活部分切自主。
- **为什么重要**：企业Agent落地的顺序决策框架——先提示词,再工作流,最后自主Agent;
智机数智化"先做哪个"的答案光谱。

### 护栏三层防线（输入侧/执行侧/输出侧）

- **来源**：第1章 1.2.6
- **作者定义**："单个护栏不太可能提供足够的保护，但将多个专门的护栏组合使用，就能构建出更有韧性的Agent 系统。"
- **关键区分**：输入侧:相关性分类器/安全分类器(区分越狱=用户主动绕过 vs 提示注入=外部数据间接操纵)/内容审核/规则保护;
执行侧:工具风险评级(可逆性/权限/财务影响→低中高,高风险额外审查或人工确认);
输出侧:PII过滤/输出验证;
人工干预两触发:超过失败阈值/高风险不可逆操作。
- **为什么重要**：Agent上线前的安全检查清单骨架;
我们的生产指令未确认不执行=执行侧护栏的实例。

### 防呆设计（Poka-yoke）在 ACI 中的应用

- **来源**：第1章 1.2.3
- **作者定义**："工具的命名和参数要直观，容易误用的地方要从设计上让错误无法发生——比如SIM 卡的缺角让卡片只能从一个方向插进卡槽……微波炉门没关好就绝不加热。这种'用设计消除错误'的思路，在制造业里有一个专门的术语，叫防呆（Poka-yoke），源自丰田生产体系。"
- **关键区分**：不是"出错后提醒",而是"让错误无法发生";
模型与工具之间唯一沟通通道是接口本身——模糊接口会被模型放大成系统性错误。
- **为什么重要**：丰田生产体系概念反向输入AI工程——制造业读者最亲切的一座桥;
我们设计Agent工具/表单/流程时直接可用的原则。

### 模型即Agent（Model as Agent）

- **来源**：第1章 1.1.3.1
- **作者定义**："先进模型通过后训练（特别是强化学习）将工具调用能力内化为原生能力：何时调用工具、调哪个、传什么参数，都由模型自己决定，无需人工编排。但这并不意味着框架层变得不重要了——恰恰相反，模型越强大，围绕模型构建的Harness 就越关键。"
- **关键区分**：被内化的是"用不用、怎么用"的决策策略;工具执行仍在模型之外的基础设施;
编排循环没有消失,而是从客户端移到服务端,决策权交给模型;
模型厂商优势=模型与Harness协同优化持续迭代。
- **为什么重要**：理解Kimi K3/GPT-5.6等新一代模型的能力边界;
"模型会不会吃掉Harness"之争的完整答案在后记。


## 二、上下文工程（第 2 章）

### KV Cache / Prompt Cache（两个层级的缓存）

- **来源**：第2章 2.3 / 2.3.3
- **作者定义**："KV Cache 是模型内部的优化——在一次推理过程中，缓存已计算的token 的键值对。Prompt Cache 则是API 服务层的优化——跨多次API 请求之间，缓存相同前缀的计算结果。"
- **关键区分**：共同约束:前缀完全不变,改一个字符缓存全废(逐层传导,所有层重算);
Prompt Cache经济影响更大(直接影响API计费,缓存读取约为首次计算的1/10);
动态信息追加末尾不破坏缓存(因果注意力:新token只依赖之前的token)。
- **为什么重要**：Agent成本工程的第一课:系统提示词/工具定义一旦确定就不要改;
时间戳/用户状态等动态内容永远作为新消息追加到末尾。

### 上下文腐化（Context Rot）

- **来源**：第2章 2.7.2
- **作者定义**："明明上下文窗口还远没有满，但Agent 突然找不到关键信息了，或者反复纠结于一个早已解决的问题。……溢出是'装不下了'，腐化是'装得下但找不到了'。"
- **关键区分**：≠上下文溢出(窗口用完);腐化更隐蔽——表面正常工作,决策质量悄然下降;
根因:注意力权重被分散+无关内容占大头+位置偏好(开头结尾注意力高,中间被忽视);
最常见失效模式不是窗口不够长,而是信息密度不对。
- **为什么重要**：长任务Agent质量退化的首要嫌疑;
对策:压缩/状态栏/子Agent隔离——主动提炼而非被动检索。

### Agent 状态栏（Agent Status Bar）/ 上下文蒸馏

- **来源**：第2章 2.6
- **作者定义**："Agent 框架在上下文末尾持续注入的状态摘要——'你已经打了3 次电话'、'当前时间是10:30'、'TODO 还剩2 项未完成'。模型每次生成新回复时都能'瞥一眼'这些状态。……把分散在上下文各处的隐式状态提炼为可直接使用的显式知识。"
- **关键区分**：原理:上下文学习更像检索而非推理——模型擅长查找不擅长主动归纳统计;
统一名称"上下文蒸馏(Context Distillation)",状态栏是其最日常形态;
三条纪律:用代码维护别用LLM批量统计/维度覆盖不足时是"假权威"/准确率当一线生产指标盯;
有价值的信息是模型自己想不出来的外部观测,不是它本可扫出来的东西。
- **为什么重要**：我们Hermes的todo工具/状态注入正是此机制实例;
智机Agent上线必配的低成本高回报组件。

### 渐进式披露（Progressive Disclosure）/ Agent Skills

- **来源**：第2章 2.5
- **作者定义**："先给Agent 看一份目录摘要，需要时再加载完整内容，就像你不会把公司所有部门的操作手册都堆到新员工桌上，而是先给一份总目录，需要哪本再去取。"
- **关键区分**：三层:元数据(name+description,数百token,启动时注入)→SKILL.md核心流程(选中后加载)→子文档/脚本(按需深入);
description写法要像路由条件而非功能介绍——"Use when/Don't use when"+反例,缺反例路由准确率明显下降;
Skill本质是"把外部内容当作指令加载"的制度化形式——第三方Skill必须审查内容如同审查代码。
- **为什么重要**：我们正在用的技能体系的理论基础;
写skill的description时按路由条件写(何时该用我>我能做什么)。

### Chat Template（聊天模板）

- **来源**：第2章 2.3.1
- **作者定义**："API 层面的结构化消息需要被转换为模型能理解的线性token 流——负责这个转换的就是Chat Template。……不同模型家族使用不同的'信封格式'。"
- **关键区分**：必须用标准API格式,不要自行拼接消息("USER:...ASSISTANT:...")——偏离训练格式会削弱多步思考能力;
工具结果错标为user消息→误触发思维链清理("算到一半草稿纸被收走");
行业从"剥离历史思考"(DeepSeek R1)反转到"强制回传reasoning_content"(V4/Kimi K2/GLM-5):对Agent场景,思考不是废料,而是状态。
- **为什么重要**：排查Agent行为异常时的底层检查项:消息角色对不对、模板协议匹配不匹配。

### 提示注入（Prompt Injection）直接与间接

- **来源**：第2章 2.4.7
- **作者定义**："攻击者通过Agent 处理的外部内容（网页、邮件、文档等），将伪装成系统指令的文本混入上下文，从而劫持Agent 的行为。……越狱是用户自己试图绕过模型的安全限制，提示注入则是攻击者通过外部数据间接操纵模型行为。"
- **关键区分**：Agent中比聊天机器人更危险——有工具调用能力,可执行不可逆操作;
每个感知工具都是注入入口(网页不可见元素/PDF元数据/图片EXIF);
上下文层防御(来源标记/角色分离/输入清洗)只是第一道防线,无法万无一失——需执行层权限控制+独立审查兜底。
- **为什么重要**：我们禁止未确认生产指令的执行=注入防御链的最后一环;
任何读外部内容的Agent功能(网页总结/邮件处理)默认当不可信输入处理。

### 时间感三轴（紧迫度/坚持度/警觉度）

- **来源**：第2章 2.6.5
- **作者定义**："紧迫度（urgency）——预算轴：把投入的力气匹配到时钟上。坚持度（persistence）——终点轴：分清真墙和假墙，也知道活儿到底干完了没有。警觉度（vigilance）——监控轴：把工具响应上的时间异常升级成一个值得追查的假设。"
- **关键区分**："三分钟写一段话"和"三十分钟写一段话"的产出应该不同,但当前Agent无论给多少预算产出几乎没区别;
失败两个方向:对真墙反复撞(410 Gone接口重试5次)/在假墙前过早收手(搜2次就断言"查无此信息");
读数必须配操作手册才改变行为。
- **为什么重要**：Agent工作节奏管理的三把尺子;
我们的cron任务/超时设置/重试策略可按这三轴审视。

### 隔离优于压缩（子 Agent 上下文隔离）

- **来源**：第2章 2.7.7
- **作者定义**："让大体积的中间信息根本不进入主上下文。……主上下文只增加两条消息：一条任务描述，一条结论——中间过程的数万token 随子Agent 的上下文一起被丢弃。"
- **关键区分**：压缩=有损的事后补救(还需额外LLM调用);隔离=噪声从一开始就与主上下文绝缘,主Agent的KV Cache前缀完全不受影响;
代价:子Agent看不到主Agent完整上下文,任务描述必须自包含;
Claude Code的Task工具、Deep Research的检索子Agent都是生产实现。
- **为什么重要**：我们delegate_task的设计正是此模式;
何时用:产生海量中间内容的任务(大范围搜索/读大量文件)一律委派,结论回传。


## 三、记忆与知识库（第 3 章）

### 用户记忆（User Memory）

- **来源**：第3章 3.1 用户记忆系统
- **作者定义**："一个主动的、持续的学习过程，其目标是构建一个关于用户的简洁而有效的预测模型。"
- **关键区分**：≠ 记录用户说过的每句话——只选择性保留对未来有用的事实;
≠ 上下文学习——用户记忆是持久的、可审查的,上下文学习临时、会话结束即消失。
= 投入额外算力做显式提取和压缩,形成可预测需求的用户模型。
- **为什么重要**：企业做"员工/客户数字画像"时,若按"完整记录"理解会做成流水账;
按作者定义应做成"选择性+抽象化+结构化"的预测模型。

### 轨迹（Trajectory）

- **来源**：第3章 3.1.2 记忆的层次结构
- **作者定义**："一次Agent 运行过程中的完整历史记录……按时间顺序排列，只增不改（append-only）。"
- **关键区分**：≠ 用户长期记忆——轨迹是单次会话流水账,长期记忆是跨会话提炼的档案;
≠ 工作记忆——轨迹是不可变完整序列,工作记忆是经筛选激活的动态子集。
- **为什么重要**：第8章持续进化、第10章多Agent状态恢复都建立在"轨迹即全部状态"上;
理解为"日志"会漏掉它作为恢复点和学习信号源的作用。

### 智能体化RAG（Agentic RAG）

- **来源**：第3章 3.3.4
- **作者定义**："知识库检索不再是自动化的前置步骤，而是被封装成一个可供Agent 随时调用的工具。Agent 采用ReAct 模式，通过'思考→行动→观察'的循环主导整个过程。"
- **关键区分**：≠ 传统RAG(固定"检索-生成"单向管道)——检索由Agent按需要自主决定何时检索、检索什么、是否继续。
= 从"被动管道"到"主动探索者"的范式转变。
- **为什么重要**：企业知识库问答若做成固定管道,复杂多跳问题必然翻车;
这是判断"我们的知识库够不够智能"的分水岭概念。

### 上下文感知检索（Contextual Retrieval）

- **来源**：第3章 3.3.5（Anthropic 提出）
- **作者定义**："在对文本块进行向量化索引之前，先利用LLM 为其生成一段简短的、包含核心上下文的'前缀摘要'，然后将前缀与原始文本块拼接后再索引。"
- **关键区分**：≠ 第2章"上下文感知压缩"——本节发生在索引期做加法(补前缀),
压缩发生在运行期做减法(裁无关)。
= 给每个文本块一张"身份标签",锚定其原始语义环境。
- **为什么重要**：两个名字相近的概念极易混淆,作用和时机完全相反;
这是Anthropic实测失败率↓49%-67%的高回报工程手段,企业知识库可直接采用。

### 双层记忆架构

- **来源**：第3章 3.3.5 / 3.4 本章小结
- **作者定义**："Advanced JSON Cards 常驻上下文提供'概览'，上下文感知检索按需提供'细节'，二者叠加。"
- **关键区分**：≠ 单一技术产物——是结构化知识管理(概览)与非结构化精准检索(细节)的协同;
= 第三层"主动服务"能力的具体实现路径。
- **为什么重要**：企业驾驶舱设计同构:KPI卡片常驻+明细按需钻取;
是"记忆系统怎么才算建成"的验收标准。

### 混合检索（Hybrid Search）

- **来源**：第3章 3.2.4
- **作者定义**："两个引擎都跑，结果合并——并行检索(稠密+稀疏)→结果融合(RRF)→神经重排序。"
- **关键区分**：稠密=语义相近向量距离近(懂同义词,漏关键词);
稀疏=BM25精确关键词匹配(懂代码/人名,不懂同义词);
重排序=跨编码器精排(面试官深谈),检索=双编码器初筛(猎头筛简历)。
- **为什么重要**："为什么搜编码找不到/搜同义词找不到"的诊断框架;
生产级RAG标配,没有单一策略全场景可靠。

### RAPTOR / GraphRAG（结构化索引两路线）

- **来源**：第3章 3.3.1
- **作者定义**："RAPTOR 采用自下而上的递归抽象……GraphRAG 将文档知识建模为由实体和关系构成的知识图谱。"
- **关键区分**：RAPTOR=树状层次摘要,适合"从概念钻进细节";
GraphRAG=实体关系网,适合"A和B什么关系"的多跳查询与实体消歧;
二者互补,生产场景组合使用优于单选。
- **为什么重要**：知识库升级时的选型词汇表;也划清了各自的能力边界。

### 三元组（Triple）与语义降级

- **来源**：第3章 3.3.1（GraphRAG 局限）
- **作者定义**："三元组用'主语-关系-宾语'的形式表达一条知识……将自然语言转为三元组不可避免地导致语义降级。"
- **关键区分**：词义消歧(bank=河岸/银行,靠上下文嵌入)≠实体消歧(两个"张医生",靠图关系边);
条件逻辑和时间依赖在三元组中丢失。
- **为什么重要**：防止把知识图谱当万能存储:核心信息仍以完整自然语言保存,图谱只作专项索引。

### 四种记忆格式（Simple/Enhanced/JSON Cards/Advanced JSON Cards）

- **来源**：第3章 3.1.3
- **作者定义**："四种渐进式的存储格式，代表了记忆粒度和结构复杂度的递进……根本张力：简单性与表达力之间的权衡。"
- **关键区分**：按"关键度×数量"分桶选型,生产系统混合使用;
Advanced JSON Cards靠backstory/person/relationship字段解决多身份消歧("张医生"是谁的医生)。
- **为什么重要**：设计任何档案/记忆系统的选型词汇表;
直接可用于企业员工画像、客户档案的格式决策。

### 记忆能力三层次（基础回忆/多会话检索/主动服务）

- **来源**：第3章 3.1.1
- **作者定义**："第一层基础回忆(准确存取);第二层多会话检索(跨对象跨时期关联推理);第三层主动服务(无明确指令下的预见性帮助)。"
- **关键区分**：作者自述是"笔者归纳口径,而非某一基准的原始分类"——评估框架,不是学术标准;
第三层是"助理级别最高标准的试金石"。
- **为什么重要**：验收任何"记忆/画像/知识库"系统的递进制标尺;
企业Agent从"答得对"到"主动提醒"的成熟度模型。


## 四、工具与安全（第 4-5 章）

### MCP（Model Context Protocol）

- **来源**：第4章 4.3 工具生态
- **作者定义**："Anthropic 于2024 年底发布的开放标准，旨在统一AI 模型与外部工具、数据源之间的通信协议——相当于为AI 工具生态制定一个通用的'插座标准'。"
- **关键区分**：客户端-服务器架构;三类原语=工具(可执行操作)/资源(只读数据)/提示模板(用户可选用);
解决互操作("一次开发,处处可用"),不解决工具过多的选择过载(那是Skills的事);
协议本身是请求-响应式,事件驱动需在协议之上另行构建。
- **为什么重要**：企业接入MES/ERP/设备数据时的协议选型基准;
接入第三方MCP=引入新信任边界,需配套审查。

### ACI（Agent-Computer Interface）

- **来源**：第4章 4.2.6 工具设计的演进
- **作者定义**："工具应该对应Agent 的目标而非底层的API 操作……如果说HCI 研究的是人如何与计算机交互，ACI 研究的就是Agent 如何与计算机交互，核心是让工具对Agent 而非对人友好。"
- **关键区分**：≠ API封装思维(一端点一工具,粒度过细);
= 面向Agent目标的接口设计,含粒度/通用性/描述/保真四原则。
- **为什么重要**：评审任何工具/MCP服务器设计的标尺;
把"给人用的系统"改造成"给Agent用的系统"时的指导思想。

### 提议者-审核者（Proposer-Reviewer）

- **来源**：引言；第4章 4.5
- **作者定义**："一个模型负责提议行动（Proposer），另一个独立的模型负责审查批准（Reviewer）——用独立的第二视角检验第一视角的产出。"
- **关键区分**：两种形态:事前审批(操作前双签)与事后验证(操作后模态切换检验);
与Sidecar的分工:审开放式思考(需能力相近模型)vs审结构化调用(轻量模型即可)。
- **为什么重要**：高风险操作(付款/生产指令/对外发信)的标配审查范式;
治"过早声明完成"和单模型盲区。

### Sidecar（边车机制）

- **来源**：第4章 4.5
- **作者定义**："伴随主Agent 思考循环运行的轻量级LLM 调用模式，它不审查主Agent 的最终输出，而是对主Agent 的行为做独立判断……对被审查的那次工具调用而言，Sidecar 起门控作用。"
- **关键区分**：借鉴微服务边车模式;只看结构化工具调用数据,刻意隔离主模型自由文本(防话术操纵);
"并行"省的是审查排队时间,不是取消审查闸门。
- **为什么重要**：实时安全校验的架构模式,亚秒级不拖慢主流程;
企业Agent执行机床/付款指令时的旁路护栏参考。

### 幂等性（Idempotency）

- **来源**：第4章 4.5（幂等性与取消语义）
- **作者定义**："同一个操作执行一次和执行多次，对外部世界的影响完全相同，因而可以安全重试。"
- **关键区分**：可幂等:唯一标识去重/先查询后变更;
不可幂等(发邮件/转账/打电话):"预检-确认"两段式,失败不就地盲目重发。
- **为什么重要**：异步架构下打断/超时是常态,幂等性是重试安全的前提;
设计任何"写"类工具时的必答题。

### 事件驱动异步 Agent / 事件流

- **来源**：第4章 4.7
- **作者定义**："所有的输入、输出、思考过程和外部交互都被统一建模为事件流——一条时间线上依次排列的事件记录。"
- **关键区分**：≠轮询(主动反复检查,低效);=新消息到达时自动触发处理逻辑;
事件只在事件循环的安全点被消费;结构化事件四维=来源/渠道/内容/上下文。
- **为什么重要**：从"被动问答"到"主动服务"的架构分水岭;
车间设备告警→Agent主动行动的基础架构。

### 主动工具发现（Active Tool Discovery）

- **来源**：第4章 4.8
- **作者定义**："让Agent 从被动接受者变为主动发现者：在执行过程中意识到能力缺口时，主动用自然语言声明'我需要什么能力'，系统再动态匹配并注入。"
- **关键区分**：≠全量注入(上下文塞满)/检索预筛(按初始查询一次性匹配,无法预见多步骤需求);
="Agent声明缺口、系统按需注入",工具schema追加到上下文末尾保KV Cache。
- **为什么重要**：企业系统工具集(MES/ERP/SCADA/文档系统)上百个时的必备机制。

### 工具遮蔽（Tool Shadowing）

- **来源**：第4章 4.3（MCP 的信任模型与安全风险）
- **作者定义**："当多个服务器提供同名或高度相似的工具时，恶意服务器可以'遮蔽'正规工具，诱导Agent 把本应发给可信服务器的调用（连同其中的敏感参数）路由到攻击者手中。"
- **关键区分**：与工具描述投毒(夹带指令)不同:遮蔽是命名空间劫持;
供应链安全范畴,接入前审查+锁定版本+最小权限缓解。
- **为什么重要**：接入多源MCP服务器时的命名冲突与劫持风险意识。

### 沙盒层级（OS级/容器/microVM）

- **来源**：第4章 4.5（执行环境的隔离与沙盒）
- **作者定义**："OS 级隔离(Seatbelt/seccomp/namespaces)→容器隔离(Docker,共享内核)→microVM(Firecracker独立内核,运行完全不可信代码的最强层级)。"
- **关键区分**：Python venv不是沙盒——只隔离包依赖,对文件系统/网络/进程无任何安全约束;
任一隔离层之上都应设资源配额(CPU/内存/磁盘/网络)。
- **为什么重要**："代码在沙盒里跑"这句话的技术验收标准;
避免把venv当安全边界的常见误解。

### 虚拟身份与隔离执行环境

- **来源**：第4章 4.7.5
- **作者定义**："赋予Agent 一套独立的虚拟身份——如同秘书拥有自己的办公电话和邮箱。这套虚拟身份包括专属的通讯账号、存储空间、计算环境，使Agent 能以透明的身份代表用户工作。"
- **关键区分**：≠直接管理用户个人账号(出错或被攻破则全部数字身份暴露);
沙盒隔离的是代码执行,虚拟电脑/手机隔离的是整个数字身份;
须以用户本人身份登录时:Human-in-the-Loop认证(VNC/RDP用户亲自登录,令牌复用)。
- **为什么重要**：企业Agent对外行动(发邮件/填报/客户沟通)时的身份基础设施设计参考。

### 元能力（meta-capability）

- **来源**：第5章 5.2 代码：通用Agent 的元能力
- **作者定义**："一种'能创造其他能力'的能力：Agent 用它当场写出新工具、新约束、新表达形式来完成任务，而不必事先把所有能力都预制好。"
- **关键区分**：普通能力=做某件具体的事;元能力=创造新能力本身;
代码是元能力:精确、可执行、可组合——产出新工具(脚本)/新约束(断言校验)/新表达形态(HTML/PPT)。
- **为什么重要**：理解"为什么给Agent代码执行能力比给100个专用工具更值"的理论根基;
企业Agent能力规划的分水岭:预制能力 vs 元能力。

### 致命三要素（+ 第四要素：持久记忆）

- **来源**：第5章 5.1.4（Simon Willison 提出，作者补充第四要素）
- **作者定义**："访问私有数据、暴露于不受信任内容、具备外部通信能力——三个要素齐备，就构成了一条完整的攻击闭环，系统即属高危。"
- **关键区分**：三要素齐备本身就足够危险,不需额外条件;
持久记忆不是并列第四要素,而是放大器:恶意指令写入长期记忆,跨会话潜伏择机触发。
- **为什么重要**：评估任何Agent部署风险的速查框架:三个要素逐项核对是否齐备;
企业Agent接入邮件/网页(不可信内容)+数据库(私有数据)+对外工具(通信)时必然三要素齐备,必须配套防御。

### 死亡螺旋（death spiral）

- **来源**：第5章 5.1.7
- **作者定义**："错误路径上触发的逻辑自身又调用LLM，再次出错，连锁触发。"
- **关键区分**：≠死循环(反复相同操作无进展)——死亡螺旋是恢复机制本身成为故障源,更隐蔽;
防护:错误路径禁用会再调模型的副作用+递归深度计数器。
- **为什么重要**：设计任何"自动恢复/自动钩子"机制时必须自问:这个恢复逻辑本身失败了会怎样。

### 熔断器（circuit breaker）

- **来源**：第5章 5.1.7（终止）
- **作者定义**："每条恢复路径都必须有明确的熔断上限：上下文压缩连续失败若干次就放弃压缩，权限分类连续失败就回退到人工询问。"
- **关键区分**：阈值来自产线数据统计(经验拐点),不是拍脑袋;
与全局终止条件(最大迭代/预算上限/人工升级)分层配合。
- **为什么重要**：任何重试/恢复机制的生产级标配;Cron任务和自动化脚本的参数设计依据。

### Artifact 模式

- **来源**：第5章 5.2.5（生成SQL 查询）
- **作者定义**："Agent 不自己读数据，而是生成一段SQL 查询代码，把这段代码作为一个独立的可执行产物（artifact）交给系统。系统拿着这段SQL 直接去数据库查询，把查到的数据渲染成用户能看到的表格。"
- **关键区分**：≠Agent读数据再复述(token贵/慢/抄写易出错);
=数据从数据库直达用户界面,LLM只生成代码不参与数据传递。
- **为什么重要**：大数据量查询场景的标准答案;
我们做报表/数据分析Agent时必须采用的分工模式。

### 自举（bootstrapping）

- **来源**：第5章 5.2.6 代码创造代码：Agent 自举
- **作者定义**："Coding Agent 如何用代码修复和创建与自己同类的Agent——自我修复、自我复制、按需生成新Agent。"
- **关键区分**：与第8章持续进化的分工:自举讲"怎样写出这些代码"(构造能力),
持续进化讲"什么证据触发自我修改+如何验证发布回滚"(治理机制);
最优路径=复制范例+定向修改(继承最佳实践),不从零生成。
- **为什么重要**：企业多Agent量产的方法论词汇:母版Agent+域化复制。

### 项目指令文件（CLAUDE.md / AGENTS.md / SOUL.md）

- **来源**：第5章 5.1.5（项目文档化）
- **作者定义**："在每次会话开始时被自动注入上下文，相当于项目级的系统提示词……承载面向Agent 的行为约定：构建与测试命令、代码风格、明确的禁区。"
- **关键区分**：≠README(面向人类读者);指令文件面向Agent:约定"在这个项目里该怎么干活";
SOUL.md约定"Agent是谁";内容不随任务变化,天然KV Cache友好的稳定前缀。
- **为什么重要**："知识必须存在于代码库本身"原则最直接的落地形态;
企业各系统接入Agent时的标准配置件。

### reward hacking（奖励黑客/破坏性捷径）

- **来源**：第5章 5.1.6（约束的另一层目的）
- **作者定义**："即使把限制写进最终评估指标，Agent 也常能找到绕过去的办法。"
- **关键区分**：结果指标达成但方式不可接受(删库重建修故障);
对策:约束动作而非仅结果(Harness)+过程惩罚(RLVP,训练侧)。
- **为什么重要**：设计任何KPI/奖励机制时的警示词:指标会受骗,要同时管过程。


## 五、评估（第 6 章）

### LLM-as-a-Judge（LLM 充当评委）

- **来源**：第6章 6.5.1
- **作者定义**："让语言模型根据专家定义的评分标准（Rubric）进行评判，在自动化规模和人类专业判断之间取得平衡。"
- **关键区分**：适用于无标准答案的开放式任务;有标准答案的任务用代码自动验证即可;
已知局限:长度偏差/位置偏差/同源偏见——需Rubric四准则+多源评判+定期校准对冲。
- **为什么重要**：企业评估Agent输出质量(报告/客服回复/分析结论)的标配方法;
但"分数只是另一个模型的意见"——校准前不可尽信。

### Rubric（评分准则）

- **来源**：第6章 6.1 / 6.5.1
- **作者定义**："量化Agent 表现的评分标准，可以是二元的（通过/不通过）、连续的（0 到100 分）或多维的（分别给准确性、效率、安全性打分）。"
- **关键区分**：四准则:专家指导/全面覆盖/重要性权重/自包含;
否决项(Veto)处理与质量正交的维度(幻觉/安全);
是迭代产物,从抽象准则演化为详尽判例集。
- **为什么重要**：企业Agent验收标准的设计模板;
也可用于员工工作质量评审的结构化。

### 消融实验（Ablation Study）

- **来源**：第6章 6.1 / 6.10.1
- **作者定义**："逐一'摘除'某个组件，看整体性能掉多少——判断该组件的真实贡献。"
- **关键区分**：≠模型替换实验(固定Harness只换模型,区分瓶颈在模型还是Harness);
消融定位Harness内部哪个部件重要;作为常规工程实践而非一次性研究。
- **为什么重要**："这个功能到底有没有用"的科学回答方式;
我们自己的Cron任务/技能/提示词模块也应定期消融验证。

### 渐进式信息透露（Progressive Information Disclosure）

- **来源**：第6章 6.2.3
- **作者定义**："模拟用户'不要一次性透露所有信息，只提供当前步骤必要的内容'——信息应按需、渐进地在对话中透露。"
- **关键区分**：≠传统benchmark开局全盘托出;真实用户表达模糊/不完整;
澄清需求的能力本身就是被评估的能力维度。
- **为什么重要**：设计客服/助手Agent及其评估的核心概念;
也是Skills"渐进式披露"在评估语境的同源思想。

### 数据泄漏（Data Contamination）

- **来源**：第6章 6.3.1（挑战五）
- **作者定义**："当评估数据被纳入训练数据时，评估测的就是记忆力而非泛化能力。"
- **关键区分**：防范四策:答案独特性/动态参数生成/时间新鲜度/金丝雀GUID;
金丝雀使泄漏"可检测",前三者使泄漏"难发生"。
- **为什么重要**：解读任何benchmark分数的前置问题;企业内训/测试集设计的防作弊意识。

### 标准误与噪声带宽（Standard Error）

- **来源**：第6章 6.7
- **作者定义**："若在n 个测试用例上测得成功率p，标准误约为√(p(1-p)/n)……95% 置信区间约为p ± 2 个标准误。"
- **关键区分**：快速判断"这点分差值不值得当真"的口算工具;
配对分析(同批任务)比独立成功率相减灵敏得多;
SE随√n缩小,扩样成本高昂。
- **为什么重要**：数据驱动决策的基本功:良品率/OEE等指标对比时同样需要判断"差异是信号还是噪声"。

### 可观测性（Observability / Trace / Span）

- **来源**：第6章 6.8
- **作者定义**："你没法直接打开系统内部看它在做什么，只能通过它输出的日志、指标和追踪数据来推断发生了什么。"
- **关键区分**：一次任务=一条trace;每个LLM调用/工具调用/检索=一个span(输入输出/起止/token/错误);
OpenTelemetry通用标准,OpenInference定义LLM应用语义约定——采集与分析解耦,避免平台锁定。
- **为什么重要**：Agent运维的基础词汇;轨迹数据同时是诊断/成本分析/评估集活化的共同原料。

### 持续进化（Continuous Evolution）

- **来源**：第8章（图8-1）
- **作者定义**："从运行经验到新版本Agent：执行任务→记录轨迹→形成信号→生成候选更新（知识/指令/程序/参数）→验证与发布（回归、灰度与回滚）→新的Agent进入下一轮运行。只有改变后续行为且通过验证的更新，才构成持续进化。"
- **关键区分**：≠保存经历(日志写盘≠学习);≠一次优化(单次修改);
=可追溯运行经验+改变后续行为+验证无退化的完整闭环。
- **为什么重要**：企业Agent从"项目交付"到"产品运营"的范式转变词汇;
判断"我们的Agent会不会越用越聪明"的检验框架。


## 六、后训练（第 7 章）

### SFT（监督微调）

- **来源**：第7章 7.1.2 / 7.4
- **作者定义**："用几千到几万条'问题—标准回答'的示范数据，教会模型'该用什么格式、什么风格、什么流程来回答'。……在数学上和预训练是同一个任务——都是预测下一个词，差别只在数据不同、损失只算在'回答'上。"
- **关键区分**：固化的是协议性知识(格式/风格/流程),不是事实性知识;
"SFT记忆":环境一变就套用旧答案;样本效率高(几千条见效),成本低;
与RL是先后关系不是竞争关系——先把"形"立起来。
- **为什么重要**：理解"微调"到底在调什么;判断"要不要为某项能力做微调"的前置概念。

### RLHF / RLVR / 奖励模型（RM）

- **来源**：第7章 7.7
- **作者定义**："RLHF 的奖励来自学习到的RM（背后是人类偏好数据），RLVR 的奖励来自规则验证器（测试是否通过、答案是否正确）。……实际部署的模型是叠加使用的，RLHF 负责对话质量与安全对齐，RLVR 负责推理与Agent 能力。"
- **关键区分**：奖励模型变体:ORM(只看最终结果)/PRM(逐步打分)/生成式RM(用自然语言讲理由);
当对错能用规则直接判定,RM退化成一段确定性代码(=RLVR);
Agent任务恰好大多是可验证的——RLVR是Agent训练主线。
- **为什么重要**：区分"对齐靠偏好"与"能力靠验证"两条训练路线;
我们的业务(报工/质检规则明确)天然是RLVR型场景。

### 拒绝采样微调（RFT / Rejection Sampling）

- **来源**：第7章 7.9.3
- **作者定义**："对每条提示采样k 条候选（常取4 到16）→用规则验证器、单元测试或参考答案判对错→只保留通过筛选的轨迹……用留下的数据做一轮SFT。"
- **关键区分**：介于纯SFT与RL之间:不训奖励模型、不做策略梯度,
只靠"从多条采样中拒绝错的留下对的"提升数据质量——可验证任务上性价比极高的数据构造手段;
模型变强后可重新采样再筛,迭代自举(STaR核心循环)。
- **为什么重要**："数据质量胜过算法"的可执行流水线:不需要新算法,只需要可靠验证器+足够采样预算。

### On-Policy Distillation（在轨蒸馏）/ OPSD（自蒸馏）

- **来源**：第7章 7.12
- **作者定义**："让学生自己生成轨迹（On-Policy，解决分布不匹配），同时让一个更强的教师模型对学生走的每一步逐token 打分（Dense Signal，解决信号稀疏）。"
- **关键区分**：SFT=离轨+稠密,RL=在轨+稀疏,On-Policy Distillation=在轨+稠密;
OPSD变体:没有更强教师时,同一模型分饰两角——教师版看"特权信息"(标准答案)讲题,学生版只见题对齐;
"对着答案讲题"远比"独立解题"容易(验证-生成不对称的又一形态)。
- **为什么重要**：当前样本效率最有希望的突破口之一;
垂直领域无强教师时OPSD是现实路径。

### 信用分配（Credit Assignment）

- **来源**：第7章 7.10.1
- **作者定义**："判断多步序列中到底哪一步对最终结果贡献最大——比如一个客服Agent 用了10 轮对话解决了用户问题，最终获得好评，但这个好评该归功于第2 轮的精准提问，还是第7 轮的耐心解释？"
- **关键区分**：单轮即时反馈无此难题;多轮延迟奖励下是核心挑战;
GRPO把轨迹级优势均摊到所有token(精准提问与无效寒暄同信用)——长程任务稀释信号,
PPO用GAE按步估计,turn-level分摊是常见折中。
- **为什么重要**：理解多轮Agent为什么难训练的核心概念;
类比企业管理:月度绩效结果好,该归功于哪个环节的动作——同样需要过程数据。


## 七、持续进化（第 8 章）

### 系统提示学习（System Prompt Learning）

- **来源**：第8章 8.2.2（Karpathy 2025）
- **作者定义**："遇到问题、想通方法后，用明确的语言提醒未来的自己'下次遇到这类问题，应先尝试这种办法'。"
- **关键区分**：≠预训练(学知识)≠微调(塑习惯)≠RL(梯度下降改参数);
=编辑文字更新行为,数据效率可能更高("知识引导的复盘比标量奖励有更高维度反馈通道");
但不天然正确——需聚类、作用域判断与回归测试。
- **为什么重要**：Prompt/Skill作为学习载体的理论基础;
我们维护SOUL.md/skills的实践正是此范式的实例。

### 睡眠学习（Sleep Learning / 离线整合）

- **来源**：第8章 8.3.5
- **作者定义**："在线Agent 的首要职责是完成当前任务并追加不可变证据；后台学习进程则在空闲期或满足门控条件时读取一批新经历，比较新旧结论、合并重复项、解决冲突、提出候选更新并运行回归。"
- **关键区分**：认知类比,不要求真的夜间运行;采集与整理分开;
允许用更大批量和更便宜的模型完成整理。
- **为什么重要**：后台Cron进化任务的设计范式;
我们memory维护/Curator的实践对应物。

### 可信根（Trusted Root）

- **来源**：第8章 8.3（图8-5）/ 8.3.4
- **作者定义**："权限、审计、验证与回滚机制不由普通进化流程自行修改。"
- **关键区分**：业务Agent可改Prompt/Skill/知识库/工具;
不可改:批准自身更新的验证器、测试用例、发布门槛、审计日志、稳定版本备份;
搜索空间越大,可信根越重要。
- **为什么重要**：自我进化系统的安全基石概念;
任何自动化系统的"谁看住看门人"问题答案。

### harness-updating 与 harness-benefit（更新能力 vs 受益能力）

- **来源**：第8章 8.3.2
- **作者定义**："Harness 更新能力是从轨迹中产生有价值的持久修改；Harness 受益能力是任务Agent 在后续运行中找到、激活并正确使用这些修改。"
- **关键区分**：两种能力与基础模型能力的关系并不相同;
端到端分数无法区分瓶颈在更新器/检索路由/指令遵循——需双向模型替换诊断。
- **为什么重要**："为什么改了没效果"的诊断框架:改对了但没加载 vs 加载了但执行不了 vs 改本身就不对。


## 八、多 Agent 协作（第 10 章）

### Loop 工程（Loop Engineering）

- **来源**：第10章 10.4.3（Addy Osmani 2026-06 总结提出）
- **作者定义**："设计一个让Agent 持续运转的循环——发现下一件该做的事、执行、验证、记录进度——由验证器而不是模型自己来判定'是否真的可以停'，人的角色则从'给Agent 写提示词的操作者'变成'设计循环的工程师'。"
- **关键区分**：核心共识:循环的瓶颈在验证器,不在模型——验证不可靠,循环转得再快也只是把劣质产出更快标记为完成;
对治三类过早终止:偷懒式假完成/过早放弃/假成功。
- **为什么重要**："我已经不再直接prompt Claude了,我的工作是写loop"(Boris Cherny)——
Agent工程的工作重心从提示词转向循环与验证器设计。

### 拜占庭故障 vs 崩溃故障

- **来源**：第10章 10.5
- **作者定义**："崩溃故障：部件停止工作；拜占庭故障：部件不停工作，但给出错误信息。"
- **关键区分**：Agent故障天生是拜占庭式:很少径直停止,而是继续给出看似可信的错误结论,且错误不会主动声明;
只能靠独立冗余(交叉验证/多数表决)发现;确定性外部反馈是唯一不会说谎的部件。
- **为什么重要**：设计Agent监控/验收时的基本故障观:沉默不是金,报错才是——不报错的最危险。

### 移交包（Handoff Package）

- **来源**：第10章 10.4.5
- **作者定义**："任务描述（接收方要做什么、验收标准是什么）、已确认的事实与约束（用户偏好、业务规则、前序阶段敲定的决策），以及结构化产物的引用（文件路径而非文件内容）。"
- **关键区分**：≠全量轨迹(试错过程/中间思考/失败尝试对接收方多半是噪声);
共享上下文移交保留完整历史(零损耗但膨胀),不共享移交传递提炼包(有损但干净专注)。
- **为什么重要**：多Agent/多班次/人机交接的标准内容规范;
企业里班组交接、外协对接同样适用。

### A2A 协议（Agent2Agent）

- **来源**：第10章 10.4.6 跨组织协作：A2A 协议
- **作者定义**："2025 年Google 发布（后捐赠Linux 基金会）。核心要素：Agent Card（能力元数据'名片'）、任务生命周期管理（已提交/进行中/需要输入/已完成/失败状态机）、不透明协作（只交换任务与产物，不暴露内部提示词与思考过程）。"
- **关键区分**：MCP解决Agent与工具互操作,A2A解决Agent与Agent互操作;
同一团队内部用消息总线即可,跨信任边界才需要A2A。
- **为什么重要**：未来与供应商/客户的Agent系统对接时的标准协议候选。

### 乐观锁（Optimistic Locking）

- **来源**：第10章 10.5.1
- **作者定义**："每个文件维护一个版本号。Agent 读取文件时记录当前版本号，写入时检查版本号是否仍与读取时一致。如果文件在此期间已被其他Agent 修改过，写入就会失败，Agent 被迫重新读取最新版本。"
- **关键区分**：≠悲观锁(打开即锁定,安全但低效);
只能防同一文件写入冲突(丢失更新),防不了跨文件语义冲突;
多Coding Agent场景主流解法其实是工作副本隔离(Git分支/worktree),冲突推迟到合并点。
- **为什么重要**：多Agent并发写共享文件(报工数据/排产表)时的基础并发控制手段。

### 涌现行为（Emergent Behavior）

- **来源**：第10章 10.6 Agent 社会
- **作者定义**："系统整体表现出的、无法从单个个体的行为规则中直接预测的集体行为模式。"
- **关键区分**：蚁群找最短路径是自然界经典例;Agent案例:AI小镇自发派对/选举传播,
Moltbook 150万Agent涌现数字宗教与机器原生协作协议,Vending-Bench自发价格战与合谋。
跨过规模临界点后产生,不可预先设计。
- **为什么重要**：理解大规模Agent部署后的"组织行为学";
警示:经济型Agent可能出现合谋等未被设计的博弈行为,治理需前置。

### 工作副本隔离（worktree）

- **来源**：第10章 10.5.1
- **作者定义**："为每个Agent 分配独立的Git 分支或worktree，各自在自己的副本上并行修改、互不干扰，冲突被集中推迟到最后的合并点，再由专门的合并步骤或人工来解决。"
- **关键区分**：≠单一工作副本上加锁;与fork进程的写时复制(copy-on-write)同思路;
与"隔离优于压缩"同源:从一开始隔离,把协调成本收敛到明确边界处理。
- **为什么重要**：多个Coding Agent并发改同一代码库的主流方案。


## 九、战略与前沿（第 9 章/后记）

### Computer Use（计算机操作 Agent）

- **来源**：第9章 9.2
- **作者定义**："Agent 通过截图理解屏幕内容、以像素坐标执行点击/输入等操作来使用计算机——不依赖应用提供API，而是像人一样操作图形界面。"
- **关键区分**：≠API调用(确定性接口):视觉操作是概率性接口,坐标靠"猜",必须动作后验证;
价值在于打通没有API的老系统(老旧软件/网页)。
- **为什么重要**：我们面对无API的老旧MES/工控界面时的备选通路——但可靠性纪律(五防错)比API场景更严。

### VLA（Vision-Language-Action，视觉-语言-动作模型）

- **来源**：第9章 9.3
- **作者定义**："统一视觉感知、语言理解与动作生成的模型范式：视觉编码器处理环境观察、语言模型理解指令并推理、动作解码器生成控制信号，实现语言条件控制与跨任务泛化。"
- **关键区分**：≠传统机器人(硬编码轨迹):VLA听懂自然语言指令并泛化到新物体/新场景;
训练目前以模仿学习(SFT性质)为主,RL在其上进一步优化(SimpleVLA-RL)。
- **为什么重要**：制造业机器人+AI的技术前沿;我们自动化集成业务未来5年的技术选项雷达。

### 动作分块（Action Chunking）

- **来源**：第9章 9.3 / 第7章实验7-13
- **作者定义**："模型一次推理生成未来多步动作，由控制线程依次执行、GPU 在后台异步生成下一批，只要推理时间小于执行时间，机器人就能保持连续流畅的运动。"
- **关键区分**：解决"慢思考vs快执行"的延迟矛盾:不让慢模型阻塞快动作;
与VLA三层架构(大脑低频规划/小脑高频执行)配套。
- **为什么重要**：慢决策快执行解耦的工程范式——同样适用于"LLM排产(慢)+机床执行(快)"的系统设计。

### 小世界假设 vs 大世界假设

- **来源**：后记
- **作者定义**："小世界假设：一个足够大的模型本就装得下物理世界里几乎所有重要的通用知识，学一次就够。大世界假设：属于某个具体用户、某家具体公司的知识……不在任何训练语料里，而且时时在变；模型只能在上岗之后持续学习，没法指望出厂时一次配齐。"
- **关键区分**：针锋相对的两种战略判断:前者导向"把行业数据蒸馏进大模型"(前沿实验室的做法);
后者导向"记忆+持续进化"(第3章与第8章的方向);
两者不互斥——通用知识靠训练,具体情境靠上岗后学习。
- **为什么重要**：企业AI战略的定位锚:智机的工艺know-how/客户偏好/现场经验属"大世界",
等不到也买不到,必须自建学习机制——这是我们做持续进化体系的第一性理由。
