# 诊断 Bug

一套针对棘手 bug 的结构化方法论。仅在明确有充分理由时才跳过某个阶段。

在探索代码库时，请阅读 `CONTEXT.md`（如果存在）以建立相关模块的清晰心智模型，并查看你所涉及领域的 ADR。

## 阶段 1 — 构建反馈循环

**这是核心技能。** 其余部分都是机械性的。如果你有一个**紧凑**的通过/失败信号来检测该 bug——一个能在这个 bug 上变红的信号——你就能找到根本原因；二分查找、假设检验和插桩都只是消费这个信号而已。如果没有这个信号，盯着代码看再多也救不了你。

在此投入不成比例的精力。**要激进。要创造性地想办法。拒绝放弃。**

### 构建反馈循环的方法 —— 大致按此顺序尝试

1. **失败测试** —— 在能触达 bug 的任何接缝层面编写：单元测试、集成测试、端到端测试。
2. **Curl / HTTP 脚本** —— 针对正在运行的开发服务器发送请求。
3. **CLI 调用** —— 使用固定输入，将 stdout 与已知正确的快照进行 diff 对比。
4. **无头浏览器脚本**（Playwright / Puppeteer）—— 驱动 UI，对 DOM/控制台/网络进行断言。
5. **重放捕获的追踪记录。** 将真实的网络请求 / payload / 事件日志保存到磁盘；在隔离环境中通过代码路径重放它。
6. **一次性测试夹具。** 启动系统的最小子集（单个服务，模拟依赖项），用一个函数调用来演练 bug 代码路径。
7. **属性 / 模糊测试循环。** 如果 bug 是"有时输出错误"，运行 1000 次随机输入并寻找失败模式。
8. **二分查找夹具。** 如果 bug 出现在两个已知状态之间（提交、数据集、版本），自动化"在状态 X 启动，检查，重复"的流程，以便你可以用 `git bisect run` 来二分定位。
9. **差异对比循环。** 将相同输入分别在旧版本和新版本（或两种配置）上运行，然后对比输出差异。
10. **人机协同 bash 脚本。** 最后的手段。如果必须由人类点击操作，用 `scripts/hitl-loop.template.sh` 来驱动他们，使循环仍然结构化。捕获的输出会反馈给你。

构建出正确的反馈循环，bug 就解决了 90%。

### 收紧循环

把循环当作一个产品来打磨。一旦你有了一个循环，就要**收紧**它：

- 能否让它更快？（缓存设置，跳过无关初始化，缩小测试范围。）
- 能否让信号更锐利？（针对具体症状做断言，而不是"没崩溃"。）
- 能否让它更具确定性？（固定时间，固定随机种子，隔离文件系统，冻结网络。）

一个 30 秒的抖动循环几乎不比没有循环好多少；一个 2 秒的确定性循环则是紧凑的——是调试的超能力。

### 非确定性 bug

目标不是干净的复现，而是**更高的复现率**。将触发条件循环 100 次，并行执行，增加压力，缩小时间窗口，注入 sleep。50% 抖动率的 bug 是可调试的；1% 则不行——持续提高复现率直到可调试为止。

### 当你确实无法构建循环时

停下来，明确说明。列出你尝试过的方法。向用户请求：(a) 访问能够复现该 bug 的任何环境，(b) 一个已捕获的产物（HAR 文件、日志转储、core dump、带时间戳的屏幕录像），或 (c) 允许在生产环境添加临时插桩。**不要**在缺少循环的情况下直接进入假设阶段。

### 完成标准 —— 一个能变红的紧凑循环

阶段 1 完成的标志是：循环已经**紧凑**且**能变红**：你能说出**一个命令**——一个脚本路径、一个测试调用、一个 curl 命令——你**已经至少运行过一次**（粘贴该命令及其输出），并且满足：

- [ ] **能变红** —— 它驱动了实际的 bug 代码路径，并对**用户描述的具体症状**做断言，因此它能够检测到这个 bug 并在修复后变绿。不是"运行不出错"——它必须能够捕获到这个具体的 bug。
- [ ] **确定性** —— 每次运行结果一致（对于抖动性 bug：按前述要求，达到一个固定的、足够高的复现率）。
- [ ] **快速** —— 秒级，而不是分钟级。
- [ ] **Agent 可运行** —— 你可以无人值守地运行它；只有在通过 `scripts/hitl-loop.template.sh` 时才需要人类参与。

如果你发现自己在构建出这个命令之前就开始阅读代码以构建理论，**停下来——跳过构建循环直接跳入假设阶段，正是本技能要防止的失败模式。** 没有能变红的命令，就没有阶段 2。

## 阶段 2 — 复现 + 最小化

运行循环。观察它变红——bug 出现了。

确认：

- [ ] 循环产生的失败模式与**用户**描述的完全一致——而不是恰好出现在附近的另一个不同的失败。错误的 bug = 错误的修复。
- [ ] 失败在多次运行中可复现（对于非确定性 bug，复现率足够高以用于调试）。
- [ ] 你已经捕获了具体症状（错误信息、错误输出、缓慢的耗时），以便后续阶段能验证修复是否真正解决了问题。

### 最小化

一旦它能变红，将复现场景缩小到**仍能变红的最小场景**。每次削减输入、调用者、配置、数据和步骤时，**一次只改一个**，每次削减后重新运行循环——只保留对产生失败至关重要的部分。

这样做的意义：最小化的复现场景缩小了阶段 3 中的假设空间（剩余的可疑移动部件更少），并成为阶段 5 中干净的回归测试。

完成标志是**每个剩余元素都是关键的**——移除其中任何一个都会让循环变绿。

在完成复现**和**最小化之前，不要继续。

## 阶段 3 — 提出假设

在测试任何一个假设之前，先产生 **3-5 个已排序的假设**。单一假设的产生会锚定在第一个看起来合理的想法上。

每个假设必须是**可证伪的**：陈述它所做出的预测。

> 格式："如果 <X> 是原因，那么 <改变 Y> 将使 bug 消失 / <改变 Z> 将使 bug 恶化。"

如果你无法陈述预测，那这个假设只是一种感觉——丢弃或精炼它。

**在测试之前将排序后的假设列表展示给用户。** 他们通常拥有能瞬间重新排序的领域知识（"我们刚刚对 #3 部署了一个变更"），或者知道已经被排除的假设。这是一个成本低、省时间的重要检查点。不要在此阻塞——如果用户不在线，按你的排序继续。

## 阶段 4 — 插桩

每个探针必须映射到阶段 3 中的一个具体预测。**每次只改变一个变量。**

工具偏好：

1. **调试器 / REPL 检查** —— 如果环境支持的话。一个断点胜过十个日志。
2. **有针对性的日志** —— 在能区分不同假设的边界处添加日志。
3. 绝不要"记录所有日志然后 grep"。

**为每个调试日志打上唯一前缀标签**，例如 `[DEBUG-a4f2]`。结束时的清理工作只需一个 grep。无标签的日志保留；有标签的日志删除。

**性能分支。** 对于性能回退，日志通常是错误的工具。取而代之的是：建立基线测量（计时夹具、`performance.now()`、性能分析器、查询计划），然后二分定位。先测量，后修复。

## 阶段 5 — 修复 + 回归测试

在修复之前编写回归测试——但前提是存在一个**正确的接缝**。

正确的接缝是指测试能够在调用点处演练**真实的 bug 模式**。如果唯一可用的接缝太浅（bug 需要多个调用者但只有一个调用者的测试，单元测试无法复制触发 bug 的调用链），那么在此处编写回归测试只会带来虚假的信心。

**如果不存在正确的接缝，这本身就是发现。** 记录下来。代码库的架构正在阻止将此 bug 锁定下来。将此标记为下一个阶段要处理的问题。

如果存在正确的接缝：

1. 将最小化的复现场景转化为该接缝处的一个失败测试。
2. 观察它失败。
3. 应用修复。
4. 观察它通过。
5. 使用原始的（未最小化的）场景重新运行阶段 1 的反馈循环。

## 阶段 6 — 清理 + 事后复盘

在宣布完成之前必须完成：

- [ ] 原始复现场景不再复现（重新运行阶段 1 的循环）
- [ ] 回归测试通过（或接缝的缺失已被记录在案）
- [ ] 所有 `[DEBUG-...]` 插桩已被移除（用 `grep` 搜索前缀）
- [ ] 一次性原型已删除（或移动到明确标记的调试位置）
- [ ] 被证明是正确的假设在 commit / PR 消息中明确陈述——以便下一个调试者可以学习

**然后问：什么措施可以预防这个 bug？** 如果答案涉及架构变更（没有好的测试接缝、调用者纠缠不清、隐藏的耦合），将具体情况移交给 `/improve-codebase-architecture` 技能来处理。在修复完成之后再做建议，而不是之前——你现在比开始时掌握了更多信息。
