# 代码库设计

设计**深度模块**：用一个小接口承载大量行为，放置在清晰的 seam 处，通过该接口可测试。在设计和重构代码的任何地方都使用这套语言和原则。目标是为调用者提供 leverage，为维护者提供 locality，为所有人提供可测试性。

## 术语表

严格使用以下术语——不要用 "component"、"service"、"API" 或 "boundary" 替代。一致的语言是核心所在。

**Module**（模块）——任何具有接口和实现的东西。刻意做到规模无关：可以是一个函数、类、包，或跨层切片。*避免使用*：unit、component、service。

**Interface**（接口）——调用者为了正确使用模块所必须知道的一切：类型签名，还包括不变量、顺序约束、错误模式、所需配置和性能特征。*避免使用*：API、signature（过于狭窄——它们仅指类型层面的表面）。

**Implementation**（实现）——模块内部的东西，即其代码体。区别于 **Adapter**：一个东西可以是一个小 adapter 加上大实现（如 Postgres 仓库），也可以是一个大 adapter 加上小实现（如内存 fake）。当 seam 是讨论主题时使用 "adapter"；其他情况使用 "implementation"。

**Depth**（深度）——接口处的 leverage：调用者（或测试）每学习一单位接口所能运用的行为量。当一个模块的大量行为藏在小接口后面时，它就是**深**的；当接口几乎与实现一样复杂时，它就是**浅**的。

**Seam**（接缝）*（Michael Feathers）*——一个你可以在不编辑该处代码的情况下改变行为的地方；是模块接口所在的*位置*。把 seam 放在哪里本身就是一个设计决策，与它后面放什么无关。*避免使用*：boundary（与 DDD 的有界上下文含义重叠）。

**Adapter**（适配器）——在 seam 处满足接口的具体事物。描述的是*角色*（它填充哪个槽位），而非实质（里面是什么）。

**Leverage**（杠杆效应）——调用者从深度中获得的好处：每学习一单位接口，获得更多的能力。一个实现回馈给 N 个调用点和 M 个测试。

**Locality**（局部性）——维护者从深度中获得的好处：变更、bug、知识和验证集中在一处，而非分散在各个调用者之间。修复一次，处处生效。

## 深 vs 浅

**深度模块** = 小接口 + 大量实现：

```
┌─────────────────────┐
│   Small Interface   │  ← 少量方法，简单参数
├─────────────────────┤
│                     │
│  Deep Implementation│  ← 复杂逻辑被隐藏
│                     │
└─────────────────────┘
```

**浅层模块** = 大接口 + 少量实现（应避免）：

```
┌─────────────────────────────────┐
│       Large Interface           │  ← 大量方法，复杂参数
├─────────────────────────────────┤
│  Thin Implementation            │  ← 仅仅是透传
└─────────────────────────────────┘
```

设计接口时，问自己：

- 我能减少方法的数量吗？
- 我能简化参数吗？
- 我能把更多复杂性隐藏在内部吗？

## 原则

- **深度是接口的属性，而非实现的属性。** 一个深度模块内部可以由小的、可 mock 的、可替换的部分组成——它们只是不属于接口的一部分。模块可以有**内部 seam**（对其实现私有，供其自身测试使用），也可以有位于其接口处的**外部 seam**。
- **删除测试。** 想象删除这个模块。如果复杂性消失了，它就是个透传层。如果复杂性在 N 个调用者中重新出现，它就是在发挥价值。
- **接口就是测试面。** 调用者和测试跨越同一个 seam。如果你想测试接口*背后*的东西，说明模块的形状可能不对。
- **一个 adapter 意味着假设性的 seam。两个 adapter 才意味着真正的 seam。** 除非确实有东西会在 seam 上发生变化，否则不要引入 seam。

## 为可测试性而设计

好的接口让测试变得自然：

1. **接受依赖，不要创建依赖。**

   ```typescript
   // 可测试
   function processOrder(order, paymentGateway) {}

   // 难以测试
   function processOrder(order) {
     const gateway = new StripeGateway();
   }
   ```

2. **返回结果，不要产生副作用。**

   ```typescript
   // 可测试
   function calculateDiscount(cart): Discount {}

   // 难以测试
   function applyDiscount(cart): void {
     cart.total -= discount;
   }
   ```

3. **小的暴露面。** 更少的方法 = 更少的测试需求。更少的参数 = 更简单的测试准备。

## 关系

- 一个 **Module** 有且仅有一个 **Interface**（它呈现给调用者和测试的表面）。
- **Depth** 是 **Module** 的属性，以其 **Interface** 为衡量标准。
- **Seam** 是 **Module** 的 **Interface** 所在的位置。
- **Adapter** 位于 **Seam** 处并满足 **Interface**。
- **Depth** 为调用者产生 **Leverage**，为维护者产生 **Locality**。

## 被拒绝的框架

- **将深度定义为实现行数与接口行数之比**（Ousterhout）：这会奖励填充实现。我们改用深度即 leverage。
- **将 "Interface" 等同于 TypeScript 的 `interface` 关键字或类的公开方法**：过于狭窄——这里的 interface 包括调用者必须知道的一切事实。
- **"Boundary"**：与 DDD 的有界上下文含义重叠。应使用 **seam** 或 **interface**。
