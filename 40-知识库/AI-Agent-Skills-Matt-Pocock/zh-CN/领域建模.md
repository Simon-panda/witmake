# 领域建模

在设计过程中积极构建和完善项目的领域模型。这是一门*主动*的学科——挑战术语、设想边缘场景、在概念明确的瞬间就写下术语表和决策记录。（仅仅*阅读* `CONTEXT.md` 获取词汇并不属于本技能——那是任何技能都能做到的一行习惯。本技能适用于你在*改变*模型，而不仅仅是消费它时。）

## 文件结构

大多数仓库只有一个上下文：

```
/
├── CONTEXT.md
├── docs/
│   └── adr/
│       ├── 0001-event-sourced-orders.md
│       └── 0002-postgres-for-write-model.md
└── src/
```

如果根目录存在 `CONTEXT-MAP.md`，则仓库有多个上下文。映射文件指向每个上下文的所在位置：

```
/
├── CONTEXT-MAP.md
├── docs/
│   └── adr/                          ← 系统级决策
├── src/
│   ├── ordering/
│   │   ├── CONTEXT.md
│   │   └── docs/adr/                 ← 上下文特定决策
│   └── billing/
│       ├── CONTEXT.md
│       └── docs/adr/
```

按需创建文件——只有当你确实有内容要写时才创建。如果 `CONTEXT.md` 不存在，在第一个术语确定时创建它。如果 `docs/adr/` 不存在，在需要第一个 ADR 时创建它。

## 会话期间

### 对照术语表进行挑战

当用户使用的术语与 `CONTEXT.md` 中已有的语言发生冲突时，立即指出。"你的术语表将'取消'定义为 X，但你似乎指的是 Y——到底是哪一个？"

### 精确化模糊语言

当用户使用模糊或含义过载的术语时，提出一个精确的规范术语。"你说的是'账户'——你指的是客户还是用户？它们是不同的概念。"

### 讨论具体场景

在讨论领域关系时，用具体场景进行压力测试。构思能探测边缘情况的场景，迫使用户精确界定概念之间的边界。

### 与代码交叉验证

当用户描述某事物如何运作时，检查代码是否一致。如果发现矛盾，把它摆出来："你的代码取消的是整个订单，但你刚才说部分取消是可能的——哪个是对的？"

### 即时更新 CONTEXT.md

当一个术语确定下来时，立刻更新 `CONTEXT.md`。不要批量处理——随时记录。使用 [CONTEXT-FORMAT.md](./CONTEXT-FORMAT.md) 中的格式。

`CONTEXT.md` 应完全不含实现细节。不要将 `CONTEXT.md` 视为规格说明、草稿纸或实现决策的存储库。它是术语表，仅此而已。

### 谨慎提供 ADR

只有当以下三个条件全部满足时才提议创建 ADR：

1. **难以逆转**——事后改变主意的成本是有意义的
2. **没有上下文会令人困惑**——未来的读者会想"为什么他们这样做？"
3. **真正的权衡结果**——确实存在可行的替代方案，你基于具体理由选择了其中之一

如果三个条件中有任何一个不满足，跳过 ADR。使用 [ADR-FORMAT.md](./ADR-FORMAT.md) 中的格式。
