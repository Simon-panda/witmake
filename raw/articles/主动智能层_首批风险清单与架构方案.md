# 主动智能层：首批风险清单与统一 Agent 架构方案

> **文档定位**：精密汽配 CNC 制造业（200 台 CNC，40+ 自动化产线，已具备完整追溯能力）的"主动智能层"建设方案。
> **服务目标**：把"发现问题 → 定位责任人"从 5-30 分钟手工查询，压缩到 < 1 分钟自动推送，并把"事后留痕"升级为"事前主动找人"。
> **关键背景**：当前班组长 7×12 工作制，目标向 6×12 演进，最终 5×12——核心约束是班长人才储备不够，需 AI 主动智能层降低"班组长不在场"的风险，配合班组长能力发展体系完成过渡。

---

## 一、核心架构洞察

**预测风险 = 自动定位的"反向问题"**

```
                  ┌─────────────────────┐
                  │   同一套数据源        │
                  │ MES/QMS/刀具/SPC/    │
                  │ 员工矩阵/物料/客诉    │
                  └──────────┬──────────┘
                             ↓
                  ┌─────────────────────┐
                  │   同一个 Agent 引擎   │
                  └─────┬───────────┬───┘
                        ↓           ↓
              "已经发生了什么？"  "可能会发生什么？"
              （Postmortem 模式） （Predictive 模式）
                  自动定位         主动预警
                        ↑           ↑
                  事件触发      持续巡检
```

**关键判断**：
- 自动定位是"看历史，找根因"——给定一个不良零件，从数据里反推
- 主动预警是"看现在，推未来"——同样的数据源，不同的查询方向
- 它们的代码 80% 可以复用：数据接入、推理引擎、路由通知、闭环验证都是同一套
- 只在**触发方式 + 推理目标**上不同

**结论**：把这两件事做成同一个产品，叫"质量风险智能体"或"根因 Agent"，对外暴露两个模式。这一架构决策可让后期维护成本减少 60%。

## 二、风险目录设计哲学

### 不要把风险硬编码在 Agent 代码里

**正确做法：风险目录是声明式配置（YAML / JSON），不是代码。**

每条风险的标准化结构示例：

```yaml
risk_id: TOOL_LIFE_CRITICAL
name: 刀具寿命临界
category: 设备
severity: 高
trigger:
  type: 实时 / 周期 / 事件
  condition: tool.remaining_life < 15% AND tool.is_active = true
data_sources:
  - 刀具管理系统
  - MES（当前在用刀具）
prediction_logic:
  type: 规则 / ML 模型 / LLM
  detail: "基于历史寿命分布的 P10 阈值动态调整"
routing:
  primary: 当班操作工
  backup: 班组长
  escalation: 调试工 + 工艺工程师（10min 未响应）
notification_level: 行动（中）
closure_condition:
  - 刀具更换记录 OR
  - 工艺工程师确认延用（带签字）
expected_action: 停机换刀，或工艺评估后延用
false_positive_handling:
  - 用户标记 → 自动调整阈值
training_link:
  - 新员工首次遇到此提示时，附带 30 秒视频 SOP
```

### 这样设计的四大价值

1. **业务人员能改**——HR 经理 / 工艺工程师不用懂代码，能调阈值、改路由
2. **能版本控制**——风险目录进 Git，每次改动可追溯（IATF 16949 审计也认这个）
3. **能 A/B 测试**——同一类风险用不同阈值在不同产线对比
4. **AI 团队能批量优化**——而不是改一处动整个系统

## 三、首批 10 条核心风险清单

**入选原则**：高价值 + 高置信度 + 行动清晰 + 一次见效

### 设备 / 刀具类

#### 1. TOOL_LIFE_CRITICAL（刀具寿命临界）
- **触发**：剩余寿命 < 15%（动态阈值，按历史 P10 调整）
- **推送**：当班操作工 → 班组长（5min 未响应）
- **闭环**：换刀记录 / 工艺签字延用
- **价值**：避免过晚换刀导致的批量废品

#### 2. TOOL_LIFE_ABNORMAL_SHORT（同型刀具寿命系统性缩短）
- **触发**：近 7 天某型号刀具实际寿命 < 30 天均值 × 75%
- **推送**：工艺工程师 + 调试工
- **价值**：早期发现来料 / 参数 / 程序异常
- **闭环**：根因报告 + 处理方案

#### 3. MACHINE_ALARM_UNRESPONDED（设备报警未处理）
- **触发**：机床报警 > 10min 未维修响应
- **推送**：维修工 → 设备科长（15min）→ 厂长（30min）
- **闭环**：维修工单关闭 + 复机记录

### 工艺 / 质量类

#### 4. FIRST_ARTICLE_SKIPPED（首件未检即批量）
- **触发**：换刀 / 换班 / 换程序后第 5 件已下线，但首件检验记录缺失
- **推送**：操作工 + 巡检员 + 班组长
- **价值**：IATF 红线，漏一次可能损失整批
- **闭环**：首件签字 + 数据上传

#### 5. SPC_TREND_VIOLATION（SPC 趋势规则触发）
- **触发**：西部电气七规则中任意一条（连续 7 点同侧 / 连续 6 点上升 / 等）
- **推送**：操作工 → 巡检员（3min）
- **注意**：**不是看单点超控**——单点超控已有报警。这里要预测的是**趋势**

#### 6. CUSTOMER_DEFECT_PATTERN_RECUR（客诉模式复发）
- **触发**：当前生产参数 / 物料 / 工艺与历史客诉签到的某批次相似度 > 80%
- **推送**：质量班长 + 工艺工程师
- **价值**：**LLM 真正能发挥的地方**——模糊匹配历史客诉文本和当前生产元数据
- **闭环**：工艺评估签字 + 加严措施

### 人员 / 能力类

#### 7. OPERATOR_COMPETENCY_MISMATCH（员工独立作业但能力不达标）
- **触发**：排班 + 实操记录显示员工 A 独立操作工序 X，但能力矩阵该项未达标
- **推送**：班组长（不是员工——员工自己不知道自己不达标）
- **价值**：**直接连通能力矩阵系统**，AI 让带教时机自动发生
- **闭环**：班组长指派带教，或调整排班

#### 8. NEW_OPERATOR_FIRST_24H（新员工独立作业前 24 小时）
- **触发**：员工首次独立操作某工序的前 24 小时
- **推送**：班组长（每 2 小时一次状态摘要，不是逐件提醒）
- **价值**：高风险窗口的主动陪伴
- **闭环**：24h 后系统自动转为常规模式

### 物料 / 批次类

#### 9. NEW_MATERIAL_BATCH_NO_VALIDATION（新批次未验证即上线）
- **触发**：新进物料批次 + 已开始批量加工 + 首件验证记录缺失
- **推送**：来料检验 + 工艺工程师 + 班组长
- **闭环**：批次首件全尺寸报告

### 跨班 / 交接类

#### 10. SHIFT_HANDOVER_INCOMPLETE（班次交接遗留未闭环）
- **触发**：上班待办（异常零件、待复检、设备问题）在交接 30min 后仍未被接手
- **推送**：接班班组长 + 上班班组长
- **价值**：**这是 7×12 → 6×12 改革最大的隐性风险点**
- **闭环**：接班签字 + 状态更新

```
                  │   风险目录 Risk Catalog   │
                  │     （YAML 配置库）       │
                  └────────────┬─────────────┘
                               ↓ 读取
┌─────────────────────────────────────────────────────────────┐
│                  统一 Agent 引擎（Python）                    │
│                                                              │
│  ┌──────────────┐  ┌──────────────┐  ┌──────────────┐     │

└──────────────────────────┬──────────────────────────────────┘
                           ↓

              ┌──────────────────┐
```

## 六、技术选型（基于现有 Python + MySQL + 阿里云 + Dify 栈）

| 模块 | 技术选型 | 说明 |
|---|---|---|
| **数据接入层** | MCP Server 封装 | 每个数据源（MES、刀具、SPC、员工、物料）封装成 MCP Server，统一接口，未来切换框架零成本 |
| **规则推理层** | Python | 性能好、可调试 |
| **模式匹配层**（如客诉复发） | LLM + 向量检索（Dify） | Dify 擅长此类编排 |
| **数值预测层**（如刀具寿命异常） | sklearn / XGBoost | 跑在阿里云 PAI 上 |
| **路由与编排** | Dify 工作流 | Dify 真正的甜点——决策编排，不是业务逻辑 |
| **推送网关** | 企微 API | 已有渠道，无需新建 |
| **闭环验证** | Python 定时任务 + MySQL 查询 | 交叉比对各系统数据 |
| **风险目录管理** | Git + 简单 Web UI | HR 经理 / 工艺能改阈值（不直接改 YAML） |

## 七、推送级别设计（防告警疲劳）

**最大的坑：告警疲劳。如果什么都推送，3 个月内全员屏蔽通知，整个项目作废。**

| 级别 | 渠道 | 预期响应 | 超时升级 |
|---|---|---|---|
| 信息（低） | 当事人每日云端首页摘要 | 当班看一眼即可 | 不升级 |
| 提醒（中） | 企微推送 | 30 分钟内确认 | 推给班组长 |
| 行动（高） | 企微 + 弹窗 | 5 分钟内行动 | 推给值班厂长 |
| 紧急（极高） | 电话 / 广播 | 立即响应 | 同步老板 |

**只有真正关键的事**才走"行动"级别以上。日常 95% 的事在"信息"级别。

## 九、反馈闭环（决定项目生死）

**第一版上线时，每条风险类型的误报率会比预期的高。**

每个推送都要带反馈按钮：

| 反馈 | 含义 | 后续动作 |
|---|---|---|
| 👍 | 有用，我已处理 | 加权该风险类型置信度 |
| 👎 | 误报 / 不需要 | 调整阈值，标记样本 |
| 🔄 | 推错人了 | 调整路由规则 |
| ❓ | 信息不全无法判断 | 补充数据源 |

**节奏建议**：
- HR 经理每周看一次反馈数据
- AI 团队每两周根据反馈调阈值 / 调路由
- 每月一次跨团队复盘会议

**没有这个闭环，3 个月后"主动智能层"就变成"主动招人烦层"——这是这类项目最常见的死法。**

## 十、与组织变革（7×12 → 6×12 → 5×12）的连接

### 风险清单倒推变革落地

让 HR 经理和 AI 团队在班组长复盘会议中问：

> **"如果我们的班组长每周多休 1 天，最让我们担心的会发生什么事？"**

把这些担心**逐条列出来**，应该 80% 都能映射到上面 10 条风险中的某几条。

| 担心场景 | 映射风险 |
|---|---|
| 班组长不在，新员工乱搞 | #7 + #8 |
| 班组长不在，交接漏 | #10 |
| 班组长不在，刀具临界没人盯 | #1 |
| 班组长不在，首件没人监督 | #4 |
| 班组长不在，客户突发要求没人响应 | **新增风险**，进第二批 |

**没有映射到的担心** → 就是第二批风险目录的扩充方向。

### 三件事必须打包做

**主动智能层 + 班组长能力发展体系 + 班长人才储备**——这三件事合起来，才是从 7×12 走向 5×12 的真正答案。

- AI 主动智能层：降低"班组长不在场"的风险
- 班组长能力发展体系：让现有班组长能力上台阶
- 班长人才储备：HR 经理牵头，扩大班长后备人才池

任何一件单独做都不行。

## 十一、重点风险算法详解：客诉复发模式匹配

`CUSTOMER_DEFECT_PATTERN_RECUR` 是 10 条风险中**唯一一条 LLM 真正能发挥独特价值的**——其他 9 条用规则就能解决。值得仔细拆解。

### 11.1 核心难点：什么叫"相似"

精密汽配的客诉同时具备**结构化 + 非结构化**双重特征：

| 结构化部分 | 非结构化部分 |
|---|---|
| 零件号、客户、日期 | 不良现象描述 |
| 物料供应商、批号 | 8D / 根因报告 |
| 刀具型号、机床 ID、程序版本 | 处理措施 / 防再发 |
| 操作工、班组长、班次、温湿度 | 客户抱怨原话 |

如果**只**做语义相似度，会出现：
- **假阳性**：两份客诉文字描述相似（"尺寸超差"），但根因完全不同，结构特征对不上
- **假阴性**：当前生产条件和历史故障批次完全一样（同供应商、同刀具、同机床），但因为现在还没有"客诉描述"（事件还没发生），向量匹配根本没法启动

**正确做法：混合检索 + 多信号打分。**

### 11.2 推荐架构

```
当前生产状态向量
     │
     ├─→ ① 硬过滤：零件号 / 工艺族 / 客户  ──→ 候选客诉集（10-50 条）
     │
     ↓
 ② 多信号打分（结构化为主）
     - 物料供应商 / 批次特征匹配
     - 刀具型号 / 机床 / 程序版本匹配
     - 员工能力 / 班次环境匹配
     - 不良现象语义相似度（向量检索）
     ↓
 ③ Top-3 加权综合分
     ↓
  ④ 阈值判断（默认 0.80，按客户/产品调）
     ↓
  ⑤ LLM 只做"解释"，不做"打分"
     - 用人话讲清楚：当前情况和哪一次客诉相似在哪
     - 给出建议动作
     ↓
  推送到质量班长 + 工艺工程师
```

### 11.3 关键设计原则

#### 原则 1：LLM 不参与最终打分

打分必须可复算、可审计、可单元测试。LLM 在这一步**只做解释生成**。

```python
def compute_recurrence_risk(current_ctx: ProductionContext) -> Optional[RiskAlert]:
    # ① 硬过滤
    candidates = db.query_complaints(
        part_no=current_ctx.part_no,
        process_family=current_ctx.process_family,
        within_months=24
    )
    if not candidates:
        return None

    # ② 多信号打分
    scored = []
    for c in candidates:
        score = _weighted_similarity(current_ctx, c, WEIGHTS)
        scored.append((c, score))

    # ③ Top-3 + 阈值
    scored.sort(key=lambda x: -x[1])
    top = [(c, s) for c, s in scored[:3] if s >= THRESHOLD]
    if not top:
        return None

    # ④ LLM 生成解释（不打分）
    explanation = llm_explain(current_ctx, top)

    return RiskAlert(
        risk_id="CUSTOMER_DEFECT_PATTERN_RECUR",
        confidence=top[0][1],
        evidence=[c.complaint_id for c, _ in top],
        message=explanation,
    )

WEIGHTS = {
    "material_supplier_match":   0.20,
    "material_batch_features":   0.10,
    "tool_type_match":           0.15,
    "machine_id_match":          0.10,
    "program_version_match":     0.15,
    "operator_competency_gap":   0.10,
    "shift_environment":         0.05,
    "semantic_similarity":       0.15,
}
```

权重不是拍脑袋，**是基于历史客诉根因分布反推的**——你们公司最常见的根因是哪几类，权重就向那些信号倾斜。**这件事让工艺工程师做，不是 AI 工程师做**。

#### 原则 2：混合数据源，不只靠向量库

```
结构化字段 → MySQL（精确匹配 + 数值距离）
不良描述 / 8D 报告 → 向量库（阿里云 DashVector 或 pgvector）
特征工程层 → Python 服务负责拼装两边
```

向量化用**通义千问的 embedding 模型**（中文制造业术语友好、阿里云内合规）。

#### 原则 3：阈值不是常量

`0.80` 这个数字一上来就**按客户分**：
- 主机厂客户（高敏感）→ 阈值 0.70
- 一般客户 → 阈值 0.85
- 内部使用 → 阈值 0.90

**为什么**：主机厂一次客诉损失太大，宁可多报；内部小批量宁可少报省得吵。

#### 原则 4：冷启动策略

| 客诉历史样本数 | 策略 |
|---|---|
| < 50 条 | 关闭模式匹配，只做规则触发 |
| 50-200 条 | 启用，但置信度强制乘 0.7 |
| > 200 条 | 完整流水线 |

### 11.4 LLM 输出示例

**输入上下文**：
```yaml

  part_no: BR-2031-A
  customer: 长城汽车

  similarity_score: 0.83
```

**LLM 推送给质量班长的告警**：

>
> 当前 CNC-03 正在加工 BR-2031-A（长城汽车订单），生产条件与 **2025-09-12 客诉 CC-2025-0317** 高度相似：
> - **同供应商**：山东 X 钢

**严重度对应不同审批层级**：

- 高/极高严重度风险新增 → 老板 + AI Lead + 工艺总监三方审批

**这是 IATF 审计的护身符**。

### 12.8 一个反人性但必须做的设计

**禁止"复制粘贴另一条风险的配置"**。原因：用户图省事复制后改两个字保存，结果触发条件、路由、闭环全错位，但表面看上去像是"已配置"。

**正确做法**：新建只能从**官方模板**起步（设备类、工艺类、人员类、物料类、交接类），模板本身经过严格设计。

## 十三、误报反馈闭环数据结构

### 13.1 核心矛盾：你不知道一个告警是不是误报

**场景**：
- 系统告警："刀具寿命临界，建议换刀"
- 班组长收到，**没换刀**，继续生产
- 后续没有客诉、没有质量问题

**这是误报吗？** 你不知道。可能是：
- A. 系统报得对，班组长偷懒，但运气好这次没出事 → 真阳但被忽略
- B. 系统报得过了，那把刀其实还能用 → 假阳
- C. 系统报得对，下批生产中出了事但没归因到这把刀 → 真阳被误判为假阳

**没有 ground truth，反馈数据就是噪音**。所以数据结构必须围绕"如何最大化收集真相"来设计。

### 13.2 五张核心表

#### 表 1：告警事件 risk_alert

```sql
CREATE TABLE risk_alert (
  alert_id       UUID PRIMARY KEY,
  risk_id        VARCHAR(64),
  risk_version   INT,               -- 当时的目录版本（追溯用）
  triggered_at   TIMESTAMP,

  -- 告警时的现场快照（不可变）
  trigger_context JSON,
  -- e.g. {part_no, machine_id, operator_id, tool_id, raw_signals, ...}

  -- 探测细节
  detection_method ENUM('rule','ml','llm','hybrid'),
  confidence_score FLOAT,
  evidence         JSON,

  -- 路由决策日志
  primary_recipient_id VARCHAR(64),
  routing_decision     JSON,
  notification_level   ENUM('info','remind','act','urgent'),

  INDEX idx_risk_time (risk_id, triggered_at)
);
```

**关键设计**：`trigger_context` 必须**完整快照**，不能只存 ID。原因——后续这台机床可能改了配置、操作工换了人，回看历史告警时**必须能还原当时的现场**。

#### 表 2：通知投递 risk_notification

```sql
CREATE TABLE risk_notification (
  notification_id        UUID PRIMARY KEY,
  alert_id              UUID,
  recipient_id          VARCHAR(64),
  recipient_role        VARCHAR(32),
  channel               ENUM('wework','sms','voice','dashboard'),
  sent_at               TIMESTAMP,
  delivered_at          TIMESTAMP,    -- 系统投递成功
  read_at               TIMESTAMP,    -- 用户已读
  is_escalation         BOOLEAN,
  parent_notification_id UUID NULL,   -- 升级链

  INDEX idx_alert (alert_id),
  INDEX idx_unread (recipient_id, read_at)
);
```

**关键洞察**：分清"已发送"、"已投递"、"已读"。
- 平均响应时延 → `read_at - sent_at`
- 谁的告警从来不读 → 这个人需要被关注
- 哪个时段告警延迟高 → 系统/网络/人员问题

#### 表 3：用户反馈 risk_feedback

```sql
CREATE TABLE risk_feedback (
  feedback_id    UUID PRIMARY KEY,
  notification_id UUID,
  alert_id       UUID,
  user_id        VARCHAR(64),

  feedback_type  ENUM(
    'useful',           -- 👍 有用
    'false_positive',   -- 👎 误报
    'wrong_recipient',  -- 🔄 推错人了
    'incomplete_info'   -- ❓ 信息不全
  ),
  feedback_at    TIMESTAMP,
  comment        TEXT,

  INDEX idx_alert (alert_id, feedback_type)
);
```

**重要提醒**：用户反馈是**信号，不是真相**。班组长很累可能误点；新员工可能不敢标 👎；有人会习惯性点 👍。

#### 表 4：闭环状态 risk_closure（系统验证，与用户反馈分离）

```sql
CREATE TABLE risk_closure (
  closure_id  UUID PRIMARY KEY,
  alert_id    UUID,

  closure_state ENUM(
    'pending',           -- 待动作
    'action_taken',      -- 系统观察到预期动作
    'escalated',         -- 已升级
    'expired',           -- 超时未闭环
    'cancelled',         -- 人工取消（带原因）
    'closed_validated'   -- 终态：动作 + 系统验证通过
  ),

  expected_evidence JSON,    -- 我们等的证据：换刀记录？SPC 数据？
  observed_evidence JSON,    -- 实际观察到的：哪些已发生

  closed_at  TIMESTAMP NULL,
  closed_by  VARCHAR(64) NULL,

  INDEX idx_state (closure_state, closed_at)
);
```

**关键差异**：
- `risk_feedback` = 用户嘴里说的
- `risk_closure` = 系统从其他数据源**反查到的**

#### 表 5：真实结果 risk_outcome（最重要的一张）

这是 **ground truth 表**，用于事后判定告警是否准确：

```sql
CREATE TABLE risk_outcome (
  outcome_id     UUID PRIMARY KEY,
  alert_id       UUID,

  actual_outcome ENUM(
    'true_positive',    -- 告警对，问题确认存在
    'true_negative',    -- 告警对，因为采取行动避免了问题
    'false_positive',   -- 告警错，实际没问题
    'unknown'           -- 无法判定
  ),

  determined_at      TIMESTAMP,
  determined_by      VARCHAR(64),
  derivation_method  ENUM('user_feedback','system_inference','human_review'),

  related_quality_event_id     VARCHAR(64) NULL,
  related_customer_complaint_id VARCHAR(64) NULL,

  notes TEXT,

  INDEX idx_outcome_time (actual_outcome, determined_at)
);
```

### 13.3 真值是怎么来的：四种推导方式

| 推导路径 | 结果 | 置信度 |
|---|---|---|
| 告警 + 用户 👍 + 系统看到预期动作 + 后续无质量问题 | True Negative（避免了问题） | 高 |
| 告警 + 用户 👍 + 系统看到动作 + 关联到一个客诉 | True Positive（问题确认） | 高 |
| 告警 + 用户没反馈 + 后续 24h 关联零件出现客诉 | True Positive（被忽略的告警） | 高 |
| 告警 + 用户 👎 + 后续 7 天无任何质量问题 | False Positive | 中 |
| 告警 + 用户没反馈 + 后续无质量问题 | Unknown | 低（**不要用作训练样本**） |

**核心原则**：宁可标 unknown，不要硬判 false positive。**ML 模型用错误的负样本训练，会越练越聋**。

### 13.4 反馈数据如何驱动模型迭代

**每周自动产出报告**：
```
按风险类型：
  TOOL_LIFE_CRITICAL
    告警量: 147 / 周
    Precision: 78%
    平均响应时延: 4.2 min
    用户 👎 率: 12%

按接收人（识别异常）:
  班组长李某某
    告警量: 23
    👎率: 45%  ⚠️ 异常高
    建议：检查推送给他的告警是否相关性低

按时段:
  夜班 0:00-6:00
    误报率比白班高 23%
    建议：检查夜班数据采集是否有延迟
```

**每月一次模型重训练**：
- 输入：过去 90 天的 TP + 确认 FP 样本
- 输出：新版阈值 / 模型权重
- 流程：训练 → 沙箱 dry-run 7 天 → 灰度 → 全量

### 13.5 反馈按钮的工程细节

很多团队把 👍/👎 放在通知消息的最末尾。**结果点击率 < 5%**。

**正确做法**：
- 班组长打开企微看告警 → 滑动消息 → 出现快捷反馈表情
- 或者：长按消息 → 反馈菜单
- 或者：每周一次主动推送"上周这 23 条告警，请帮我们标记"

**不要让用户为反馈付出认知成本**。

## 十四、三个主题如何串成一件事

```
风险目录管理界面（十二）
        │
        │ 配置变更，触发系统更新
        ↓
统一 Agent 引擎（五）
        │
        ├─→ 模式匹配算法（十一）→ 产生告警
        │
        ↓
告警 → 通知 → 闭环 → 反馈数据库（十三）
        │
        │ 每周分析 → 输出洞察
        ↓
回到风险目录管理界面 → 用户调整阈值/路由 → 形成反馈飞轮
```

**三件事其实是一件事**：让风险预警系统**自我进化**。
- 没有第十二节（管理界面），用户改不动 → 系统僵化
- 没有第十三节（反馈闭环），改不知道往哪改 → 系统盲调
- 没有第十一节（高质量算法），改了也没用 → 系统不可信

## 附录 C：客诉结构化抽取 Prompt 设计

> 这是十一节"客诉复发模式匹配"的前置工程。如果历史客诉不被结构化，模式匹配根本无从下手。这一附录给出可直接落地的工程方案。

### C.1 为什么这件事被严重低估

很多团队的第一反应是："丢一个 Prompt 进 Claude/通义千问，让它把客诉抽成 JSON 不就行了？"

**这种做法在 demo 阶段能跑，生产环境必然崩**。原因：

1. **客诉文档格式杂乱**：Word、PDF 扫描、邮件正文、图片转文字混在一起，长度从 200 字到 20 页不等
2. **字段多 + 推断需要上下文**：30+ 个字段一次抽，LLM 准确率会从 95% 跌到 70%
3. **抽错了不知道**：没有 ground truth 就没有质量监控，错误会一直累积
4. **生产成本失控**：上千份历史客诉重抽一次，可能花掉好几千块 token 费用，而且每改一次 Prompt 就要重抽

### C.2 总体策略：多趟（Multi-pass）+ 缓存 + 验证

```
原始客诉文档
     │
     ↓
[Pass 1] 文档分类与预清洗
     - 是不是真的客诉？还是抱怨邮件 / 内部记录？
     - 文档结构识别：是 8D 报告？口述记录？信件？
     │
     ↓
[Pass 2] 基础字段抽取（廉价快速）
     - 客户、日期、零件号、不良现象描述
     - 用 Haiku / Qwen-Turbo 这类小模型即可
     │
     ↓
[Pass 3] 根因抽取（高价值，慢但准）
     - 用 Sonnet / Qwen-Max
     - 输出结构化的根因 + 类目
     │
     ↓
[Pass 4] 关联事实抽取（最重要！）
     - 物料供应商、批次、刀具、机床、程序、操作工
     - 这些是模式匹配的核心特征
     │
     ↓
[Pass 5] 措施抽取
     - 8D 的 D5（治标）、D7（治本）
     │
     ↓
[Pass 6] 跨字段一致性校验
     - 抽出的批次号在系统里存在吗？
     - 抽出的刀具型号是已知型号吗？
     │
     ↓
入库（结构化客诉知识库）
```

**为什么多趟比单趟好**：

| 维度 | 单趟抽取 | 多趟抽取 |
|---|---|---|
| 准确率 | 70-80% | 90-95% |
| 模型成本 | 全部走大模型 | 简单字段走小模型 |
| 调试 | 错了不知道哪步 | 每步可独立测试 |
| 增量更新 | 改一个字段全部重抽 | 改哪步只重跑哪步 |

### C.6 评估集（Evaluation Set）

**这是大多数团队跳过、然后付出惨痛代价的环节**。

构建步骤：
1. 从历史客诉中**随机抽样 50-100 条**（不要挑简单的）
2. **工艺工程师人工标注**——这是 Gold Standard，不能让 AI 标
3. 标注时间预算：每条 5-10 分钟，总共 1-2 个工作日
4. 存为 JSONL：`{document, ground_truth}`

每次 Prompt 迭代：
```python
def evaluate_extraction(prompt_version: str) -> EvalReport:
    results = []
    for sample in eval_set:
        predicted = extract_with_prompt(sample.document, prompt_version)
        gold = sample.ground_truth

        for field_name in CRITICAL_FIELDS:
            pred_values = set(item.value for item in predicted[field_name])
            gold_values = set(item.value for item in gold[field_name])

            tp = len(pred_values & gold_values)
            fp = len(pred_values - gold_values)
            fn = len(gold_values - pred_values)

            results.append({
                "field": field_name,
                "precision": tp / (tp + fp) if (tp + fp) else None,
                "recall": tp / (tp + fn) if (tp + fn) else None,
            })
    return aggregate(results)
```

**质量门槛**：
- 任何关键字段 P/R < 85% → Prompt 不能上线
- P/R 在 85-95%：人工复核兜底，可以上线
- P/R > 95%：可以做自动入库（仍建议抽样复核）

### C.7 常见失败模式与应对

| 失败模式 | 应对 |
|---|---|
| LLM 凭空捏造数值 | Prompt 强制 source_text + 上线后做 regex 校验：source_text 必须出现在原文中 |
| 同一字段抽出多个不同值 | 在 Prompt 中明确"列出所有"+ 后处理去重 |
| 中文制造业术语理解偏差 | Few-shot 示例中放典型术语 + 维护一个领域词表（"切深"≠"切宽"等） |
| 表格内容被错误解析 | Pass 1 识别表格结构，转成 markdown 表后再喂下一 Pass |
| 扫描 PDF 中的 OCR 错误 | OCR 后先做字符级清洗（"O"和"0"、"l"和"1" 之类） |
| Prompt 改了一版，旧数据要不要重抽？ | 建立"重抽决策矩阵"：关键字段变化 → 重抽；非关键字段微调 → 不重抽 |

## 附录 D：沙箱回放引擎工程实现

> 这是十二节"风险目录管理界面"的核心引擎，也是确保系统不被坏 Prompt / 错误规则摧毁的最后防线。

### D.1 战略地位

```
风险目录变更 → 沙箱回放（必经之路）→ 灰度上线 → 全量生效
                       ↑
                  最后一道闸门
```

**不要把它当成"测试工具"**——它是生产系统的**强制性安全机制**：
1. **防止微小改动炸毁全公司**：阈值调错一位、路由规则写反，瞬间引发 10000 条误报
2. **让业务人员敢动**：HR 经理 / 工艺工程师如果调阈值就可能引事故，他们就不敢调
3. **是反馈飞轮的支点**：每月模型重训练、每周阈值优化，都依赖沙箱给出可量化结论

**没有沙箱，整个"自我进化"的故事都讲不下去。**

### D.2 四个真正难的问题

#### 难题 1：时间旅行的正确性

回放 5 月 20 日事件时，所有查询必须返回 5 月 20 日时刻的数据，不是今天的。
**这是双时态（bitemporal）问题，不是写个 SELECT 能解决的。**

#### 难题 2：副作用隔离

沙箱必须能完整跑流水线（路由、LLM、闭环），但**绝对不能**：发企微通知、写生产表、触发外部 API、影响真实用户。同时要测的东西不能 stub 太多，否则结论不可信。

#### 难题 3：LLM 不确定性

LLM 输出有随机性。同输入跑两次输出不同 → 用户上午看 47 条告警，下午看 51 条 → 失去信任。

#### 难题 4：性能

7 天 × 40 产线 × ~1000 事件/线/天 = **28 万次评估**。
**目标：< 30 秒返回结果**。

### D.7 第四层：LLM 确定性策略

```python
class DeterministicLLMClient:
    def __init__(self, base_client, cache_db):
        self.base = base_client
        self.cache = cache_db

    def call(self, prompt: str, model: str, temperature: float = 0.0):
        cache_key = sha256(f"{model}|{temperature}|{prompt}".encode()).hexdigest()
        cached = self.cache.get(cache_key)
        if cached:
            return cached.response

        response = self.base.call(prompt, model, temperature)
        self.cache.set(cache_key, {
            "response": response,
            "model": model,
            "temperature": temperature,
            "called_at": now(),
        })
        return response
```

**沙箱启动时强制**：`temperature=0` + 走 deterministic cache。

**Cache key 必须包含**：`model_version | temperature | prompt_hash`。Prompt 改动 → hash 变 → 缓存自动失效。

```python
    fingerprint = lambda a: (a.trigger_event_id, a.risk_id)

    current_set = {fingerprint(a): a for a in alerts_current}
    proposed_set = {fingerprint(a): a for a in alerts_proposed}

    removed = [current_set[k] for k in current_set.keys() - proposed_set.keys()]

        if current_set[k].routing != proposed_set[k].routing or \

```

### D.9 性能优化

| 阶段 | 朴素 | 优化后 | 技术 |
|---|---|---|---|
| 事件读取 | 5-10 秒 | < 1 秒 | 分区扫描 + 流式游标 |
| 规则评估 | 60-120 秒 | 5-10 秒 | 按产线并行 + 早终止 |
| 时点快照 | 14000 秒 | < 5 秒 | snapshot + 增量 + LRU 缓存 |
| LLM 调用 | 每次 1-3 秒 | < 1ms 命中 | deterministic cache |

**关键技术**：
- **流式处理**：不全量加载事件到内存
- **产线级并行**：ProcessPoolExecutor，8 worker
- **快照查询缓存**：同沙箱运行内 (entity_id, hour) → snapshot
- **硬过滤早终止**：风险规则的硬过滤先评估，不满足直接跳过

### D.10 七大陷阱与应对

| 陷阱 | 后果 | 应对 |
|---|---|---|
| 回放漂移 | 当前数据被追溯修改，回放失真 | 检测：实体 modified_after_replay_time 时警告 |
| 级联依赖 | 规则 A 影响 B 的输入 | 拓扑排序按依赖跑 |
| 外部 API 状态 | 客户 EDI 等无法时间旅行 | 缓存历史响应 / mock / 标记不可沙箱化 |
| 数据保留期 | 老数据被清理 | 定义"沙箱回放最大窗口" = 保留期 - 余量 |
| LLM 缓存中毒 | 错误 Prompt 输出被反复用 | Cache key 必含 prompt_version |
| 性能退化 | 朴素实现跑几小时 | 性能基准测试入 CI |
| 虚假信心 | 沙箱通过 ≠ 生产无事 | 沙箱必要不充分，配合灰度 + 自动回滚 |

## 附录 E：路由决策算法

> 核心命题：路由是问责分配，不是任务派单。"路由不公平 → 推卸责任"是这套系统最容易踩的人际雷区。

### E.1 战略地位

路由系统的核心质量标准不是"准"，而是 **"可解释 + 可申诉 + 可审计"**。

四种典型不公平后果：

| 现象 | 后果 |
|---|---|
| 同一班组长总收到告警 | 第一个人开始怠工/离职 |
| 漏推给应负责的人 | 出事后扯皮："系统没通知我" |
| 派给能力不达标的人 | "你为什么把这事派给我，我又不会" |
| 多人同时收到同一告警 | 都以为别人在处理，都不动 |

### E.2 四个真正难的问题

1. **实时上下文比静态规则多 100 倍信息**：在岗、工位、当前告警数、能力档、冷却状态等多维并发查询
2. **能力矩阵的微妙性**：能力差不一定不派，但派的方式不同（独自 vs CC 班组长 vs 完全升级）
3. **升级链不能写死**：分风险类型，分时间窗口，分当事人状态
4. **负载均衡 vs 责任不可越界**：负载只在"职责范围内"平衡，不能跨界

### E.3 整体架构：静态责任矩阵 + 动态评分

```
告警触发
    ↓
[Step 1] 责任矩阵 → 候选池 (eligible pool)
    ↓
[Step 2] 实时可用性过滤 → 可用池 (available pool)
    ↓
[Step 3] 多因子评分 → 排序
    ↓
[Step 4] 主备分配（主 + 备 1-3）
    ↓
[Step 5] 决策审计日志
    ↓
推送 + 启动升级倒计时
```

### E.6 评分函数

```python
def compute_routing_score(person, alert, ctx) -> tuple[float, dict]:
    breakdown = {}

    # 责任匹配度（0-1）
    breakdown["responsibility_match"] = 1.0 if person.role == alert.required_role else 0.5

    # 工位邻近度（0-1）
    breakdown["station_proximity"] = compute_proximity(
        person.current_station, alert.trigger_station
    )

    # 工序能力（达标 1.0，边缘 0.7，不达标 0.3）
    competency = ctx.capability_matrix.get(person.id, alert.required_competency)
    if competency >= REQUIRED:
        breakdown["competency"] = 1.0
    elif competency >= REQUIRED * 0.8:
        breakdown["competency"] = 0.7
    else:
        breakdown["competency"] = 0.3

    # 负载（反向）
    breakdown["load_factor"] = max(0, 1 - 0.15 * person.active_alerts)

    # 历史响应率
    breakdown["response_rate"] = person.response_rate_7d

    # 认知连续性（最近 1h 处理过同类 +0.2）
    recent_similar = ctx.has_handled_similar(person.id, alert.risk_type, within_minutes=60)
    breakdown["continuity_bonus"] = 0.2 if recent_similar else 0.0

    # 临下班惩罚
    minutes_to_shift_end = (person.shift_ending_at - now()).total_seconds() / 60
    response_window = alert.expected_response_minutes
    if minutes_to_shift_end < response_window * 1.5:
        breakdown["shift_end_penalty"] = 0.3
    else:
        breakdown["shift_end_penalty"] = 1.0

    weights = WEIGHTS_BY_RISK_TYPE[alert.risk_type]
    score = sum(breakdown[k] * weights[k] for k in breakdown)
    return score, breakdown
```

### E.8 五种响应状态

```python
class ResponseState(Enum):
    NO_RESPONSE        = "no_response"        # 完全没响应
    READ_NO_ACTION     = "read_no_action"     # 看了没动作
    ACKNOWLEDGED       = "acknowledged"        # 明确接手
```

不同 state 触发不同升级行为：
- `NO_RESPONSE` → 时间到自动升级
- `READ_NO_ACTION` → 软提醒"还在处理吗？" + 计时
- `ACKNOWLEDGED` → 暂停计时器，等闭环
- `HANDED_OFF` → 直接路由到目标人，重启计时
- `REFUSED` → 立刻升级，移出本告警的链

## 附录 F：MCP Server 封装现有 ERP/MES/WMS 实战指南

> 这是 IT 团队接下来 2-3 个月的具体动作纲领。做对了，未来切换 Agent 框架几乎零成本；做错了，会重写两遍。

### F.1 战略意义

**短期 vs 长期对比**：

| 维度 | 直接做 Dify 插件 | 先做 MCP Server |
|---|---|---|
| 短期开发速度 | 快 1-2 周 | 慢 1-2 周 |
| 切换 OpenClaw 时 | 重写一遍 | 零成本 |
| 接入百炼 Agent 时 | 重写一遍 | 零成本 |
| 接入 Claude / GPT 时 | 重写一遍 | 零成本 |
| 多个 Agent 共享 | 不行 | 天然支持 |
| 6 人 IT 团队的维护成本 | 长期高 | 一次性投入 |

用户已采用 Dify + OpenClaw 双引擎，**没有 MCP 这个选择实际上不存在**。

### F.2 MCP 架构基础

```
┌─────────────────────────────────────┐
│  Agent 框架 (Dify / OpenClaw / 等)   │   ← MCP Client
└──────────────┬──────────────────────┘
               │ MCP Protocol (JSON-RPC over stdio/HTTP)
               ↓
┌─────────────────────────────────────┐
│  MCP Server                         │
│  - Tools（可调用动作）              │
│  - Resources（可读资源）            │
│  - Prompts（预定义提示模板）        │
└──────────────┬──────────────────────┘
               ↓
┌─────────────────────────────────────┐
│  现有 Python ERP/MES/WMS API         │
└─────────────────────────────────────┘
```

**对此项目，95% 是 Tools，5% 是 Resources**（如 SOP 文档、当班次摘要）。

### F.3 八个核心工程决策

#### 决策 1：服务器边界——按业务域拆，不按系统拆

**❌ 不推荐**：一个 ERP Server、一个 MES Server、一个 WMS Server
**理由**：LLM 视角是"业务"，不是"系统"。"刀具寿命"对 LLM 是一件事，但底层数据可能横跨多个系统。

**✅ 推荐 5 个 Server**：

| Server | 包含的能力 | Owner |
|---|---|---|
| `mcp-production` | 工单、排程、生产状态 | 熟 MES 的人 |
| `mcp-quality` | SPC、首件、客诉、不良追溯、8D | 同上 + 工艺工程师 |
| `mcp-equipment` | 机床、刀具寿命、维护记录 | 熟设备/刀具系统的人 |
| `mcp-people` | 出勤、能力矩阵、培训 | 熟 HR 系统的人 |
| `mcp-material` | 物料批次、库存、供应商 | 熟 ERP/WMS 的人 |

**6 人团队，每人负责 1 个 Server，留 1 人做共享基础设施。**

#### 决策 2：工具粒度

**❌ 太粗**（不安全）：
```python
def execute_query(sql: str) -> dict
```

**❌ 太细**（LLM 选不准）：
```python
def get_tool_remaining_life(tool_id: str) -> float
def get_tool_machine_id(tool_id: str) -> str
```

**✅ 业务有意义的复合动作**：
```python
def get_tool_state(tool_id: str, include_history: bool = False) -> ToolState
def get_machine_current_context(machine_id: str) -> MachineContext
def query_complaints_similar_to(production_context: dict, top_n: int = 5) -> list
```

**经验值**：每个 Server 暴露 8-15 个工具，全公司 40-60 个。超过 100 个，LLM 选错率上升。

#### 决策 3：认证 / 授权

**双层认证架构**：

```
Agent → MCP Server: 服务账号认证（机器到机器）
              + acting_as_user_id（每次调用必传）
              ↓
MCP Server 内部：检查 acting_as_user 是否有权限
              ↓
          调用业务 API（带原始用户身份）
```

**实现规范**：
```python
@tool
def get_employee_capability_matrix(
    employee_id: str,
    acting_as_user_id: str,  # 必传，所有工具都有
) -> CapabilityMatrix:
    if not auth.can_view_capability(acting_as_user_id, employee_id):
        raise PermissionError(...)
    audit.log("mcp.get_employee_capability", acting_as_user_id, ...)
    return capability_service.get(employee_id)
```

**关键原则**：
- LLM 不应该通过 Agent 看到真人也看不到的数据
- 每次调用都进审计日志
- 权限规则继承现有 ERP 的 RBAC，不要新建一套

#### 决策 4：工具描述（Description）

### F.4 完整工具实现示例

```python
from mcp.server import Server
from mcp.types import Tool
from pydantic import BaseModel, Field

class ToolStateResponse(BaseModel):
    tool_id: str
    tool_type: str
    remaining_life_pct: float = Field(ge=0, le=100)
    is_active: bool
    current_machine_id: str | None
    current_workstation: str | None
    last_changed_at: str
    history: list[dict] | None = None

@server.tool()
async def get_tool_state(
    tool_id: str,
    acting_as_user_id: str,
    include_history: bool = False,
) -> ToolStateResponse:
    """
    查询某把 CNC 刀具当前状态。

    适用场景：
    - 用户问"X 刀具还能用吗"、"X 刀具寿命剩多少"
    - 需要知道刀具是否已装机、装在哪台机床
    - 排查质量问题需要了解涉事刀具的当前状态

    不适用场景（请用其他工具）：
    - 想看刀具历史变更轨迹超过 10 条 → 用 get_tool_lifecycle_events
    - 想批量查多把刀具 → 用 query_tools_by_filter

    Args:
        tool_id: 刀具唯一编号（如 T-2031-A07）
        acting_as_user_id: 调用者用户 ID（必传，用于权限/审计）
        include_history: 是否包含最近 10 条事件历史

    返回字段：
        tool_id, tool_type, remaining_life_pct (0-100),
        is_active, current_machine_id, current_workstation,
        last_changed_at, history (仅当 include_history=True)

    错误处理：
    - 刀具 ID 不存在 → 抛 NotFoundError，请向用户询问准确编号
    """
    # 1. 参数校验
    if not tool_id or not tool_id.startswith("T-"):
        raise MCPError(
            code="INVALID_PARAMETER",
            message=f"tool_id 格式应为 'T-XXXX'，收到 '{tool_id}'",
        )

    # 2. 权限检查
    if not auth.can_view_tool(acting_as_user_id, tool_id):
        raise MCPError(
            code="PERMISSION_DENIED",
            message=f"用户 {acting_as_user_id} 无权查看刀具 {tool_id}",
        )

    # 3. 缓存检查
    cache_key = f"tool_state:{tool_id}:{include_history}"
    cached = await redis.get(cache_key)
    if cached and not include_history:
        audit.log_call(..., cache_hit=True)
        return ToolStateResponse.parse_raw(cached)

    # 4. 业务调用
    try:
        state = await tool_service.get_state(
            tool_id, include_history=include_history
        )
    except NotFoundError:
        raise MCPError(
            code="NOT_FOUND",
            message=f"刀具 {tool_id} 不存在。请确认编号格式（如 T-2031-A07）。",
        )

    # 5. 缓存写入
    if not include_history:
        await redis.setex(cache_key, 30, state.json())

    # 6. 审计日志
    audit.log_call(
        tool="get_tool_state",
        actor=acting_as_user_id,
        params={"tool_id": tool_id, "include_history": include_history},
        cache_hit=False,
    )

    return ToolStateResponse.parse_obj(state)
```

**所有工具都遵循 校验 → 鉴权 → 缓存 → 业务调用 → 缓存写入 → 审计 流水线**。可做成装饰器统一应用。

### F.5 与现有 API 层的关系

```
                ┌→ Web UI ──┐
                ├→ Mobile ──┤
                ├→ EDI ─────┼→ REST API ──┐
                │           │              ├→ Business Logic Layer ──→ MySQL
                └→ Agent ───→ MCP Server ──┘
```

**MCP Server 是适配层，不是业务层**。它做的事：
- 把 LLM 友好的参数翻译成业务 API 调用
- 把业务返回包装成 LLM 友好的结构
- 加上权限、缓存、审计

**绝对不该做**：
- 复制业务规则（"工单已完成则不能改"这类规则只能在业务层写）
- 直连 MySQL（要走业务层 API）
- 维护独立的数据状态

### F.7 八个常见陷阱

| 陷阱 | 后果 | 应对 |
|---|---|---|
| MCP Server 复制业务逻辑 | 数据不一致 | 强约束：只调业务 API，不连数据库 |
| 工具描述写得像代码注释 | LLM 选错工具 | 写描述时把 LLM 当用户 |
| 鉴权用服务账号一刀切 | 数据越权、审计失败 | acting_as_user 必传，每次检查 |
| 错误返回栈追踪 | LLM 瞎处理 | 结构化错误码 + 建议 |
| 缓存对所有数据用同 TTL | 实时数据陈旧 | 分层 TTL |
| 工具粒度太细 | LLM 多步调用乱 | 业务有意义的复合操作 |
| 没有调用审计 | 出事查不出 | mcp_call_log 必建 |
| 一上来做 50 个工具 | 6 人扛不住 | 按域分批 |

### F.8 三个核心结论

1. **MCP 是适配层，不是业务层**：所有业务逻辑在现有 Python 服务里。MCP Server 永远只做"翻译 + 包装"。
2. **工具描述就是 Prompt 工程**：每个 description 决定 LLM 用不用、用得对不对。技术好的工程师写得未必好——让有 LLM 经验的人 review。
3. **acting_as_user_id 是合规红线**：每个工具都必须接收并校验真实调用者身份。这条做错，IATF 审计翻车。

```python
def batch_features_score(current_ctx, complaint) -> float:
    if not current_ctx.batch_features or not complaint.batch_features:
        return 0.0

    features_to_compare = ["hardness", "carbon_content", "anomaly_flags"]
    scores = []

    for feat in features_to_compare:
        if feat in current_ctx.batch_features and feat in complaint.batch_features:
            cur_val = current_ctx.batch_features[feat]
            cmp_val = complaint.batch_features[feat]

            if isinstance(cur_val, (int, float)):
                scale = FEATURE_SCALES[feat]
                distance = abs(cur_val - cmp_val) / scale
                scores.append(max(0, 1 - distance))
            else:
                scores.append(1.0 if cur_val == cmp_val else 0.0)

    return sum(scores) / len(scores) if scores else 0.0
```

**经验**：批次特征数据通常缺失，权重不能给太高。

### G.2 向量化策略

#### 不要把整篇 8D 报告丢进 embedding

8D 报告 80% 是流程性内容，全文向量化会被噪音淹没。

**正确做法：分字段单独向量化**

```python
class ComplaintEmbeddings:
    defect_phenomenon: list[float]      # 不良现象描述
    root_cause_summary: list[float]      # 根因摘要
    customer_complaint_original: list[float]  # 客户原话
```

**理由**：不同场景用不同向量。
- 当前生产中没有"现象"（事件未发生）但有上下文 → 用 root_cause_summary
- 排查现有不良时有现象但没根因 → 用 defect_phenomenon

#### Embedding 模型选择

| 模型 | 推荐度 |
|---|---|
| 通义千问 text-embedding-v3 | ⭐⭐⭐⭐⭐ 阿里云原生、合规、中文好 |
| BGE-M3 | ⭐⭐⭐⭐ 开源可自托管 |
| 阿里云 PAI-Rec embedding | ⭐⭐⭐ |
| OpenAI text-embedding-3 | ❌ 数据出境，禁用 |

**推荐通义千问 text-embedding-v3**。

#### 文本预处理

**做**：
- 去除 8D 模板文字（"D1: 团队组建"等）
- 统一术语（"刀具寿命"和"刀寿"归一）

**不做**：
- 分词
- 去除停用词
- 关键词抽取替代向量

**现代 embedding 模型自己处理这些更好**。

#### 索引选择

5 年总共 1000-5000 条客诉的规模：

**推荐**：阿里云 DashVector（托管），或直接 in-memory + Faiss。

```
5000 条 × 3 个 embedding 字段 × 1024 维 × 4 字节 = 60MB
内存检索，毫秒级。
```

**不要用 Milvus / Elasticsearch**——杀鸡用牛刀。

#### Embedding 版本控制

模型升级时，所有历史向量要重算：
- 每个 embedding 存储时带 `model_version`
- 检索时只用同版本向量比较
- 升级时分批回填，过渡期允许两版共存

```python
def dynamic_threshold(customer, product_family, target_precision=0.80):
    historical_alerts = get_historical_alerts(customer, product_family)
    sorted_by_score = sorted(historical_alerts, key=lambda a: -a.score)

    cumulative_tp = 0
    cumulative_total = 0
    for alert in sorted_by_score:
        cumulative_total += 1
        if alert.was_true_positive:
            cumulative_tp += 1
        precision = cumulative_tp / cumulative_total
        if precision < target_precision:
            return alert.score

    return sorted_by_score[-1].score
```

```
每月 1 号：
1. 收集上月所有 CUSTOMER_DEFECT_PATTERN_RECUR 告警
2. 收集上月所有真实客诉
3. 对每条真实客诉：
   - 客诉发生前是否预警过？
   - 是 → TP；否 → FN，分析原因
4. 对每条告警：
   - 后续是否真发生？
   - 是 → TP（确认）；否 → 可能成功避免 / 误报，调查
5. 计算 precision / recall / F1
6. 某指标连续 3 月下滑 → 触发权重重训
```

**自动化报表 SQL**：

```sql
SELECT
    COUNT(*) FILTER (WHERE outcome = 'true_positive')   as tp,
    COUNT(*) FILTER (WHERE outcome = 'false_positive')  as fp,
    COUNT(*) FILTER (WHERE outcome = 'false_negative')  as fn,
    COUNT(*) FILTER (WHERE outcome = 'true_positive') * 1.0
        / NULLIF(COUNT(*) FILTER (WHERE outcome IN ('true_positive', 'false_positive')), 0)
        as precision,
    COUNT(*) FILTER (WHERE outcome = 'true_positive') * 1.0
        / NULLIF(COUNT(*) FILTER (WHERE outcome IN ('true_positive', 'false_negative')), 0)
        as recall
FROM customer_defect_pattern_results
WHERE created_at >= DATE_SUB(NOW(), INTERVAL 1 MONTH);
```

### G.7 反模式

| 反模式 | 后果 |
|---|---|
| 用 LLM 直接判断"这两条客诉相似吗" | 慢、贵、不确定、不可解释 |
| 单一阈值打天下 | 主机厂误报疯狂 / 一般客户漏报 |
| 全文向量化 8D 报告 | 信号被流程性内容稀释 |
| 用 OpenAI embedding | 数据出境，IATF 审计不过 |
| 冷启动期硬上线 | 误报满天飞，用户失去信任 |
| 权重一年不调整 | 业务变了，算法没跟上 |
| 没有跨客户迁移机制 | 新客户长期没保护 |
| 语义相似度权重 > 0.4 | 字面相似但工程无关的客诉乱匹配 |

### G.8 三个核心结论

1. **8 个信号、8 个相似度函数、加权求和**：不是高级算法，是工程。每个信号的相似度函数都要单独打磨，**这才是工艺工程师的真正贡献点**。
2. **权重不是终点，是起点**：方法 1→2→3 循序渐进。3 年内别想跳到方法 4。
3. **冷启动期要敢于关闭功能**：前 50 条客诉之前应该是关的。强行启用是在用误报教坏用户对系统的信任。

## 附录 H：告警分级、升级链与消息聚合工程化

> 这是整个主动智能层的"输出层"——前面所有工作的成败，最终都体现在用户收到一条告警那 3 秒钟的体验上。

### H.1 核心洞察：告警是个生命周期

告警不是"事件 → 推送"的一次性动作。每条告警是一个**多状态、可演化的对象**：

```
[创建] → [评估级别] → [合并/抑制判断] → [初次投递] → [等待响应]
                                                          ↓
                                              ┌───────────┼───────────┐
                                              ↓           ↓           ↓
                                          [已确认]    [无响应]    [转交]
                                              ↓           ↓           ↓
                                          [处理中]    [升级]      [新接收人]
                                              ↓           ↓           ↓
                                              └─────→  [闭环]  ←─────┘
```

**目标**：让每条告警以最低打扰成本走到闭环，同时绝不漏掉真问题。这两个目标天然冲突，下面所有工程都在调和它们。

### H.2 级别决策算法（动态，不写死）

```python
def decide_alert_level(risk_def, context) -> AlertLevel:
    base_level = risk_def.base_level
    adjustments = []

    # 临下班 → 升级
    if context.minutes_to_shift_end < 30 and risk_def.requires_action:
        adjustments.append(("near_shift_end", +1))

    # 主机厂客户 → 升级
    if context.customer_tier == "OEM_AAA":
        adjustments.append(("high_value_customer", +1))

    # 7 天内同根因复发 → 升级
    if context.has_recent_same_root_cause(within_days=7):
        adjustments.append(("recurring_pattern", +1))

    # 接收人已超载 → 降级
    if context.recipient.active_alerts > 5:
        adjustments.append(("recipient_overloaded", -1))

    # 已有同类活跃 → 降级
    if context.has_open_alert_same_type(window_min=30):
        adjustments.append(("duplicate_active", -1))

    adjustment_total = sum(delta for _, delta in adjustments)
    final_level = clamp(base_level + adjustment_total, INFO, URGENT)

    # 高严重度有"地板"
    if risk_def.severity == "high" and final_level < REMIND:
        final_level = REMIND

    return final_level, adjustments
```

**关键设计**：基线级别是配置（YAML），调整因子是代码；调整不超过 ±2 级；高严重度有地板；每次调整记录原因。

### H.4 抑制（Suppression）

抑制和聚合的区别：聚合是"合并发"，抑制是"根本不发"。

```python
def should_suppress(alert, context) -> Optional[SuppressionReason]:
    # 1. 重复抑制
    if context.recently_alerted(
        recipient=alert.primary_recipient,
        risk_id=alert.risk_id,
        entity_id=alert.entity_id,
        within_min=alert.risk_def.cooldown_minutes,
    ):
        return SuppressionReason("duplicate", "30min 内已就此事告警")

    # 2. 处理中
    if context.has_open_alert_being_handled(
        risk_id=alert.risk_id, entity_id=alert.entity_id
    ):
        return SuppressionReason("in_progress", "已有人正在处理")

    # 3. 速率限制
    if alert.primary_recipient.alerts_in_last_30min > 8 and alert.level <= REMIND:
        return SuppressionReason("rate_limit", "30min 内已 8 条告警")

    # 4. 维护窗口
    if context.is_in_maintenance_window(alert.entity_id):
        return SuppressionReason("maintenance", "该设备处于计划维护")

    # 5. 已知问题
    if context.is_known_issue(alert.risk_id, alert.entity_id):
        return SuppressionReason("known_issue", "已记录为已知问题")

    return None
```

**铁律**：
- urgent 级别永不抑制
- 抑制必须留痕（写库不发推）
- 每周报告抑制率，> 30% 说明设计有问题

### H.7 风暴保护（Storm Protection）

#### 三层保护

**第一层：源头熔断**

```python
class AlertCircuitBreaker:
    def should_break(self, new_alert) -> bool:
        self.window_alerts = [
            a for a in self.window_alerts
            if a.created_at > now() - timedelta(minutes=1)
        ]
        self.window_alerts.append(new_alert)

        # 1 分钟 > 100 条 → 熔断
        if len(self.window_alerts) > 100:
            return True

        # 同类型 1 分钟 > 30 条 → 熔断该类型
        same_type = sum(1 for a in self.window_alerts if a.risk_id == new_alert.risk_id)
        if same_type > 30:
            return True

        return False
```

熔断后：新告警入"风暴桶"，给管理员 urgent 通知，等人工解除。

**第二层：自适应聚合**

```python
def is_recipient_in_quiet_hours(recipient, alert_time) -> bool:
    if alert.level == URGENT:
        return False

    last_shift_end = recipient.last_shift_ended_at
    if last_shift_end and (alert_time - last_shift_end) < timedelta(hours=8):

def route_with_quiet_hours(alert, primary_recipient):
```

### H.13 三个核心结论

1. **告警是生命周期，不是投递**：从创建到闭环可能经历 10 个状态。把状态机做扎实，比把 LLM 调精细更重要。
2. **聚合 + 抑制是产品，不是优化**：不做这两层，前面所有算法精度再高，用户也会因告警淹没而关闭通知。
3. **风暴保护和 Quiet Hours 不是 nice-to-have**：生产 1 年内一定会遇到风暴；班组长一定会在睡觉时被无意义打扰。这两块没做，系统会以最丢脸的方式失败。
