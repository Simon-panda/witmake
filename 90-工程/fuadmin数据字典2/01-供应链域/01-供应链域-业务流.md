# 01-供应链域 · 业务流（代码验证版）

> 生成: 2026-07-24 | 来源: 后端 api.py/model.py 实证 | 总览: [[fuadmin数据字典2总览]]



# A1 供应链域-采购+结算 业务流（代码验证版）

## 1. 采购申请→采购订单主链（PR→PO）
表链路: generator_purchase_requisition(requisition_number) → generator_purchase_requisition_detail(purchase_requisition_id 挂申请单) → [approval_process JSON 审批, state 1已申请→2已复核→3已批准] → generator_purchase_order(order_number) → generator_purchase_order_detail(purchase_order_id 挂订单, purchase_requisition_detail_id 回链申请行, supplier_material_map_id 协议价映射)
说明: 申请单由需求部门创建并走 JSON 审批流（state 枚举经代码行内注释确认）；订单行通过 purchase_requisition_detail_id 回链申请行，实现"申请→订单"行级追溯；supplier_material_map_id 指向供应商-物料协议价映射确定单价。已用 purchase_requisition/model.py 与 purchase_order_detail 骨架验证。锚点提示与代码一致。

## 2. 订单审批与到货入库回写链
表链路: generator_purchase_order(state 审批状态) → generator_purchase_order_detail(state 到货状态: 1未到货/2全部到货/3部分到货/1000退换货, stock_quantity 累计入库量)
说明: purchase_order/api.py(2262-2331)入库接口验证：next_stock_quantity = 当前 stock_quantity + inbound_quantity 累计回写，并与 quantity 比较自动置明细 state（满量→2全部到货，否则→3部分到货）；满量后拒绝超量入库。锚点"入库(stock_quantity 累计回写)"验证成立。

## 3. 订单附件/发票凭证链（修正锚点）
表链路: generator_purchase_order_detail ↔ generator_order_detail_document_mapping(purchase_order_detail_id + document_id M2M中间表, actual_quantity 实际到货数量) ↔ generator_purchase_order_document(doc_type 附件类型, doc_number 附件编号, state 0草稿/1未支付/2部分支付/3全部支付)
说明: purchase_order_document/model.py 验证：doc_number 是附件自身编号（verbose"附件编号"，help"如发票号等"），并非挂订单号；附件与订单明细通过 OrderDetailDocumentMapping 中间表多对多关联。**修正锚点提示**："doc_number挂订单号"不准确，实际关联走 M2M 中间表。

## 4. 付款申请→付款记录链
表链路: generator_payment_application(purchase_order_id 主链挂订单, settlement_bill_id 次链挂结算单, state 0未申请/1已申请/2审批中/3已批准/100取消) → generator_payment_record(payment_application_id, amount 付款金额, pay_time, pay_user) → 回写 generator_purchase_order.paid_amount/due_amount
说明: purchase_order/model.py 验证 PaymentApplication.purchase_order FK（锚点成立），另有 settlement_bill FK 指向结算单（未启用链路预留）；api.py 中 _derive_payment_application_status 按已批准申请金额合计≥订单总价判定"已结清"。

## 5. 结算链（建成未启用，24表全0行）
表链路: generator_settlement_bill(bill_number 唯一, state 0草稿/1处理中/100已作废) → generator_settlement_bill_detail(settlement_bill_id, purchase_order_detail_id + source_purchase_order_detail_id 快照 + source_snapshot JSON) → generator_settlement_invoice(settlement_bill_id, invoice_code/invoice_number) → generator_settlement_invoice_detail(settlement_invoice_id + settlement_bill_detail_id) → generator_settlement_payment_allocation(payment_record_id × settlement_bill_detail_id) → generator_settlement_invoice_payment_allocation(settlement_payment_allocation_id × settlement_invoice_detail_id)
说明: settlement_bill/model.py 验证：结算行从采购订单明细分摊，保留来源 ID 与不可变快照防止源单变更；数量口径 quantity_basis=order_quantity(按订单)/inbound_quantity(按入库)；付款经两级分摊（付款记录→结算行→发票行）实现精确核销。该模块仅有 model.py 无 api.py/router.py，数据库 24 表全 0 行，判定建成未启用。

## 6. 历史审计流（全模块通用）
表链路: 各业务表 OperationHistoryMixin + HistoricalRecords → generator_historicalpurchase*(id 原样快照, history_id 主键, history_date, history_type +/-/~, operation_id UUID 归组, operation_label 操作标签, history_user_id 操作人)
说明: api.py 的 HistoryGroupSchema/group_history_events 验证：同一次业务操作产生的多表历史记录共享 operation_id，前端按组展示操作事件；锚点无冲突。

## 7. 多站点平行分表流
表链路: 智机(主表无后缀) / 治通(_zt) / 广汇(_gh) / 泰峰(_tf) 四套平行表 + generator_purchase_order.order_belong 归属标识 + _copy1 数据库层站点备份副本
说明: model.py 分区注释明确四套站点模型结构同构；api.py 按 mode 参数切换模型（_get_related_models_by_mode）；_copy1 表仅有数据库骨架无代码模型，为历史迁移/备份副本，不参与在线业务。


# A2 供应链域核心业务流（仓储/物流/供应商/付款/退货）

## 1. 采购到货入库链
表链路: generator_purchase_order_detail → generator_warehouse_transaction（stock_operation_type=0入库/4其他入库）→ generator_warehouse_transaction_detail（warehouse_transaction_id 关联，purchase_order_detail_id 回写）→ generator_warehouse_inventory（库存数量回写）
说明: 仓管员基于采购订单明细创建入库单，明细行记录到货数量与库位，同步更新采购订单明细的已到货数量与到货状态（全部到货/未全部到货），并回写仓库库存台账。入库按钮自动把经办人设为当前用户、主单状态置为已入库。

## 2. 申请出库链（项目物料）
表链路: generator_project_material_summary_detail（project_qrcode 匹配）→ generator_warehouse_transaction（stock_operation_type=3申请出库→1出库）→ generator_warehouse_transaction_detail（state 4未出库→5已出库）→ generator_warehouse_inventory（扣减）
说明: 申请出库单按入库二维码匹配项目物料汇总明细，自动带出项目名称/项目号/申请人作为领料人；出库完成后扣减库存，明细结存数量 remaining_quantity 同步更新，并向仓库管理员发送企微通知。

## 3. 物流结存流转链
表链路: generator_logistics_waybill（receipt_number）→ generator_logistics_transaction_table（logistics_waybill_id 关联；product_stock_id、balance_mode_id 关联）→ generator_logistics_product_stock（结存量）；期初由 generator_logistics_beginning_record 建账
说明: 物流员登记收/送货单后，在流转表逐笔记结存流水，结存方式字符串如"毛坯收入(入库)(仓库结算)"，第一个括号判出入库、第二个括号判结算方式。产品库存按公司→产品→零部件三级分类维护仓库/客户/冻结三套结存量。

## 4. 付款申请-付款链
表链路: generator_purchase_order → generator_payment_application（purchase_order_id / settlement_bill_id 关联，state 审批流 0→1→2→3）→ generator_payment_record（payment_application_id 关联）→ 回写 generator_purchase_order.paid_amount/due_amount
说明: 采购员对采购订单或结算单发起付款申请，经审批流批准（state=3）后财务才能录入付款记录；累计付款不得超申请金额，每次付款后重算订单已付/未付金额，并向申请创建人发送付款通知。订单整单取消时联动终止其全部付款申请（state=100）。

## 5. 供应商报价-取价链
表链路: generator_supplier → generator_supplier_material_mapping（supplier_id + purchase_material_id 唯一）→ 采购订单取价 → generator_warehouse_inventory（supplier_material_map_id 溯源）
说明: 采购员在价格中间表维护各供应商对物料的税后单价、税点、最少采购量与有效期；采购下单时按映射取价，入库后库存台账通过 supplier_material_map_id 保留报价溯源。供应商无独立评价表。

## 6. 退货链
表链路: generator_return_order（belong 站点、tracking_number 物流单号）→ generator_return_order_detail（return_order_header_id 关联，qrcode 逐件）→ 黄单/返厂（is_rework_record_generated、is_returned_to_factory）
说明: 外检创建退货主单（编号 TH 前缀，phase=0），逐件扫码登记明细并校验二维码重复；明细记录检查记录与处置状态（0不合格 1合格 2隔离 3报废 4未检查）。物流收货后 phase=1、退货发出后 phase=2；需返工的明细生成黄单（返工记录）。

## 7. 快递轨迹订阅链（未启用）
表链路: generator_logistics_shipment（com+num 唯一）→ generator_logistics_detail_map（shipment_id ↔ purchase_order_detail_id）→ generator_logistics_push_log（shipment_id）
说明: 设计为按快递公司编码+单号订阅第三方轨迹查询，缓存请求/响应原文与派揽件员信息，推送回调落 push_log 供审计重放，detail_map 把快递单绑定到采购订单明细。三张表在库中均为 0 行，功能未启用。
