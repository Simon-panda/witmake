| WP | 内容 | 负责 | 工时 |

## 二、事件 Schema（统一事件流，载荷自包含）

| 字段 | 说明 |
|---|---|
| `event_id` | 全局唯一（`alm_YYYYMMDD_NNNNNN`），业务幂等键组成部分 |
| `event_type` | `equipment.alarm` / `quality.spc` / `tool.life` / `cron.completed` / `system.heartbeat` |
| `severity` | P1 紧急 / P2 重要 / P3 普通 / P4 周报类 |
| `source` | 引擎风险目录条目 ID（溯源用） |
| `ts` | ISO8601 带时区 |
| `scope_hint` | 目标 scope（公司/产线 → `personal:<user>`，依赖 identity_map） |
| `payload` | **自包含**：机床号、报警码、最近读数、30 分钟内出现次数——agent 处理不必回头查 |
| `signature` | HMAC-SHA256（引擎→网关方向） |

**载荷自包含是硬要求**：事件里带足处理所需上下文，agent 被唤醒后直接分析，不为基本信息再发起查询（省 token、降时延）。

## 三、触发过滤规则表（上线闸门）

| # | 规则 | 参数 |
|---|---|---|
| F1 | P1 立即唤醒，不过滤 | — |
| F2 | 同一 source+机床号 30 分钟内重复事件 → 合并计数，不重复唤醒 | 抑报窗口 30 min |
| F3 | P3 批量汇总，每 30 分钟最多唤醒 1 次/scope | 窗口 30 min |
| F4 | P4 不实时唤醒，汇入周报 | — |
| F5 | 夜间 22:00-06:00 非 P1 不推个人，只落库 | — |
| F6 | 单 scope 每日唤醒硬上限 | 20 次/日（超限转人工汇总） |

**过滤目标**：事件→唤醒比 ≤ 20%（即 ≥80% 事件被过滤/合并）。未达此比例不许扩大推送范围。

## 四、紧急度路由（与架构文档"告警三分发"一致）

| 严重度 | 例 | 处理策略 | 通道 |
|---|---|---|---|
| P1 | 停线 / 安全 / 批量不良 | 取消式（立即，打断当前任务） | 企微 + 短信兜底 |
| P2 | 单机床告警 / SPC 超限 | 队列式（当前任务完成后处理） | 小程序内通知 |
| P3 | 刀具寿命预警 | 抑报窗口批量 | 小程序 |
| P4 | 周报类 | 不实时 | 企微周报 |

## 五、W1 数据流（8 步）

```
引擎风险目录判定告警
 → ① 构造事件（自包含载荷）
 → ② 过滤规则引擎（F1-F6）
 → ③ POST 统一接入网关 /events/agent-wake（HMAC 签名）
 → ④ 网关验签 + identity_map 映射目标 scope
 → ⑤ 经 QM core API 触发 webhook wake（fireKey 幂等）
 → ⑥ scope agent 唤醒，按 skill 指引经 MCP 下钻（fuadmin MCP 已实测打通）
 → ⑦ 生成解释 → 按 P 级通道推送（小程序/企微）
 → ⑧ 员工 👍/👎 回写误报闭环（沿用架构既定设计）
```

## 六、W2 数据流与幂等设计

**Hermes 侧（config.yaml，零代码）**：

```yaml
hooks:
  outbound:
    - url: https://fuadmin.internal/api/agent-events
      events: [on_session_end]
      secret_env: HERMES_OUTBOUND_WEBHOOK_SECRET
      timeout: 10
      name: fuadmin-cron-callback
```

**fuadmin 侧**：Django view 做 HMAC 验证（约 20 行，`hmac.compare_digest` 比对 `X-Hermes-Signature-256`）→ 落库 → 驾驶舱展示。

**幂等关键（源码实证）**：Hermes 每次 POST 的 `delivery_id` 都是新 uuid4（含重试），**不能**用作幂等键。幂等键 = `session_id + hook_event_name + extra` 内业务 ID（如 run_id）；`delivery_id` 仅用于日志追踪。接收端对业务键建唯一索引。

## 七、Token 成本估算（量化）

| 项 | 数值 |
|---|---|
| 单次唤醒成本 | input ~8k（系统提示+事件载荷）+ 2-3 轮 MCP 下钻累计 input ~20k + output ~1.5k ≈ **¥0.007-0.01/次**（DeepSeek：input ¥0.27/M、output ¥1.1/M） |
| 过滤后日均唤醒 | ≤30 次（P1 2-5 + P2 10-15 + P3 批量 ~16） |
| 月成本（正常） | ≈ **¥9/月** |
| 月成本（不过滤的风暴情形，300 次/日） | ≈ ¥90/月——金额仍在总盘（¥2,000-4,000/月）3% 以内，但**员工被打扰不可接受** |

结论：过滤规则首先是体验闸门，其次才是成本闸门。

## 八、保活判死与失败兜底

| 机制 | 参数 |
|---|---|
| 心跳 | 引擎每 5 分钟发 `system.heartbeat`；QM 侧最后事件时间 >15 分钟 → "事件通道静默"告警给 IT（苏杨） |
| 死信 | 网关/QM 5xx → 落死信表 → 每 5 分钟重放；连续 3 次失败 → 企微告警 IT |
| 唤醒失败 | 快速失败，**升级人工**（带完整事件上下文），不做"智能"修正 |
| 慢调用警觉 | 预期 500ms 的调用跑 5s → 升级假设排查 |

## 九、验收标准（量化 4 项）

| # | 指标 | 标准 | 对比基线 |
|---|---|---|---|
| 1 | W1 时延 | P1 告警产生 → 小程序收到 agent 解释 ≤ **60 秒** | 轮询方案 5 分钟 |
| 2 | 过滤率 | 事件→唤醒比 ≤ **20%** | — |
| 3 | 幂等 | 同一业务键重复推送（重试/重放）→ 仅 1 条通知 | — |
| 4 | W2 时延 | cron 完成 → 驾驶舱可见 ≤ **30 秒**；连续 3 次失败 → 死信告警必触发 | — |
