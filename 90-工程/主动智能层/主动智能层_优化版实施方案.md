> **文档定位**：在《主动智能层：首批风险清单与统一 Agent 架构方案》基础上的优化实施方案。原方案架构设计正确，本文聚焦于"怎么落地更稳、更快、更少返工"。
> **核心输出**：重新排版的 6 阶段路线图 + 数据就绪度审计 + MVP 风险重选 + 成本模型 + 放行标准。
> **适用对象**：HR 经理、IT 团队负责人、AI 团队、厂长——这是执行层面的路线图。

## 一、30 秒读原方案：哪些保留，哪些调整

| 保留（架构正确） | 调整（落地需要优化） |
|---|---|
| 预测 + 定位统一 Agent 引擎 | 加一个 Phase 0 做基础设施验证 |
| 风险目录 YAML 声明式 | MVP 风险选择换掉一个 |
| 10 条首批风险清单 | 时间线拉长 2x，加数据审计前置 |
| 告警生命周期 + 风暴保护 | 加成本模型、回滚方案、放行标准 |
| LLM 只解释不打分 | 培训前移到 Phase 1 |

**一句话**：原方案的架构设计可以不改一行代码沿用，但实施节奏、前置条件、风险控制需要重新编排。

---

## 二、最核心的优化：6 个阶段替代原来的 3 个

原方案是 Phase 1 → Phase 2 → Phase 3 三阶段。问题在于 Phase 1 的前置工作量（基础设施 + 数据接入 + 告警管道）被压进了同一个"4-6 周"窗口，和 2 个业务风险混在一起，导致时间估计失真。

优化后拆成 6 个阶段，把基础设施和业务风险解耦：

```
Phase 0     Phase 1A    Phase 1B    Phase 2     Phase 3     Phase 4
空壳跑通  → 信任建立  → 核心风险  → 全量上线  → 模型升级  → 组织变革
(2周)      (2周)       (6周)       (8周)       (持续)      (并行)
```

---

### Phase 0：空壳跑通（2 周）

**目标：一条假告警从产生到推送，全链路不丢不漏。**

**做什么：**

1. 部署一个 Python 服务，内含：
   - 一个"Hello World"假风险（hardcode，不查数据源）
   - 告警状态机的基本骨架（CREATED → SENT → ACKNOWLEDGED → CLOSED）
   - 企微推送通道（发到项目组自己的群，不推生产线）

2. 验证以下时序：
   - 告警产生 → 排队 → 推送：< 10 秒
   - 用户点"已确认" → 状态变更 → 日志落库：< 3 秒
   - 超时 5 分钟无响应 → 升级推送到第二人：< 10 秒偏差

3. 部署闭环：
   - 一个 Redis 或 RocketMQ 用于延迟升级队列
   - 一个 MySQL 表（alert + alert_state_transition）
   - 一个最简单的 Web 管理台（哪怕只有一页，能看到今天的告警列表）

**交付物：**

- 企微群收到一条"测试告警"并可点击确认
- 状态流转日志完整入库
- 升级倒计时验证通过（时间扭曲测试）

**为什么 Phase 0 是必选项：**
如果没有这一步，Phase 1 第一次推送真告警时，通道断了 / 状态丢了 / 升级没触发——用户对系统的第一印象就毁了。制造业的信任，一次就够了。

---

### Phase 1A：信任建立——选对第一条风险（2 周）

**目标：让第一个用上系统的班组长说"这东西有用"。**

**做什么：**

上线 3 条"极低成本"风险，验证数据管道可用：

#### R1: SHIFT_HANDOVER_INCOMPLETE（班次交接遗留未闭环）——原 #10

- **数据源**：MES 交接班模块（已有）+ ERP 工单状态（已有）
- **规则**：纯 SQL——交接记录中的待办项，30min 后状态仍为"未处理"
- **推送**：接班班组长 + 交班班组长
- **为什么第一个做**：不需要任何新数据采集，不依赖实时信号，规则等于一条 SQL，误报率极低。它直接解决 7×12→6×12 的交接风险。

#### R2: OPERATOR_COMPETENCY_MISMATCH（员工独立作业但能力不达标）——原 #7

- **数据源**：排班表 + 技能矩阵（HR 系统，已有）
- **规则**：JOIN 两张表，匹配排班工序和技能矩阵的达标状态
- **推送**：班组长（不推员工本人）
- **为什么做**：触动 HR 经理的切身痛点的第一条 AI 应用。不需要传感器，不需要实时信号。一份 Excel 就能验出效果。

#### R3: FIRST_ARTICLE_SKIPPED（首件未检）——原 #4

- **数据源**：MES 工序流转 + 质量检验模块
- **规则**：换刀/换班/换程序事件后，统计已下线件数，交叉查质检记录
- **推送**：操作工 + 巡检员 + 班组长
- **为什么做**：IATF 红线，风险价值明确，规则中等复杂度

**三条风险同时在 1 条产线试点。**

**交付物：**

- 3 条风险在试点产线上运行
- 每条风险过去 2 周的数据回放验证（模拟触发，不等真实事件）
- 班组长每日收到 ≤ 3 条告警（不是 30 条）
- 反馈按钮被点过至少 20 次

---

### Phase 1B：核心风险上线（6 周）

**目标：补上 7 条风险，试点产线跑满 10 条全量。**

**注意事项：每条风险上线前必须做 1 天的"影子模式"——跑在后台，记录"如果上线会推什么"，人工验证 24 小时再开推送。**

**做什么：**

| 风险 | 原编号 | 数据就绪度要求 |
|---|---|---|
| 刀具寿命临界 | #1 | 刀具管理系统需提供实时剩余寿命接口 |
| 同型刀具寿命异常 | #2 | 需 30 天刀具更换历史数据 |
| 设备报警未处理 | #3 | 需机床报警信号实时接入 |
| SPC 趋势违规 | #5 | 需 SPC 系统支持按零件/工序查连续点 |
| 客诉模式复发 | #6 | 需结构化客诉历史 ≥ 50 条，LLM 推理通道 |
| 新员工前 24h | #8 | 需排班系统 + 技能矩阵 |
| 新批次未验证 | #9 | 需来料检验 + 批次上线记录接口 |

**每个风险都有"数据就绪度"条件。不满足的，跳过，不硬上。**

**交付物：**

- 试点产线 10 条风险全部运行
- 每条风险的误报率 < 25%（第一版接受这个数字）
- 闭环率 > 60%
- 企微群日推送量约 15-25 条（含 info 级别日报）

---

### Phase 2：全量上线 + 反馈闭环（8 周）

**目标：从 1 条产线扩展到全厂 40+ 条产线，同时把误报率压到 10%。**

**做什么：**

1. **逐条产线接入**，不批量铺开。每条新产线先跑 3 天影子模式。
2. **周三复盘会**：AI 团队 + 产线班组长 + 质量工程师，15 分钟，看本周误报/漏报 Top 3 案例，现场调阈值。
3. **月度反馈报告**（HR 经理主导）：
   - 各风险类型的 precision / recall
   - snooze 频率异常的班组长
   - 升级链执行率
4. **培训**：分 3 轮
   - 班组长培训：怎么用反馈按钮、怎么指派人、怎么看日报（1h）
   - 操作工培训：告警来了做什么、什么不是告警（30min）
   - HR 经理 + 工艺培训：怎么调风险目录参数、怎么提新风险需求（2h）

**交付物：**

- 40+ 产线全量运行
- 误报率 < 12%，闭环率 > 80%
- 培训覆盖率 100%（核心人员）
- 月度报告模板建立

---

### Phase 3：模型升级 + 自动定位（持续）

**目标：把"事后查根因"的自动定位功能做出来（原方案的 Reactive 模式）。**

这个阶段不是封闭周期的，而是和 Phase 2 并行。

**做什么：**

1. **自动定位 v1**：输入零件号 + 不良现象 → Agent 从 MES/QMS/刀具/SPC 数据里反推根因 + 推荐责任人。
2. **ML 替换纯规则**：刀具寿命预测从 P10 阈值 → XGBoost 回归（需 6 个月以上数据）。
3. **风险目录扩充**：HR 经理和工艺工程师在主复盘会上提新风险，AI 团队评估数据就绪度后依次加入。

**交付物：**

- 自动定位从"查 5 个系统 30 分钟"到"1 个查询 30 秒"
- 3 条以上风险从纯规则升级为 ML 模型
- 风险目录从 10 条扩展到 20+ 条

---

### Phase 4：组织变革对接（与 Phase 2 并行启动）

**目标：回答"到底什么时候可以从 7×12 走向 6×12"。**

**做什么：**

1. **定义放行标准**（和 HR 经理、厂长一起定）：

| 指标 | 目标值 | 数据来源 |
|---|---|---|
| 10 条风险综合误报率 | < 10% | 告警反馈数据 |
| 10 条风险综合闭环率 | > 85% | 告警状态机 |
| 系统可用率（uptime） | > 99.5% | 运维监控 |
| 用户满意度（班组长 NPS） | ≥ +30 | 匿名问卷 |
| 无 P0 事故运行时长 | ≥ 3 个月 | 事故记录 |

2. **分步过渡**：
   - 达标后第 1 个月：选 2 个班组长从 7×12 改 6×12（自愿试点）
   - 第 2-3 个月：扩大到 4-6 个班组长
   - 第 4-6 个月：全量切换
   - 每一步都留回滚点——如果某个月 P0 事故 > 0，暂停扩展

3. **持续监控"不在场风险"**：
   - 每周统计班组长不在场时的：
     - 告警升级次数
     - 未闭环告警数
     - 真实生产异常数
   - 如果这三个数字连续 4 周不升反降，就是 6×12 的最好证据

## 三、数据就绪度审计——每条风险的前置条件

这是原方案完全缺失的一块，也是最容易让项目翻车的。**上线任何一条风险前，先检查数据源能不能打。**

```yaml
数据就绪度审计模板:
  风险ID: TOOL_LIFE_CRITICAL
  依赖数据源:
    - 源: 刀具管理系统
      接口类型: API / DB直连 / 文件导入
      当前状态: [未接入/部分接入/已接入]
      数据完整度: [<50%/50-80%/>80%]
      数据时效: [实时/小时级/天级]
      负责人: 某某某
      就绪动作: "开放刀具剩余寿命查询 API，联调 2 天"
  审计人: IT 负责人
  审计日期: 2026-06-20
  结论: [就绪/待整改后重新审计/暂无数据源]
```

**10 条风险逐条审计。结论为"暂无数据源"的，不要硬上，改用影子模式积累数据。**

## 四、成本模型（MVP 阶段月度估算）

原方案没有成本数字。这里给一个参考模型（基于阿里云 + Dify 企业版 + 自建 Python 服务）：

| 项目 | 月度费用（估算） | 说明 |
|---|---|---|
| ECS（Python Agent 引擎 2 台） | ¥1,200 | 4C8G，包年更划算 |
| RDS MySQL | ¥800 | 告警 + 状态机数据存储 |
| Redis（延迟队列 + 热缓存） | ¥400 | 512MB 基础版即可 |
| 阿里云 PAI（ML 训练） | ¥0（MVP 阶段） | MVP 用规则，不训练，此项暂为 0 |
| Dify Cloud 团队版 | ¥500 | LLM 编排，客诉复发用 |
| 向量数据库（DashVector） | ¥300 | 客诉 embedding 存储 |
| 通义千问 Token 费 | ¥200 | 按客诉复发日调用量 < 50 次估算 |
| 企微推送 | ¥0 | 已有渠道 |
| **月度合计** | **¥3,400** | MVP 10 条风险全量运行 |

**Phase 2 全量（40+ 产线）后，月度可能到 ¥6,000 - ¥10,000，主要增长点是 LLM Token 和训练算力。**

预算建议：先按 3 个月 MVP 申请 ¥10,000 云资源费，跑完 Phase 2 再追加。

## 五、回滚与降级方案——系统挂了怎么办

这是原方案没有谈到但生产必需的部分。

### 三层降级

| 级别 | 触发条件 | 降级动作 |
|---|---|---|
| 一级降级 | Python 引擎不可用 | 告警暂停推送，企微群发一条"系统维护中"，班组长恢复手动巡检 |
| 二级降级 | 数据源（MES/刀具）不可用 | 依赖该数据源的风险规则自动暂停，其他风险继续运行 |
| 三级降级 | 企微推送通道不可用 | 告警写库不推送，Web 管理台保留完整记录，恢复后一次性回放 |

### 手动 SOP

每个班组长手里有一张 A4 纸：**"AI 助手挂了，我这 8 小时要手动盯什么"**。内容就是 10 条风险的手动检查清单——从系统日志反过来写的：

1. 每 2 小时看一次刀具管理系统，剩余寿命 < 20% 的标记换刀
2. 换班 / 换刀后确认首件已检
3. 交接班记录自查
4. ...

**这份 SOP 本身就是风险目录的"人肉版"——它应该在 Phase 1A 就写好，不等到系统宕机了临时编。**

## 六、团队分工：谁做什么，不做什么

| 角色 | 做什么 | 不做什么 |
|---|---|---|
| AI 团队（2-3 人） | Python Agent 引擎、数据接入 MCP、规则编码、ML 模型 | 不定风险优先级（那是 HR + 工艺的事） |
| IT 团队（1-2 人） | 服务器部署、企微通道、数据库、运维监控 | 不调风险阈值（那是业务的事） |
| HR 经理 | 风险优先级拍板、反馈数据周/月回顾、培训安排、7×12→6×12 路线 | 不写代码 |
| 工艺工程师 | 设定初版阈值、审核客诉模式匹配的权重、签延刀决策 | 不写代码 |
| 班组长（试点） | 用反馈按钮、参加周三复盘 | 不调系统参数 |
| 厂长 | 审批放行标准、重大告警升级终判 | 不日常操作 |

## 八、风险清单：这个方案自己的风险

要做主动智能层，这个优化方案本身也有风险，值得先列出：

| 风险 | 概率 | 影响 | 缓解措施 |
|---|---|---|---|
| 数据源接口对接超预期 | 高 | Phase 1B 延期 | 每条风险提前 1 周做数据接口联调，不等到开发阶段 |
| 班组长不点反馈按钮 | 中 | 没数据调阈值 | Phase 1A 选 1 个最积极的班组试点，HR 经理亲自带 |
| LLM 调用费用超预算 | 低 | 月度成本翻倍 | 客诉复发用缓存 + 日调用量封顶 50 次 |
| 刀具管理系统接口不可用 | 中 | #1, #2 无法上线 | 先上 #4, #7, #10 等不依赖刀具数据的风险 |
| 厂长不批预算 | 中 | 项目停摆 | 用 Phase 1A 的真实数据说话（"3 周帮班组长抓了 12 个遗漏交接"） |

## 九、总结：与原方案的差异对照

| 维度 | 原方案 | 优化方案 |
|---|---|---|
| 阶段数 | 3 个 | 6 个（拆解基础设施和业务风险） |
| MVP 风险 | #1 + #4 | #10 + #7 + #4（信任优先，低成本高价值） |
| 前置工作 | 无 | Phase 0 空壳跑通 |
| 数据审计 | 无 | 每条风险上线前强制数据就绪度审计 |
| 时间估计 | 4-6 周 MVP | 4 周 Phase 0+1A，8 周达原 MVP 效果（10 条风险试点线） |
| 成本 | 未提及 | 月度 ¥3,400（MVP），全量 ¥6,000-10,000 |
| 降级方案 | 未提及 | 三层降级 + 手动 SOP |
| 组织变革 | 定性论述 | 定量放行标准 + 分步过渡路线 + 监控指标 |
| 培训 | Phase 2 | Phase 1A 起，试点产线每天 15 分钟站会 |

**原方案的架构设计不需要改**——这是最重要的结论。优化只是让落地更稳、让信任建立更快、让第一推动更容易发生。
