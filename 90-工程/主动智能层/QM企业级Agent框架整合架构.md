> **决策（Simon 2026-08-02）**：以 yc-software/qm 为企业 Agent 框架，40 名骨干人手一个 Agent；入口为三通道——微信小程序 + 企微身份授权 + 网页密码登录（统一身份联邦）。
> **文档定位**：选型依据 + QM 长期性评估 + 四层整合架构 + 权限映射 + 成本与节奏。

## 一、选型结论：OpenWork vs QM

| 维度 | OpenWork（different-ai） | **QM（yc-software / YC 官方）✅ 入选** |
|---|---|---|
| 定位 | 开源版 Claude Cowork，桌面 App + 能力分发 | Multiplayer agent harness，企业多租户协作框架 |
| 成熟度 | 19.9k⭐，2026-01 创建 | 3.9k⭐，2026-07-29 创建（极新，风险见二节） |
| 许可 | 开源（协议待确认） | **MIT**（可私有 fork，无绑定风险） |
| 部署 | 桌面 + 依赖厂商云（api.openworklabs.com） | **完全自部署**（自有云账号），数据不出域 |
| 核心抽象 | workspace + 能力包分享 | **scope（人/房间）级隔离**：记忆/文件/密钥/权限/cron/sandbox |
| Agent 驱动 | opencode；能力经 MCP 暴露给任意客户端 | 同一核心可换 harness：Pi/OpenCode/Codex/Claude Code |
| 后台任务 | 无一等公民 cron | **crons + watches 核心特性** |
| 安全模型 | 桌面策略 | 三档 posture（Strict/Auto/Dangerous）+ 预声明命令硬拒绝 + 全审计 |
| 入口 | 桌面 App | Slack + Web（均不用，改接小程序，见三节） |

**入选理由**：① scope 隔离模型与"40 骨干人手一个 Agent"直接对应；② MIT + private fork + `deploy/layers/` 定制分离，core 与上游字节一致——天然支持"版本冷冻、低频升级"；③ 全接口化（harness/模型/store/sandbox 可换），不被单一供应商锁定；④ 自部署满足 IATF 数据主权。OpenWork 作为管理层桌面能力分发的补充保留观察，不进主架构。

## 二、QM 长期使用评估

**结论：可押注，设 6 个月验证期（至 2027-02），"低升级频率"靠版本冷冻策略实现。**

| 支撑长期使用 | 风险与对冲 |
|---|---|
| MIT 许可，永远可 fork | 项目极新（2026-07-29 创建）→ **版本冷冻**：锁 tag 不追 main，季度用 `update-qm` 合并评估，年升级 ≤4 次 |
| YC 官方 dogfood，维护持续性高 | 无中国 IM 生态（仅 Slack）→ 自研小程序 connector，一次到位，反而是最干净资产 |
| 全接口化：任何一层过时换一层 | Node/TS 栈 vs 团队 Python 栈 → 不改 core（layers 配置 + skills 为 markdown），Python 能力继续投在主动智能层引擎与 MCP |
| layers 定制分离，上游合并冲突最小 | 部署目标原为 fly/aws → 自部署阿里云 ECS，core 无厂商依赖 |

**安全垫**：40 个 scope 配置、组织级 skills、MCP Server、小程序 connector 全在自研层与标准协议上——即使 QM 项目衰退，可整体迁移至任何 harness。验证期观察指标：上游 commit 活跃度、breaking change 频率、社区 connector 生态。

## 三、总体架构：四层 + 共享数据平面

```
┌──────────── 入口层：3 种登录（同一身份的三个载体）────────────┐
│ ① 微信小程序(一线全员) ② 企微身份授权(告警/审批) ③ 网页密码(管理层) │
└───────┬────────────────┬──────────────────────┬───────────┘
        │ OpenID         │ WeCom OAuth          │ password
        └────────────────┼──────────────────────┘
┌──────────▼─── 网关层：统一接入网关 ─────────────────────────┐
│ ①三通道auth验证 ②身份映射→employee_id+dept_level(identity_map)│
│ ③路由(业务→fuadmin / AI→QM / 告警→引擎) ④三通道合一审计(IATF)  │
└─────┬──────────────────┬───────────────────────┬───────────┘
┌─────▼─────┐   ┌────────▼────────┐   ┌──────────▼──────────┐
│ 企业云      │   │ QM Core(Agent层) │   │ 主动智能层引擎(自研)    │
│ fuadmin    │   │ 40个隔离scope    │   │ 风险目录/告警状态机/   │
│ ERP+MES+WMS│   │ harness可换/cron │   │ 风暴保护/反馈闭环     │
└─────┬─────┘   └────────┬────────┘   └──────────┬──────────┘
      └─────────┬────────┴───────────┬───────────┘
           ┌────▼────────────────────▼────┐
           │  MCP Server 层(共享数据平面)    │
           │  刀具/CMM/对刀仪/MES/HR/SPC/报工 │
           │  权限在此统一执行(不下沉到入口)   │
           └────────────────┬──────────────┘
                     MySQL (fuadmin) + 告警库
```

### 身份联邦（三登录→一身份→一 scope）

| 登录方式 | 凭证 | fuadmin 字段 | 就绪度 |
|---|---|---|---|
| 小程序 | wechat_openid / wechat_id | 字段现成，40 人中 38 人已绑 | 🟢 95% |
| 网页密码 | username+password（Django hash） | system_users 本就是 Django 用户表 | 🟢 90% |
| 企微授权 | wecom_userid | 需建 identity_map 表+首次绑定流程 | 🟡 待建 |

**SSO-gate 机制**：网关验证后向 QM Core 传受信身份断言，QM 不另建账号体系——任何入口进入都落到同一 scope、同一份记忆（小程序问一半、网页继续问，上下文连续）。

### 通道×角色匹配

| 角色 | 主用 | 辅用 |
|---|---|---|
| lv6 班长（一线） | 小程序（业务+AI+告警） | 企微（收告警） |
| lv5 主管 | 小程序+企微（审批） | 网页 |
| lv3/lv4 经理/厂长 | 网页（驾驶舱/QM Web UI） | 企微（审批/告警） |
| lv1-2 决策层 | 网页+企微 | — |

### 告警三分发、反馈一闭环

引擎按`严重度×角色`路由：一级紧急→企微+短信兜底；普通→小程序内通知；周报类→企微。任何入口的 👍/👎/🔄 回写同一张反馈表，误报率模型只有一份。

**权限不下沉原则**：通道只是身份载体，授权只在 MCP 层执行一次（dept_level 行级过滤）——未来新增第四、第五种入口，数据权限零改动。

### 6 条关键设计决策

| # | 决策 | 理由 |
|---|---|---|
| 1 | **三入口+身份联邦**：小程序（一线）/企微（告警审批）/网页密码（管理层，含 QM Web UI）；统一接入网关做身份映射与审计 | 通道=身份载体，scope 与记忆跨通道连续；授权只在 MCP 层一次 |
| 2 | **QM scope 与 40 人架构图一一对应**（见四节映射） | 昨天完成的组织架构工作直接复用为 scope 开通清单 |
| 3 | **主动智能层保持独立，不进 QM** | 引擎是机器-facing 监控（7×24、确定性、IATF 审计链），QM 是人-facing 协作——生命周期不同。交汇点：①告警落库→QM agent 经 MCP 下钻解释；②小程序反馈按钮回写误报闭环 |
| 4 | **定时任务分工**：生产告警→引擎 cron；个人助理（日报/纪要/邮件 triage）→QM cron | 各用所长 |
| 5 | **Dify/OpenClaw 归位**：Dify 只做客诉复发分析+RAG；OpenClaw 为 Simon/IT 运维引擎，不对员工 | 员工-facing agent 框架只留 QM，避免双头 |
| 6 | **QM 自部署阿里云 ECS**，与企业云内网可达 MySQL/MCP | 数据不出域 |

## 五、成本与实施节奏

### 成本（40 人规模）

| 项 | 月费 |
|---|---|
| ECS 4C8G ×2 + RDS Postgres 基础版 | ¥800-1,200 |
| LLM token（国产模型，40 人×日均 20 轮） | ¥1,000-2,500 |
| 小程序 AI Tab + QM connector（一次性自研） | 1-1.5 人月 |
| **合计** | **¥2,000-4,000/月** |

### 实施节奏（与 [[人员组织架构与Agent投放规划]] T1-T4 梯队对齐）

```
M1-2  QM POC = T1 生产条线7人 · 小程序AI Tab上线 · harness=OpenCode
M3-4  T2 十二人 · 告警中心上线（订阅消息+企微/短信双通道兜底）
M5-6  T3/T4 全量40人 · posture 分档强制 · 版本冷冻节奏固化
M7+   季度合并上游 · 2027-02 验证期评估 → 宣布长期押注或迁移
```

## 六、风险与盯办事项

| # | 风险 | 盯办 |
|---|---|---|
| 1 | 小程序订阅消息需员工主动订阅且次数受限 | 一级紧急告警：小程序内通知 + 企微/短信双通道兜底 |
| 2 | QM 项目极新，API 可能 breaking | 版本冷冻 + 季度合并，禁止追 main |
| 3 | Node 运维能力（团队主力 Python） | IT 软件小组接管部署运维；AI 小组不动 core |
| 4 | 泰峰 ~60 人 vs 系统 ~30 人 | T2 投放前补录泰峰员工入 fuadmin |
| 5 | QM connector 为自研单点 | 代码+文档入 `deploy/layers/zhiji/`，纳入版本库管理 |
