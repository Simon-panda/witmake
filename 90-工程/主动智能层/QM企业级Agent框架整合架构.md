## 一、选型结论：OpenWork vs QM

| 维度 | OpenWork（different-ai） | **QM（yc-software / YC 官方）✅ 入选** |
|---|---|---|
| 定位 | 开源版 Claude Cowork，桌面 App + 能力分发 | Multiplayer agent harness，企业多租户协作框架 |
| 成熟度 | 19.9k⭐，2026-01 创建 | 3.9k⭐，2026-07-29 创建（极新，风险见二节） |
| 许可 | 开源（协议待确认） | **MIT**（可私有 fork，无绑定风险） |
| 部署 | 桌面 + 依赖厂商云（api.openworklabs.com） | **完全自部署**（自有云账号），数据不出域 |
| 核心抽象 | workspace + 能力包分享 | **scope（人/房间）级隔离**：记忆/文件/密钥/权限/cron/sandbox |
| Agent 驱动 | opencode；能力经 MCP 暴露给任意客户端 | 同一核心可换 harness：Pi/OpenCode/Codex/Claude Code |
| 后台任务 | 无一等公民 cron | **crons + watches 核心特性** |
| 安全模型 | 桌面策略 | 三档 posture（Strict/Auto/Dangerous）+ 预声明命令硬拒绝 + 全审计 |
| 入口 | 桌面 App | Slack + Web（均不用，改接小程序，见三节） |

**入选理由**：① scope 隔离模型与"40 骨干人手一个 Agent"直接对应；② MIT + private fork + `deploy/layers/` 定制分离，core 与上游字节一致——天然支持"版本冷冻、低频升级"；③ 全接口化（harness/模型/store/sandbox 可换），不被单一供应商锁定；④ 自部署满足 IATF 数据主权。OpenWork 作为管理层桌面能力分发的补充保留观察，不进主架构。

## 二、QM 长期使用评估

**结论：可押注，设 6 个月验证期（至 2027-02），"低升级频率"靠版本冷冻策略实现。**

| 支撑长期使用 | 风险与对冲 |
|---|---|
| MIT 许可，永远可 fork | 项目极新（2026-07-29 创建）→ **版本冷冻**：锁 tag 不追 main，季度用 `update-qm` 合并评估，年升级 ≤4 次 |
| YC 官方 dogfood，维护持续性高 | 无中国 IM 生态（仅 Slack）→ 自研小程序 connector，一次到位，反而是最干净资产 |
| 全接口化：任何一层过时换一层 | Node/TS 栈 vs 团队 Python 栈 → 不改 core（layers 配置 + skills 为 markdown），Python 能力继续投在主动智能层引擎与 MCP |
| layers 定制分离，上游合并冲突最小 | 部署目标原为 fly/aws → 自部署阿里云 ECS，core 无厂商依赖 |

**安全垫**：40 个 scope 配置、组织级 skills、MCP Server、小程序 connector 全在自研层与标准协议上——即使 QM 项目衰退，可整体迁移至任何 harness。验证期观察指标：上游 commit 活跃度、breaking change 频率、社区 connector 生态。

## 三、总体架构：四层 + 共享数据平面

```
┌──────────── 入口层：3 种登录（同一身份的三个载体）────────────┐
│ ① 微信小程序(一线全员) ② 企微身份授权(告警/审批) ③ 网页密码(管理层) │
└───────┬────────────────┬──────────────────────┬───────────┘
        │ OpenID         │ WeCom OAuth          │ password
        └────────────────┼──────────────────────┘
┌──────────▼─── 网关层：统一接入网关 ─────────────────────────┐
│ ①三通道auth验证 ②身份映射→employee_id+dept_level(identity_map)│
│ ③路由(业务→fuadmin / AI→QM / 告警→引擎) ④三通道合一审计(IATF)  │
└─────┬──────────────────┬───────────────────────┬───────────┘
┌─────▼─────┐   ┌────────▼────────┐   ┌──────────▼──────────┐
│ 企业云      │   │ QM Core(Agent层) │   │ 主动智能层引擎(自研)    │
│ fuadmin    │   │ 40个隔离scope    │   │ 风险目录/告警状态机/   │
│ ERP+MES+WMS│   │ harness可换/cron │   │ 风暴保护/反馈闭环     │
└─────┬─────┘   └────────┬────────┘   └──────────┬──────────┘
      └─────────┬────────┴───────────┬───────────┘
           ┌────▼────────────────────▼────┐
           │  MCP Server 层(共享数据平面)    │
           │  刀具/CMM/对刀仪/MES/HR/SPC/报工 │
           │  权限在此统一执行(不下沉到入口)   │
           └────────────────┬──────────────┘
                     MySQL (fuadmin) + 告警库
```

### 身份联邦（三登录→一身份→一 scope）

| 登录方式 | 凭证 | fuadmin 字段 | 就绪度 |
|---|---|---|---|
| 小程序 | wechat_openid / wechat_id | 字段现成，40 人中 38 人已绑 | 🟢 95% |
| 网页密码 | username+password（Django hash） | system_users 本就是 Django 用户表 | 🟢 90% |
| 企微授权 | wecom_userid | 需建 identity_map 表+首次绑定流程 | 🟡 待建 |

**SSO-gate 机制**：网关验证后向 QM Core 传受信身份断言，QM 不另建账号体系——任何入口进入都落到同一 scope、同一份记忆（小程序问一半、网页继续问，上下文连续）。

### 通道×角色匹配

| 角色 | 主用 | 辅用 |
|---|---|---|
| lv6 班长（一线） | 小程序（业务+AI+告警） | 企微（收告警） |
| lv5 主管 | 小程序+企微（审批） | 网页 |
| lv3/lv4 经理/厂长 | 网页（驾驶舱/QM Web UI） | 企微（审批/告警） |
| lv1-2 决策层 | 网页+企微 | — |

### 告警三分发、反馈一闭环

引擎按`严重度×角色`路由：一级紧急→企微+短信兜底；普通→小程序内通知；周报类→企微。任何入口的 👍/👎/🔄 回写同一张反馈表，误报率模型只有一份。

**权限不下沉原则**：通道只是身份载体，授权只在 MCP 层执行一次（dept_level 行级过滤）——未来新增第四、第五种入口，数据权限零改动。

### 6 条关键设计决策

| # | 决策 | 理由 |
|---|---|---|
| 1 | **三入口+身份联邦**：小程序（一线）/企微（告警审批）/网页密码（管理层，含 QM Web UI）；统一接入网关做身份映射与审计 | 通道=身份载体，scope 与记忆跨通道连续；授权只在 MCP 层一次 |
| 2 | **QM scope 与 40 人架构图一一对应**（见四节映射） | 昨天完成的组织架构工作直接复用为 scope 开通清单 |
| 3 | **主动智能层保持独立，不进 QM** | 引擎是机器-facing 监控（7×24、确定性、IATF 审计链），QM 是人-facing 协作——生命周期不同。交汇点：①告警落库→QM agent 经 MCP 下钻解释；②小程序反馈按钮回写误报闭环 |
| 4 | **定时任务分工**：生产告警→引擎 cron；个人助理（日报/纪要/邮件 triage）→QM cron | 各用所长 |
| 5 | **Dify/OpenClaw 归位**：Dify 只做客诉复发分析+RAG；OpenClaw 为 Simon/IT 运维引擎，不对员工 | 员工-facing agent 框架只留 QM，避免双头 |
| 6 | **QM 自部署阿里云 ECS**，与企业云内网可达 MySQL/MCP | 数据不出域 |

## 七、Buzz 架构借鉴清单（审计哈希链 + YAML 工作流）

> 来源：block/buzz（27.5k⭐，Rust，Apache-2.0）源码实证——`buzz-audit` / `buzz-workflow` crate，2026-08-15 拉取。Buzz 本身不进主路线（项目仅 6 个月、Nostr 公钥身份与企微实名体系不兼容），以下两项设计吸收进自研层，QM core 不动（版本冷冻原则）。

### 7.1 审计哈希链 → 网关层"三通道合一审计"与 QM 审计模块

Buzz 每条审计是一个链式条目：`(community_id, seq)` 为主键，`hash = SHA256( tenant ‖ seq ‖ 时间戳(µs归一) ‖ action ‖ actor ‖ object ‖ canonical_json(detail) ‖ prev_hash )`，首条 prev_hash 为 32 字节零（创世）。

| # | Buzz 设计决策 | 我们的映射 |
|---|---|---|
| 1 | **租户绑定**：tenant id 排在哈希前像首位，条目无法跨链重放验证 | 对应 scope/公司代码——泰峰的审计条目不可能拼接进集团链 |
| 2 | **detail 入哈希**（key 排序的规范 JSON）：上下文任何改动即 HashMismatch | 审批意见、告警 payload、权限变更全部防篡改 |
| 3 | **时间戳归一到存储精度**（微秒）："哈希你所存储的"，从 DB 行可逐条重算 | 避免写入/验证前像分裂的坑（Buzz 自己踩过，测试钉死） |
| 4 | **detail 禁写秘密**：token/口令在类型层面无槽位 | 审计字段白名单，密钥永不落审计表 |
| 5 | **验证=顺序重算**：链 per-tenant 独立、seq 单调 | IATF 审核现场可重算演示，构成防篡改证据链 |

**落地**：网关层审计表加 `seq / prev_hash / hash` 三列 + 一个校验脚本，≈2-3 人日，M1-2 POC 期即可实施。

### 7.2 YAML 工作流 → QM cron/watch 之上的业务自服务层

Buzz 工作流为业务人员可写的 YAML：**4 触发器**（`message_posted` / `reaction_added` / `schedule`(cron 或 "1h" 间隔) / `webhook`(POST `/hooks/{id}`)），可选 evalexpr 过滤；**7 动作**（send_message / send_dm / set_channel_topic / add_reaction / call_webhook / request_approval / delay）；步骤支持 `if` 条件（不满足=跳过而非失败）与 `timeout_secs`。

| # | Buzz 设计决策 | 我们的映射 |
|---|---|---|
| 1 | **审批门=挂起-恢复**：`request_approval` 生成密码学随机 token，执行暂停、trace 保留，批准后从断点步骤续跑（超时默认 24h） | QM Strict 档审批与告警升级同构——审批应持久化"运行+断点"，而非一次性询问；一级告警 24h 未批→自动升级经理 |
| 2 | **SEC-006 混淆代理人防护**：含 `call_webhook`（数据外发）的 workflow，保存和运行都要求 owner/admin——它以保存者身份长期外发内容 | 凡"把 scope 数据发到外部"的 skill/cron 必须走晋升审批 + Auto 档以上，写进 skill 晋升流规则 |
| 3 | **触发器即业务语义**：表情（👍=批准）、定时、外部 webhook | 小程序/企微 👍👎 回写已具雏形；webhook 触发器未来可接 MES/对刀仪/视觉检等外部事件 |

**落地**：QM cron/watch 保持技术态不动，自研层加"YAML→QM cron 编译器"（外发类仅组织管理员可保存），≈3-5 人日，M3-4 随告警中心一并评估。

## 八、Agents 入门课三课借鉴清单（生产观测 + 上下文工程 + 签名回执）

> 来源：microsoft/ai-agents-for-beginners（72.2k⭐，MIT，2024-11 创建）第 10/12/18 课全文精读，2026-08-16（课程全文镜像 `C:\Users\ASUS\repos\ai-agents-for-beginners`，配套 [[AI开源课程评估与内训路径]]）。课程本体=大模型组教材，以下三组设计吸收入自研层，QM core 不动（版本冷冻原则）。

### 8.1 生产可观测性与评估（课10）→ QM run 观测层与 skill 晋升门禁

课10 要点：Trace/Span 模型（OpenTelemetry 为标准）；六类指标=延迟/成本/请求错误/用户反馈（显式👍👎+隐式重问重试）/准确率/自动评估（RAGAS、LLM Guard）；离线（金标数据集+CI 门禁）与在线（真实流量+模型漂移+A/B）双评估闭环：offline→deploy→monitor→收失败案例→补数据集→迭代；成本三策=SLM 分级+路由模型+响应缓存。

| # | 课程设计决策 | 我们的映射 |
|---|---|---|
| 1 | **Span 级追踪**：一次 agent 运行拆成 LLM 调用/工具调用逐步记录 | QM 有 RUN_STORE 运行级记录，**缺 span 级**——报工问答出错时无法定位是取数错还是推理错；自研层加 run_span 表（run_id/step/类型/耗时/token） |
| 2 | **离线评估=上线门禁**：金标数据集回归，防"越改越差" | 与 A1 路由回归基线（reverse-skill 借鉴，待立项）合并：建报工/质量问答 goldenset 50 条（口径已固化进 MCP），skill 晋升必跑 |
| 3 | **显式+隐式用户反馈**入指标 | 小程序/企微 👍👎 回写（七节已具雏形）+ "同一用户 3 分钟内重问同类问题"=隐式负反馈，回写 run 表 |
| 4 | **成本三策**（SLM 分级/路由/缓存） | 已有预算帽（$50/人/天）管总量，缺**单 run 成本可见性**；deepseek-chat 与 kimi-k3 分级路由留 M5-6 评估 |

**落地**：run_span 表 + 查询页（自研，栈与 PG 一致，不引 Langfuse 重依赖）≈3-4 人日；goldenset 50 条 ≈1 人日（与 A1 合并）；M3-4 随告警中心一并实施。

### 8.2 上下文工程四失效（课12）→ 语义口径治理与 skill 编写规范

课12 要点：上下文五型=指令/知识/工具/会话历史/用户偏好；管理六策=scratchpad/记忆/压缩/多智能体/沙箱/运行时状态；**四失效**=poisoning（幻觉入记忆反复引用→校验+检疫）、distraction（历史淹没→摘要）、confusion（工具过多→RAG 选工具，**上限<30**）、clash（新旧指令冲突→剪枝/外置 scratchpad）；**上下文检查记录**只存计数/id/哈希/策略标签，不落 prompt 原文。

| # | 课程设计决策 | 我们的映射 |
|---|---|---|
| 1 | **写长期记忆前先校验**（防 poisoning） | 我们已有活教材：agent 裸算达成率 161%（plan=0 追加单污染）——口径固化进 MCP 工具已起步；skill 编写规范加"记忆检疫"条款：凡写 scope 长期记忆的事实必须带数据源 |
| 2 | **上下文检查记录**（计数/id/哈希，不落原文） | 与 7.1 审计链互补：7.1 记"做了什么"，本项记"模型看到了什么"——不落原文天然防泄密，IATF 审核可演示 |
| 3 | **工具 loadout 上限 <30**（防 confusion） | org seed skills ~19 个 + 40 人自创后将快速膨胀——skill 路由单一事实源（A1）加规模预警线 |
| 4 | 跨会话记忆需显式写入（课12 scratchpad/记忆分层） | 实证吻合：QM 实测"请记住"不自动落长期记忆——班长 skill 模板里固化"写入长期记忆"引导语 |

**落地**：skill 编写规范增补（记忆检疫+显式记忆引导）≈0.5 人日；上下文检查记录字段随 8.1 run_span 一并建（+1 人日）；M3-4。

### 8.3 签名回执与人工审批回执（课18）→ 7.1 审计链升级 + Strict 审批密码学绑定

课18 要点：回执=Ed25519 签名 + JCS 规范 JSON（RFC 8785）+ SHA-256 + prev_hash 链（schema `agent.tool_call.v1`）；证明**归属/完整/顺序**三性，**不证明**动作正确性、策略真被执行、人-key 绑定、输入真实性；**人工审批回执**（`human.approval.v1`）：审批人签完整动作 digest，执行回执带 `parent_approval_ref`，审批/执行**双 pinned 密钥注册表**分离；拒绝态含**权限过期**（策略版本迁移/key 轮换/审批超时）与 **digest 替换**（真审批绑定假动作）；生产清单：密钥入 KMS、公钥 JWK Set 发布、链头外部锚定、append-only 存储、每条 ~500B（10K 调用/日≈1.8GB/年）；IETF 草案 draft-farley-acta-signed-receipts + 跨语言一致性测试向量。

| # | 课程设计决策 | 我们的映射 |
|---|---|---|
| 1 | **哈希链+非对称签名**：审计者仅凭公钥离线验证，不需信任我们 | 7.1 Buzz 链是无签名哈希链（自证）；升级为 Ed25519 签名链——IATF 外审/客户验厂可离线重算，证据力升一档 |
| 2 | **审批-执行双回执**：证明"人批的就是被执行的那个动作"（防 digest 替换） | 直接补齐 OWASP 自查 P0"人在回路绕过"的技术证据链；QM Strict 审批（approvalKey 三档）目前只有 DB 记录，无密码学绑定 |
| 3 | **权限过期拒绝**（策略版本/key 轮换/超时） | 映射 skill 晋升流：晋升后策略版本变更，旧审批自动失效 |
| 4 | **回执边界**（不证明正确性/策略执行） | 写进 QM runbook：回执是地基，输入校验与策略执行是另两层——防"有回执=已治理"误判 |

**落地**：随 7.1 一并实施时引入签名（密钥先走 core `.env`，KMS/JWK 发布/外部锚定留 M5-6），7.1 原估 2-3 人日 **+2 人日**；M1-2 POC 期。
