> **起因（2026-08-17）**：Simon 转发"托管式智能体平台"视频（核心主张：跳出"手搓 Agent"，建托管式平台作中央控制台；四步法=定义Prompt→挂MCP→IAM鉴权→沙箱发布；宣称 TCO 降 60%），问：**yc QM + Nextcloud + Outline + Dify 能否搭出所要求的平台？** 后经两轮深化：①supervision 确认为 roboflow 视觉库（非 Superset）；②Node-RED 作为 IoT 关键软件纳入。
> **文档定位**：本轮架构咨询的完整结论 = 能力对标 + 双星型架构 + 融合路线 + 风险清单 + 待决策项。架构图源文件见文末。

## 一、核心结论：QM 本身就是托管平台，不需要另建

视频描述的托管平台六要素，QM 全有且多数已实测。**概念纠偏：Nextcloud/Outline 不是平台组件，是 Agent 的数据/知识源；真正的平台 = QM（运行时）+ authentik（IAM）+ MCP 层（工具网关）。**

| 视频平台能力 | 我们栈的承担者 | 现状 |
|---|---|---|
| 免运维托管、多租户隔离 | QM scope 隔离（人/房间级记忆/密钥/权限/cron） | ✅ 金丝雀测试通过 |
| 定义 Prompt | QM skill 体系（个人→组织晋升流） | ✅ 全生命周期实测 |
| 挂载 MCP 工具 | opencode config mcp 段（fuadmin MCP 已通） | ⚠ 能挂但需工程师改 config，业务人员无法自助 |
| IAM 鉴权 | authentik（已部署）+ QM connector OIDC | ⚠ 设计完成，connector 待写 |
| 沙箱发布/执行拦截 | QM 安全三档（Strict 工具执行前拦截） | ✅ 审批流实测；沙箱执行需 Docker → 上 ECS 解决 |
| 统一密钥管理 | sidecar jail，key 走 core .env | ✅ 已验证 |
| 全息审计 | QM core 审计数据 | ⚠ 数据在，缺管理界面 |
| 防 Token 无底洞 | 预算帽（个人/组织双级）+ 模型目录审批（锁国产） | ✅ 内置杀手锏 |
| MCP 网关连遗留系统 | local stdio MCP | ⚠ 单机模式，未网关化/目录化 |

**视频营销话术点破**："10 万次并发 TCO 降 60%"是 SaaS 厂商口径，40 人场景永远到不了该量级，不适用。我们的经济账：自建 ≈500–2,400 元/月（模型 API DeepSeek ¥0.27/1.1 每 M tok + ECS），SaaS 托管平台对照 8,000–28,000 元/月（按席位 200–700 元/人/月 × 40 席），**自建省 80%+ 且数据不出内网（IATF 7.5.3）**。

## 二、Dify 定位决策：推荐方案 A（QM 单核）

| | 方案 A：QM 单核 ✅推荐 | 方案 B：QM+Dify 分层 | 方案 C：维持并存 |
|---|---|---|---|
| Dify 定位 | 降级为 RAG 检索 API，UI 不对业务开放 | 业务自助轻应用层（禁建自主 Agent） | 不动 |
| 割裂风险 | 无 | 中（两套权限体系） | 高（双轨=平台版"野生 Agent"） |
| 月成本 | 500–2,400 元 | 800–3,000 元 | 同 B |

推荐 A 的三条理由：①实测最大教训是**口径失控**（Agent 裸算达成率 161% vs 正式口径 83.2%），口径必须收进 QM 的 skill/MCP 层统一固化，Dify 双轨使"40 个班长问出 40 个数字"的风险翻倍；②QM skill 晋升流已实现"业务想象力→能力"的自助路径；③符合少系统、低升级频率、不被绑定的铁律。Dify 的 RAG 由 gbrain 知识库路线承接。

**QM 接入 Dify 的接法**（保留存量应用价值）：照 `mcp-fuadmin-server.py` 模板写薄 wrapper，把 Dify App API（chat-messages / workflows/run）封装为 QM 工具，0.5–1 人日。**红线：Dify 应用内模型必须锁国产，否则旁路 QM 模型目录审批，成本闸门开后门。**

## 三、双星型架构（v1.1 含 Node-RED）

不是链式串联，是两个独立的星型：

- **身份星型**：authentik = 门禁中心。人经 OIDC 登录各系统（QM connector / Gitea OAuth2 认证源 / Outline ✅已接 / Nextcloud user_oidc 插件 / OpenObserve Dex / Node-RED editor 前置代理）。账号同步源 = 企微（入离职）+ fuadmin（dept_level→权限映射）。**铁律：全系统 username = 工号，中文名仅显示名。**
- **能力星型**：QM = 调度中心。Agent 经 MCP/沙箱调用各系统能力，带 scope 权限 + actor 工号 + 审批 + 预算帽。

**集成矩阵**（SSO 接法 / QM 工具化 / 风险）：

| 系统 | SSO | QM 工具化 | 风险 |
|---|---|---|---|
| Gitea | OAuth2 认证源 | 社区 gitea-mcp / REST wrapper | 读=低，提交代码=高（挂审批） |
| Outline | ✅ 已接 | 社区 outline-mcp | 读=低，写=中 |
| Nextcloud | user_oidc 插件 | nextcloud-mcp-server（社区） | 读=低 |
| Dify | CE 无原生 SSO | 薄 MCP wrapper | ⚠ 模型旁路须锁死 |
| OpenObserve | OIDC（Dex） | 只读查询 wrapper | 低 |
| supervision | 不需要（算法库） | 沙箱 CLI / 边缘工位 | — |
| drawio/Graphviz/pandoc/MkDocs | 不需要（CLI） | 沙箱镜像预装 | 低 |
| send_wecom_file | 企微 token 独立 | QM 工具封装 | **高，必挂 Strict 审批** |

**架构图**：`企业AI托管平台总体架构-v1.1.png` / `.drawio`（本目录内，diagrams.net 可编辑）。状态编码：✅已实测、虚线框=待建、红边=高风险挂审批、⚠=旁路风险。

## 四、融合四阶段与六大融合面

| 阶段 | 名称 | 形态 | 目标 |
|---|---|---|---|
| S0 | 共存（现状） | 各系统独立，QM 实验室已通，fuadmin MCP 已接 | 现在 |
| S1 | 互联 | SSO 全通 + MCP 只读 + 小程序入口 | +8 周 |
| S1.5 | IoT 试点（新增，可与 S1 并行） | 瓶颈产线 20–30 台采集 → Node-RED → OpenObserve | +4 周 |
| S2 | 联动 | 告警→Agent 初诊→企微推送；写操作受控开放；视觉质量闭环 | +6 月 |
| S3 | 融合 | 统一语义层，跨源分析（工资×产量×质量） | +12 月 |

**关键认知：S1 是工程问题，S2 是可靠性问题，S3 是组织问题——越往后治理占比越高。**

六大融合面及首要难点：

| 融合面 | 目标态 | 首要难点 |
|---|---|---|
| 1 身份 | 一次登录全栈通行，操作溯源到工号 | actor 传递断链（深水区 2） |
| 2 数据 | 一个入口查全企业，40 人问出同一数字 | 口径治理（深水区 3）+ 工具数量爆炸（5 个 MCP server=55K token；>100 工具 SOTA 模型选错率飙升 → 每系统只暴露 3–5 个面向目标的工具） |
| 3 知识 | SOP/体系文件随问随取，且是当前有效版 | 时效（改版后旧版仍被检索=按废版操作）→ Outline 文档状态机，检索只命中"受控"；图纸二进制 → 只抽元数据卡（图号/名称/材料/关键尺寸）进知识库 |
| 4 能力 | 业务人员自助沉淀 | skill 质量参差 → 晋升即评审；skill 加 owner+版本字段 |
| 5 事件 | 出事先知道（告警→初诊→推送） | 事件风暴（200 台机床告警量会烧光 token）→ Node-RED 层过滤防抖，唤醒 ≤50 次/天 |
| 6 视觉 | 缺陷→结构化入库→关联工单批次→8D 草稿 | 图像不进上下文（GB/天级）→ 边缘处理出结构化结果，Agent 只看数据+抽样图像（≤20 张/天） |

## 五、三大深水区（一票否决级，须 Simon 拍板立规）

### 1. 客户图纸保密 × 云端大模型 —— 最高风险
产品是主机厂客户图纸（缸体/缸盖/差速器），有保密协议。Agent 经 Nextcloud MCP 读图纸→进 prompt→发云端 API = **客户知识产权流出企业边界，商务事故**。
**硬控制（代码级强制，不靠自觉）**：①客户图纸永不进云 prompt——Nextcloud 目录打标，MCP 工具层硬拒绝，仅元数据卡可检索；②内部工艺/SOP 可进云走国产模型；③必须读图纸内容的敏感任务切本地小模型通道。

### 2. actor 传递与审计链 —— IATF 合规命门
服务账号=审计断链（7.5.3 不符合项）；per-user token=40 人×6 系统=240 个 token 运维爆炸。**折中：服务账号 + actor 透传 + run_id 做 QM 审计与目标系统审计的 join key。** 只读期可先行，任何写操作上线前必须闭环此链（P3 前置验收项）。

### 3. 口径治理的组织属性 —— 技术解决不了的部分
161% vs 83.2% 的根因是"哪个口径对"没有裁决人。机制：**口径委员会**（建议 Simon+徐经理+财务）唯一裁决权；固化进 MCP/skill/flows.json 的每条口径带**版本号+生效日期+裁决人+反例说明**；变更走"提→裁决→IT 改→企微通知"流程。**没有此机制，40 个 Agent 就是 40 个口径放大器——错误数字有了 AI 的权威外衣，比没有 Agent 更糟。**（多 Agent 错误级联放大教训：错误经传播会因"一致性"获得更高可信度，交叉验证必须用独立数据源。）

## 六、Node-RED 纳入（v1.1 更新要点）

**定位**：IoT 边缘层 = 事件转译层的工业标准答案，补上融合面 5 最大的坑（物理信号转译）。事件闭环首次完整成立：

```
机床/PLC（FANUC 95%/西门子）→ Node-RED（采集·防抖·统一 schema，只搬运不判断）
→ OpenObserve（汇聚·告警）→ QM watch → Agent 初诊 → 企微推送班长
```

**分工铁律：Node-RED 做"感知"，Agent 做"判断"，统一事件 schema 解耦。**

四条新原则：
1. **流内阈值 = 隐性口径，必须评审**——"主轴负载>80% 算过载"写进 flows.json 就是未经裁决的口径定义；flows.json 进 Gitea 版本化+评审，与 MCP 口径同等待遇（三处口径一处裁决）。
2. **采集分级，绝不 200 台一把抓**——新机走 FANUC FOCAS/MTConnect（FOCAS 是付费 option，估算 3k–8k 元/台，需询价）；老机/无网口走外挂 IO 采集盒（500–2k 元/台）；先瓶颈产线 20–30 台。
3. **设备网与办公网隔离，单向上行**——边缘实例在设备网，只 push 事件出防火墙，任何请求不可下行入设备网。
4. **editor 前置 authentik 代理**——Node-RED 无原生 OIDC。

新增风险：**Node-RED 实例散落 = 新版"图纸散落个人电脑"**（工程师各自登 editor 改流）→ 生产实例只接受 Git 部署，editor 只读——与图纸失控同一解法。车间网络改造（交换机/VLAN）、边缘工控机（~4k 元/车间）为已知工程量。

**S1.5 试点投资估算：5–15 万（含 FOCAS 授权/采集盒/工控机/实施，需询价确认）。** 回报：稼动率/故障率/MTBF 从人工填报变实时计算——OEE 自动化第一次有了数据基础，也是向 40 骨干推广 Agent 最有说服力的钩子。试点成功标准：**该产线稼动率从人工填报变成大屏实时数。**

## 七、综合风险矩阵

| 风险 | 概率 | 影响 | 缓解 |
|---|---|---|---|
| 客户图纸泄密进云 API | 中 | 极高 | 深水区 1 硬隔离 |
| 口径错误规模化传播 | 高 | 高 | 深水区 3 机制 + 独立数据源交叉验证 |
| QM 上游停更/转向 | 中 | 高 | private fork + 版本冷冻（已定），core 源码已深读 |
| QM core 单点（挂=40 人全停） | 中 | 高 | ECS 进程守护 + PG 备份；S2 后考虑双实例 |
| Node-RED 实例散落 | 高 | 高 | flows.json 进 Gitea，生产只接受 Git 部署 |
| 事件风暴烧 token | 高 | 中 | Node-RED 层过滤前置 + 组织预算帽兜底 |
| PG 单库膨胀（artifact 堆积） | 高 | 中 | artifact 归档 NAS/Nextcloud，PG 只留索引 |
| 模型 API 依赖（涨价/限流） | 中 | 中 | DeepSeek/Kimi 双备份；预算帽限损 |
| 社区 MCP server 投毒/质量 | 低 | 高 | 白名单 + 锁版本 + 源码审查 |
| FOCAS 授权成本 | 确定 | 中 | 分级采集，老机外挂盒绕行 |
| 40 人早高峰并发 | 中 | 中 | 16 workers 实测；队列化；超预算排队 |

组织风险：40 骨干素养差异（skill 模板化，只点不改）；早期答错损害信任（S1 只开只读，写操作压到 S2）；IT 小组 3–4 人运维 8 系统（版本冷冻+季度三检查）；关键人依赖（每组件至少 2 人会，README 文档化）；老员工抵触（入口无感化，不新增 App）。

## 八、待 Simon 拍板清单（4 项）

1. **图纸保密红线**：客户图纸永不进云端大模型，MCP 层硬隔离——列为平台第一章程（唯一不可逆风险）。
2. **口径委员会**：成员名单（建议 Simon+徐经理+财务），随 S1 上线同步生效。
3. **S1 立项**：8 周（ECS+Docker → connector+OIDC → Gitea/Nextcloud 部署 → 首批 5 骨干试点 → 40 人推广）。
4. **S1.5 试点产线选定**：选瓶颈且网口条件最好的产线，定了出采集方案清单（机型盘点→FOCAS/MTConnect/外挂分类→询价单）。
