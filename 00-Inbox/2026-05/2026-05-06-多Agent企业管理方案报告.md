## 一、摘要

OpenClaw 提供了**完整的多 Agent 协同架构**，支持从"单一 Agent → 多 Agent 路由 → 多 Agent 多层次协同"的渐进式搭建。本文档系统阐述可用的技术方案、架构选择和实施路径。

## 二、OpenClaw 多 Agent 技术全景

### 2.1 核心能力矩阵

| 能力维度 | 支持程度 | 关键技术点 |
|----------|----------|-----------|
| **多 Agent 隔离** | ✅ 原生支持 | 独立的 workspace、session store、auth profile |
| **消息路由** | ✅ 原生支持 | binding 机制（channel → account → peer → agent） |
| **子 Agent 并行** | ✅ 原生支持 | `sessions_spawn`，深度嵌套可达5层 |
| **ACP 外部编码器** | ✅ 插件系统 | Claude Code / Gemini CLI / Codex |
| **持久会话** | ✅ 原生支持 | 会话绑定 + 线程持久化 |
| **安全沙箱** | ✅ 原生支持 | 容器级隔离，粒度 per-agent / per-session |
| **工具权限控制** | ✅ 原生支持 | per-agent tool allow/deny/profiles |
| **背景任务** | ✅ TaskFlow | 多步骤工作流编排 + 等待/恢复/状态持久化 |
| **自动化改进** | ✅ 技能框架 | Self-improving、Proactive Agent |
| **飞书/微信集成** | ✅ 渠道插件 | Feishu / WeCom 消息通道 |

### 2.2 三种 Multi-Agent 模式对比

| 模式 | 适用场景 | 隔离程度 | 通信方式 | 典型配置 |
|------|----------|----------|----------|----------|
| **多 Agent 路由** | 不同通道/用户分到不同Agent | workspace 完全隔离 | 通过 binding 静态路由 | 微信→生产Agent，飞书→质量Agent |
| **子 Agent 并行** | 一个任务拆多个子任务 | session 级隔离 | 主Agent spawn子Agent，完成后 announce | 分析OEE→并行调取各线数据 |
| **ACP 外部编码器** | 复杂编程/数据分析 | 外部进程隔离 | OpenClaw 调外部 CLI 工具 | CNC 宏程序编写→Codex |

## 三、企业级多 Agent 架构设计

### 3.1 总体架构图（文字描述）

```
                    ┌─────────────────────────────────────┐
                    │            Simon（总经理）             │
                    │        主 Agent（协调者/CEO助理）       │
                    │        思维体：全企业经营视野            │
                    └──────────┬──────────────┬────────────┘
                               │              │
             ┌─────────────────┤    sessions_spawn（子Agent，并行/串行）
             │                 │              │
     ┌───────▼───────┐ ┌──────▼──────┐ ┌─────▼───────┐
     │  生产模块Agent  │ │ 质量模块Agent │ │ 工程模块Agent │
     │  MES/OEE/排程   │ │ IATF/SPC/良率│ │ 工艺/刀具/设备 │
     └───────────────┘ └─────────────┘ └─────────────┘
                         ┌──────────────────┐
                         │  供应链/采购Agent  │
                         │  库存/供应商/物流  │
                         └──────────────────┘
                         ┌──────────────────┐
                         │  人事/财务 Agent   │
                         │  绩效/成本/预算    │
                         └──────────────────┘
```

### 3.2 设计原则

1. **一个主 Agent（CEO 助理）+ 多个专业子 Agent**：主 Agent 掌握全局语境，按需调度子 Agent
2. **子 Agent 按管理模块划分**：生产、质量、工程、供应链、人事、财务
3. **子 Agent 隔离但可通信**：每个子 Agent 有独立的 workspace/SOUL.md/TOOLS.md
4. **主 Agent 负责协调和汇总**：不直接钻入专业细节，由子 Agent 处理
5. **TaskFlow 编排跨模块流程**：复杂的多步骤流程（如"质量事故→分析→改进→验证"）用 TaskFlow 固化

### 3.3 Agent 角色定义表

| 模块 | Agent ID | 职责 | 核心文件 | 工具权限 |
|------|----------|------|----------|----------|
| CEO 助理 | `main` | 全局协调、汇报、战略决策辅助 | SOUL.md, MEMORY.md | 全部 (含 sessions_spawn) |
| 生产运营 | `production` | OEE、稼动率、排程、节拍分析 | 生产相关 skills | read, exec(受限), sessions_list |
| 质量管理 | `quality` | 良品率、SPC、IATF16949、溯源 | 质量相关 skills | read, write(报告), exec(受限) |
| 工程技术 | `engineering` | 工艺参数、刀具寿命、设备健康 | 工艺/刀具/设备 skills | read, write(参数), browser |
| 供应链 | `supply-chain` | 采购、库存、供应商、物流 | 供应相关 skills | read, web_search, browser |
| 人力资源 | `hr` | 绩效、人才、组织 | 人事相关 skills | read, write(报告) |
| 财务成本 | `finance` | 成本核算、能耗、ROI | 财务相关 skills | read, exec(受限) |
| 自动化集成 | `automation` | 交钥匙工程方案评估 | 自动化/视觉 skills | read, browser, exec(受限) |

## 四、关键技术实现

### 4.1 路由与绑定（Messages → 对应 Agent）

**核心机制**：通过 OpenClaw 的 `bindings` 配置，将不同渠道的消息路由到对应 Agent。

```json5
{
  agents: {
    list: [
      { id: "main", workspace: "~/.openclaw/workspace", default: true },
      { id: "production", workspace: "~/.openclaw/workspace-production" },
      { id: "quality", workspace: "~/.openclaw/workspace-quality" },
      { id: "engineering", workspace: "~/.openclaw/workspace-engineering" },
    ],
  },
  bindings: [
    // 老板的飞书消息 → 主Agent
    { agentId: "main", match: { channel: "feishu", accountId: "main" } },
    // 微信群/飞书群专门讨论生产 → 生产Agent
    { agentId: "production", match: { channel: "feishu", accountId: "main",
      peer: { kind: "group", id: "oc_xxxxxx_production" } } },
    // 质量群 → 质量Agent
    { agentId: "quality", match: { channel: "feishu", accountId: "main",
      peer: { kind: "group", id: "oc_xxxxxx_quality" } } },
  ],
}
```

### 4.2 子 Agent 并行与协作

**核心机制**：主 Agent 通过 `sessions_spawn` 发起子 Agent 并行任务，子任务完成后自动 announce 结果回主会话。

#### 架构配置

```json5
{
  agents: {
    defaults: {
      subagents: {
        maxSpawnDepth: 2,          // 允许子Agent再产生子Agent（主→模块→细化任务）
        maxChildrenPerAgent: 5,    // 每个Agent最多5个并发子任务
        maxConcurrent: 16,         // 全局子Agent并发上限
        runTimeoutSeconds: 300,    // 子任务默认5分钟超时
      },
    },
  },
}
```

#### 典型工作流：日生产简报生成

```
主Agent 收到Simon请求："今天生产简报"
  │
  ├─ sessions_spawn("production") → 调取OEE数据、故障清单
  ├─ sessions_spawn("quality")    → 调取良品率、SPC异常
  ├─ sessions_spawn("engineering")→ 调取设备状态、维护提醒
  │
  └─ 等待所有子Agent announce → 汇总 → 生成完整简报
```

### 4.3 TaskFlow 跨模块流程编排

**适用场景**：需要多步骤、等待外部输入、持久化状态的复杂流程。

#### 典型例子：质量事故处理流程

```
1. 质量Agent检测到批量不良 → 创建TaskFlow
2. step1: 质量Agent分析不良类型和范围
3. step2: sessions_spawn生产Agent → 排查当班设备/参数
4. step3: sessions_spawn工程Agent → 分析刀具/工艺
5. step4: 等待Simon批复处置方案（setWaiting）
6. step5: Simon确认后 → 执行围堵/返工/调整
7. finish: 生成质量事故报告
```

#### TaskFlow 配置示例

```javascript
// 质量事故处理流程 - 简化示意
const taskFlow = api.runtime.tasks.flow.fromToolContext(ctx);

const flow = taskFlow.createManaged({
  controllerId: "quality/incident-handling",
  goal: "处理质量事故",
  currentStep: "analyze",
  stateJson: {
    incidentId: "Q-20260506-001",
    product: "缸体",
    defectType: "孔径超差",
    affectedLot: "B20260505-12",
  },
});

// step2: 派发生产排查
taskFlow.runTask({
  flowId: flow.flowId,
  runtime: "subagent",
  childSessionKey: "agent:main:subagent:production-investigation",
  task: "排查当班设备MC-F-035的加工参数和刀具状态",
  status: "running",
});

// step4: 等待Simon决策
taskFlow.setWaiting({
  flowId: flow.flowId,
  currentStep: "await_simon_approval",
  waitJson: {
    kind: "reply",
    channel: "feishu",
    threadKey: "feishu:incident-001",
  },
});
```

### 4.4 Proactive Agent 模式（主动式 AI）

**核心能力**：Agent 不再只是被动响应，而是主动发现问题和机会。

适用到各模块 Agent：

| 模块 | 主动行为 | 触发条件 |
|------|----------|----------|
| 生产Agent | 推送OEE下降预警 | 某个设备连续2小时OEE<70% |
| 质量Agent | 推送SPC异常预警 | X-bar图出现连续7点同侧 |
| 工程Agent | 推送刀具寿命到期 | 某型号刀具剩余寿命<10% |
| 供应链Agent | 推送库存预警 | 某物料库存低于安全库存 |

### 4.5 WAL 协议（持久化信息）

**核心机制**：用户每次提供关键信息（决策、偏好、数据），Agent 在回复前先写入 `SESSION-STATE.md`。

- **主 Agent**：记录 Simon 的管理决策、偏好变化、公司策略调整
- **各模块 Agent**：记录本模块的关键数据更新、工艺调整、设备变更

## 七、关键考量与风险

### 7.1 模型成本估算

| 场景 | 每日预估 Token | 月费用（按 deepseek-chat 价格） |
|------|---------------|-------------------------------|
| 主Agent日常对话 | 50万 input / 10万 output | ~ ¥30-50 |
| 子Agent查询数据 | 30万 input / 5万 output | ~ ¥15-30 |
| 批量分析/报告 | 100万 input / 20万 output | ~ ¥60-100 |
| **合计** | | **~ ¥100-180/月** |

> 注意：此估算基于 deepseek-chat 价格。若使用更高阶模型（如 GPT-5、Claude），费用会显著增加。

### 7.2 风险与应对

| 风险 | 影响 | 应对措施 |
|------|------|----------|
| 子Agent间信息孤岛 | 某个模块不知其他模块的决策 | 主Agent负责统筹 + 跨Agent MEMORY共享 |
| 子Agent并行失控 | 过多子Agent同时运行消耗资源 | 设置 `maxConcurrent` 上限 + 关键流程用串行 |
| 安全/权限漏洞 | 子Agent误操作关键数据 | sandbox隔离 + tool allowlist 精确控制 |
| 幻觉/错误信息 | 不准确的数据进入管理决策 | 所有子Agent结果必须经主Agent交叉验证 |
| Simon 不习惯多Agent交互 | 使用率低，价值打折扣 | 渐进式推进，从主Agent开始，逐步增加 |

### 7.3 实施建议

1. **从主Agent强化开始**：不要一上来就建多个 Agent。先把 CEO 助理做好
2. **先做生产Agent**：这是核心价值最大的模块（OEE、排程、设备）
3. **消息通道用飞书起步**：飞书是 Simon 最常用的工具，绑定最直接
4. **每个子Agent有清晰的边界**：用 SOUL.md 定义好职责范围，避免"越权"
5. **主Agent做 Gatekeeper**：所有跨模块决策、对外报告，由主Agent统一出口
