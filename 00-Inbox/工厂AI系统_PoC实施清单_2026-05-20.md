# 工厂 AI 系统 2 周 PoC 实施清单

> 适用架构：Dify + OpenClaw + Qwen（双 RTX 5090）
> 文档日期：2026-05-20
> 目标：在投入完整架构之前，用 2 周时间验证 5 个关键假设

---

## 0. PoC 要回答的 5 个"是/否"

在叠 OpenClaw、上 35B 之前，必须回答：

1. **硬件能跑**：双 5090 在工厂电力/散热环境下，满载 30 分钟不降频?
2. **召回够用**：工厂术语、料号、缺陷代码,RAG 能不能稳定召回对的 chunk?
3. **延迟可忍**:5 个员工同时问,首字延迟 < 3 秒?
4. **权限能落**:Dify 知识库隔离能不能 100% 挡住越权?
5. **员工愿意用**:3 个真人试 1 周后,有人会主动再用?

**任一不过,先解决再扩规模。**

## D0-D1:硬件验收(不要相信发票)

### 必跑命令

```bash
# 1. 卡识别 + CUDA 版本
nvidia-smi
# 期望:2x RTX 5090,CUDA >= 12.4(5090 是 Blackwell,老 CUDA 跑不了)

# 2. PCIe 拓扑(5090 没 NVLink,跨卡通信全靠 PCIe Gen5)
nvidia-smi topo -m
# 期望:两卡之间 PIX 或 PHB;如果是 SYS(跨 NUMA),张量并行性能腰斩

# 3. P2P 带宽
# 编译 cuda-samples 里的 p2pBandwidthLatencyTest
# 期望:双向 >40GB/s(PCIe Gen5 x16 理论 64GB/s)

# 4. 满载 30 分钟不降频
gpu-burn 1800
# 另一终端监控:
watch -n1 'nvidia-smi --query-gpu=temperature.gpu,clocks.sm,power.draw --format=csv'
```

### 验收门槛

| 项目 | 通过线 | 不通过怎么办 |
|------|------|------------|
| 两卡识别 + CUDA 12.4+ | ✅ | 重装驱动 |
| P2P 带宽 >40GB/s | ✅ | 检查是否同 CPU 的 PCIe lane |
| 30 分钟满载温度 <85°C 且 SM 时钟掉幅 <10% | ✅ | **加工业风扇或换散热**,否则跑大模型必炸 |
| 整机峰值功率 < UPS 容量 80% | ✅ | 升级 UPS(双 5090+CPU 峰值 1.2-1.5kW,UPS 至少 2kVA) |

工厂电网不稳是隐形杀手,UPS 这一项不能省。

## D1-D2:Dify 单机部署

**形态**:Docker Compose。不要上 K8s,PoC 阶段运维成本远超收益。

```bash
git clone https://github.com/langgenius/dify --branch <最新稳定 tag>
cd dify/docker
cp .env.example .env
```

### .env 必改项

```ini
# 向量库
VECTOR_STORE=qdrant
QDRANT_URL=http://qdrant:6333

# 文件上传(工厂手册经常 >50MB)
UPLOAD_FILE_SIZE_LIMIT=100
UPLOAD_FILE_BATCH_LIMIT=20

# 强制 HTTPS(内网也开,否则 SSO 跳转会被浏览器拒)
NGINX_HTTPS_ENABLED=true

# SSRF 代理别关(默认开),关了员工能让 Agent 扫内网
SSRF_PROXY_HTTP_URL=http://ssrf_proxy:3128
```

### 部署后立即做的 4 件安全事

1. 改默认管理员密码(首个访问者自动变 owner,必须你本人来)
2. **关闭注册**:设置 → 仅邀请
3. 给 OpenClaw 单独生成 API Key,不要复用管理员
4. PostgreSQL 每日 cron 备份

### LLM 接入:PoC 阶段用 7B,不要直接上 35B

```bash
docker run --gpus '"device=0"' -p 8000:8000 \
  vllm/vllm-openai:latest \
  --model Qwen2.5-7B-Instruct \
  --max-model-len 8192 \
  --gpu-memory-utilization 0.85
```

GPU 0 跑 LLM,GPU 1 留给 embedding 服务。**物理隔离最稳,不要让两个服务抢同一张卡的显存。**

## D3-D5:Embedding 选型测试(最值得花时间的一步)

### 为什么最关键

LLM 答错了你能看见、会纠。**Embedding 错了你看不见——它就是没召回,员工以为系统没这个内容,慢慢就不信了。**

### 测试集构造(D3 上午)

从工程部抽 **50 份真实文档**,覆盖:

- 工艺参数表(结构化)
- 操作 SOP(步骤)
- 设备故障手册(问题-原因-方案)
- 质量标准(带表格和公差)
- 培训材料(长篇叙述)

让一个工艺工程师写 **50 个真实问题**,每题标注"答案在哪份文档第几页"。这是 ground truth。

### 候选模型

| 模型 | 维度 | 显存 | 优劣 |
|------|------|------|------|
| **bge-m3** | 1024 | ~2GB | 中文好、支持密集+稀疏混合,**首选** |
| bge-large-zh-v1.5 | 1024 | ~1.5GB | 成熟稳定,但不支持长文本 |
| Qwen3-Embedding(如可用) | 4096 | ~16GB | 同源术语理解好,显存大 |
| OpenAI text-embedding-3-large | 3072 | 0(API) | 质量基线,**但数据出网,工厂禁忌** |

### 测试矩阵

不用全跑。先固定 `chunk=512 / overlap=100`,跑 3 个 embedding,选 top-2 再微调 chunk。

### 评测指标 + 通过线

```
Recall@5  >= 80%   # 前 5 个候选里能命中
Recall@10 >= 92%   # 前 10 个几乎都能命中
MRR       >= 0.65  # 平均排名前 1-2 位
```

### 必考"硬题"

- 料号查询("BX-2034 的扭矩参数")→ 测表格 chunk 召回
- 缺陷代码("DC-07 是什么意思")→ 测缩写处理
- 跨文档("A 工艺和 B 工艺的区别")→ 测多 chunk 召回

## D6-D8:压测(用真实硬件,不是云数据)

### 压测场景

| 场景 | 并发 | 输入 token | 输出 token | 目的 |
|------|------|-----------|-----------|------|
| 基线 | 1 | 1500 | 500 | 单用户体验上限 |
| 日常 | 5 | 1500 | 500 | 一个工段同时问 |
| 高峰 | 15 | 1500 | 500 | 早班开会同时查 |
| 极限 | 30 | 1500 | 500 | 排队/拒绝拐点 |
| 长上下文 | 5 | 8000 | 500 | 全文塞进去会怎样 |

每场景跑 30 分钟。

### 关键指标 + 容忍线

```
TTFT  ≤ 3 秒   # 超过 5 秒员工就放弃
ITL   ≤ 50ms  # 100ms+ 流式明显卡顿
E2E   ≤ 15 秒(500 token 输出)
成功率 ≥ 99%  # 95% 以下员工开始抱怨
```

### 压测时三个终端同步看

```bash
# 终端1:GPU
nvidia-smi dmon -i 0,1 -s pucvmet

# 终端2:vLLM 队列深度(排队 = 延迟根因)
curl http://localhost:8000/metrics | grep -E 'num_requests|gpu_cache'

# 终端3:Dify 后端
docker stats dify-api dify-worker
```

### 不达标怎么办

| 症状 | 根因 | 处理 |
|------|------|------|
| TTFT 高 | RAG 慢 / vLLM 排队 | 加 vLLM 副本 / 优化 Qdrant 索引 |
| ITL 抖动 | KV cache 满了在抢占 | 减 max-model-len / 限并发 |
| GPU 利用率 <60% | batch 没攒够 | 调大 max-num-batched-tokens |
| OOM | 长上下文 + 高并发 | **硬上限**,必须减其一 |

## D8-D14:真实用户试用

### 选人原则

**不选**:你最铁的下属(会捧场)、IT 部门(会挑刺)。

**要选**:

- 1 个一线工艺工程师(每天查手册 5+ 次的真实用户)
- 1 个新员工(最受益群体)
- 1 个老师傅(最难取悦群体,过他这关基本就成了)

### 每日数据收集

飞书/企微 表格即可:

```
| 时间 | 问了什么 | 答得对吗 (1-5) | 答得快吗 (1-5) | 我会再问吗 |
```

每天下班 5 分钟 standup,每人说 1 个好用、1 个不好用的。

### D11 中期检查 — 出现任一项暂停 PoC

- 三人里有人 2 天没主动用 → 体验有硬伤
- 出现 1 次"看到了不该看的内容" → 权限漏洞,必须立刻定位
- 单日错误率(员工标记错答)>30% → RAG 召回有问题

## D14 决策框架

| 维度 | 通过线 |
|------|------|
| Recall@5 | ≥ 80% |
| TTFT @ 5 并发 | ≤ 3s |
| 权限零越权 | 100%(1 次都不行) |
| 主动使用率 | ≥ 60%(10 个工作日里 6 天) |
| 单次问答电费 | 算清账 |

**全过** → 进二期:叠 OpenClaw、扩 35B、铺第二个部门。

**任一不过** → **不要往上叠**。回头解决,多花 2 周比上线翻车便宜 10 倍。

## 常见坑(提前避免)

1. **PDF 解析烂**:扫描件直接进 Dify 是空的。先用 PaddleOCR 或 MinerU 转结构化文本。
2. **表格毁灭性流失**:默认 chunk 切碎表格。工艺参数表必须特殊处理(保留整表为单 chunk)。
3. **5090 驱动陷阱**:Blackwell 架构,CUDA 12.1 / PyTorch 2.1 跑不动。锁定 CUDA 12.4+ / PyTorch 2.5+。
4. **embedding 别和 LLM 抢卡**:embedding GPU 1,LLM GPU 0,物理隔离。
5. **Dify sandbox 吃 CPU**:默认有个空转的 sandbox 容器,PoC 机 CPU 弱会有感知。
6. **审计日志一开始就开**:Dify 默认不存完整 prompt,要去 PostgreSQL 手动开。后补很麻烦。
